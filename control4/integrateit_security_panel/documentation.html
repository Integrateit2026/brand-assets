1 Start here

IntegrateIT Security Panel puts the native Control4 Security screen into a room — the real one, with the arm dial, the emergency buttons, the zone list and the countdown, not a custom page made of buttons. It declares Control4's own securitypanel proxy (binding 5001) and one security partition proxy (binding 5002), plus the type-7 SECURITY_SYSTEM room binding that is what actually makes the Security tile appear in a room's Navigator. Everything on that screen is driven by this driver: 32 zones, up to 4 garage doors, arm Home and Away, entry and exit delays, bypass, trouble, an activity log, and a panic button wired to all four Navigator emergencies.

There is no panel hardware behind it. The driver holds the state and publishes it; arming the real system is Composer programming you write against the security equipment already on site — on this house, the Chowmain UniFi Protect driver's own Enable Arm Alarm / Disable Arm Alarm. That split is the whole design, and the Safety boundary section below is not boilerplate. Read it before you commission.

CONVENIENCE INTEGRATION ONLY — NOT AN ALARM PATH. This is not listed alarm signalling, it is not monitored, it does not dispatch, and it does not call a central station. The panic button summons nobody. Never present this driver to a homeowner as a monitored alarm system.
Commissioned on a real Control4 OS 3.x controller on 2026-08-27, in a live project, not a simulator. What was exercised there: the Security tile appearing in the room, the partition and its state strings, the zone list with zones auto-naming from their bound sensors, the garage limit inputs deriving position, and the arm and disarm flow end to end — and the driver's own self-test passed on that controller. Alongside that, the proxy declaration, the eight reserved partition-state strings, the zone and garage state machines, delays, bypass, emergencies, the activity log, licensing and documentation pass automated simulation QA, and every proxy string in the driver was taken from Control4's own security proxy template or from a Control4-authored driver — never inferred from another IntegrateIT driver.
Three things nobody has yet watched Navigator draw, and they stay fenced until somebody does: how the second screen's tile renders on a touch screen and in the phone app; how Navigator renders an author-defined partition state TYPE (the opt-in unconfirmed marker); and whether Navigator renders a REQUEST_ADDITIONAL_INFO prompt at all (the opt-in close-and-arm question). Each is opt-in or additive, each degrades in the safe direction, and each has a written path to closure in Bench: watching Navigator draw the open fences. Nothing else in this driver waits on them.

What you get

  • The native Navigator Security screen — arm dial with Home and Away, zone list, countdown, emergency control, and a functions button whose order is fixed and never reordered at runtime: Clear Alarm first, then Close Garages And Arm, then the siren pair, then each door as a pair — its close, then its open — and the two chime toggles last
  • A second screen of our own, shipped inside the driver — its own room tile opens a full panel page on touch screens and in the phone app, with a keypad, the zone and garage lists and the recent-activity tail. No wiring, no web server, no second control path: see The second screen
  • 32 zones, each one a Composer CONTACT_SENSOR connection plus a name and a type, that name themselves from the sensor bound to them, across nine zone types including delayed variants of Perimeter, Interior Follower and Glass Break — the entry delay is a property of the zone, not of the type
  • Up to 4 garage doors as first-class doors, each with Fully Closed, Fully Open and Obstruction inputs, four derived states and four arm behaviours
  • Arm confirmation: the driver marks an arm UNCONFIRMED until something outside Control4 says otherwise, and says so on screen
  • A panic button — Fire, Medical, Police and Panic, each firing its own programming event, never blocked by the licence gate
  • An activity log that survives a reboot, plus C4:RecordHistory records under category Security that carry the same moments into Control4's own history and app
  • A door chime while the house is disarmed, switchable from the Security screen and the second screen, plus homeowner bypass — bypass and unbypass a zone from either screen without a laptop
  • Per-zone battery with a low-battery threshold, panel trouble reporting, and two independent input paths with a Zone State Source property that tells you in 30 seconds which one is really live

2 Safety boundary

This is a convenience and status layer over security equipment the customer already owns. It is not listed alarm signalling, monitoring, or life-safety equipment, and it must never be sold, labelled, or explained to a homeowner as one. The UniFi system, its own app, and any listed communicator remain the system of record.
  • The panic button summons nobody. Pressing Panic on the Navigator Security screen fires the Panic Triggered programming event and puts the partition into ALARM. That is all it does. No call is placed, no signal is transmitted, nobody is dispatched. Whatever happens next — a siren, a push notification, an announcement, lights to full — is Composer programming a dealer wrote, and if nobody wrote it, nothing happens. Wire it before you hand the project over, and tell the homeowner in plain words exactly what it does and does not do.
  • The driver arms nothing. Armed Home, Armed Away and Disarmed are events. The real system arms because your programming told it to. If that programming is missing or fails, the Navigator screen will read ARMED while the house is not.
  • The driver fires no garage relay, and that is structural. All twelve garage connections are CONTACT_SENSOR inputs. There is no relay output on this driver, so it is not capable of moving a door. Open Garage and Close Garage raise Open Garage N Requested / Close Garage N Requested and stop there; the garage door driver you wire them to owns the obstruction sensor, the limit switches and the pre-movement warning. Routing a door around those protections from a security driver would be indefensible on a pinch hazard, so the ability was left out rather than gated.
  • Unknown counts as open. A zone the driver has never heard from blocks arming rather than showing green, and a garage door that is not positively at its closed limit counts as open — for the zone list, for arming, and for the alarm logic. A panel that renders "I have no idea" as READY is the worst bug this driver could have.
  • The Arm/Disarm Code is a convenience check. It lives in the Composer project. It is not a graded security credential, it is never logged or printed, and left blank the driver validates nothing.

3 The second screen

Alongside the native Security screen, the driver publishes a second room tile that opens a panel page the driver hosts itself. It is a proxy of its own, on binding 5003, sitting beside the panel proxy on 5001 and the partition on 5002 — one more declaration in the same driver, not a companion device. The page ships inside the driver package and is served over controller:// from the controller the driver is running on. There is no web server to install, no port to open, no address to type, and nothing about it leaves the house.

**There is no wiring step, and there is nothing you could wire. Unlike the zones and the garage limits, this proxy declares no connection at all — there is no entry for it in Connections, because a tile has nothing to bind to. It is declared by the driver, so it appears on its own once the driver is added or updated and Navigators refresh. It asks Control4 for the mobile renderer as well as the touch-screen one, so it works on Control4 touch screens and** in the phone app. It is also declared non-primary, so it does not displace the room's real device tiles or compete with the Security screen for the room — it sits alongside them.

It is not a second control path. Every button on that page sends its verb to the same partition handlers Navigator itself calls. The licence gate, the arm-mode check, the state guards, the not-ready refusal and the user-code check are the same code on the same path — there is no shortcut around any of them, and no press on this page carries more authority than the same press on the Security screen. If you want to know what a press will do, the answer is in the rest of this document; the page does not have its own rules.

What the page does have is more reach. A Navigator functions button can only carry a fixed list of function names, so a verb that needs to say which zone — bypassing zone 7 rather than zone 9 — has nowhere to put the number and cannot live there. The page has the zone list in front of it, so it can. Same handler, same gate, same refusal; it is simply able to ask a question the static menu cannot phrase.

What it shows. A state disc that carries the partition state, the arm mode and the live countdown — arming, armed, entry, exit, alarm — reading from the driver, never guessing. Under it: every published zone, faulted ones first, with open, closed, bypassed and tripped shown as the driver has them; the garage doors, with derived position and obstruction; and a recent-activity tail, the newest lines from the same activity log Print Activity Log dumps. Arm Home, Arm Away, Disarm, the functions the partition currently permits, and the emergency row are all on it.

Two of those lists behave differently, and it is worth knowing which. The functions are filtered before they are drawn: a door that is Disabled, a bypass verb for a zone that cannot be bypassed, Chime Off when the chime is already off — none of them reach the glass, because a button the driver would refuse has no business being there. The arm modes are not: Home and Away are always both drawn, exactly as they are on the native Security screen, and if Arm Modes does not permit the one that was pressed the driver refuses it and the reason lands on the page. That is the same refusal Navigator gets, from the same check, and it fails in the same direction — the house does not arm. If a site only ever wants one mode, expect the other button to be present and to say no.

The keypad honours the project. With no Arm/Disarm Code set there is nothing to check, and the page does not stand a keypad in the way of anything. With a code configured, the keypad shows exactly as many pips as that code has digits — the driver tells the page the code's length and never the code itself — and Code Required To Arm decides whether arming asks for it as well as disarming. A wrong code is reported on screen immediately, as a refusal from the driver rather than a guess by the page: the pips shake, the keypad stays up, and the attempt is not written into the activity log. The driver never prints, logs or displays a code value, and this page is not an exception to that.

It degrades rather than lies. If the page cannot reach the driver — an old package, a stale cache, a browser opened outside Navigator — it says so, labels itself a preview, and controls nothing. It never draws a state it did not receive, and it never renders a stale countdown as a live one. A page that is out of date with the driver ignores what it does not recognise instead of guessing.

The tile's rendering is one of the three open fences — see the warning at the top of this page, and Bench: watching Navigator draw the open fences for how to close it. The engine behind it is the same engine the native screen has been commissioned against.

4 Wire and commission

  1. Add IntegrateIT Security Panel to the project and to the room that should show the Security screen. The room binding is autobind, so the Security tile normally appears on its own. If it does not, open Connections and confirm Room Selection Partition 1 is bound to the room, then refresh Navigators.
  2. Bind sensors to zones. In Connections, each UniFi sensor is its own child device of the Chowmain UniFi Protect driver with two CONTACT_SENSOR control outputs — Motion Sensor and Door Sensor. Drag each output onto Zone 1…Zone 32 on this driver. A multi-sensor exposing both motion and a door contact is two zones, one per output. Note which sensor went to which zone number; that is the only bookkeeping this step needs.
  3. Set each bound zone's type, and leave its name blank. Every zone ships as Disabled on purpose — a Disabled zone is inert, is never published to Navigator, and can never block arming, so nothing appears on the Security screen until you set Zone N Type. Leave Zone N Name blank and the driver adopts the name of the device bound to that connection, so you name the sensor once in Composer and the zone follows; type a name only to override it, or when nothing is bound.
  4. Bind the garage doors — both limit switches. Each door has three inputs: Garage N Fully Closed, Garage N Fully Open and Garage N Obstruction. Bind the closed and open limits from the garage door driver. The obstruction input is optional, and a door with nothing bound to it is treated as having no obstruction, not as unknown, so a door without an obstruction sensor is still armable. Then set Garage N Mode — every door starts Disabled. Leave Garage N Name blank to adopt the name of the device bound to the Fully Closed input.
  5. Check the limit polarity before you trust it. Garage Limit Switch Polarity decides which contact state means "the door got here". Run the Print Garage Table action: it prints, per door, the mode, the name, both raw contact states, the state the driver derived from them, the obstruction and the polarity in force. Cycle one door open and closed and read it again. Backwards on the default setting makes a closed door read as in-transit — loud, wrong and safe. Backwards the other way could let an open door read closed, which is the failure that matters.
  6. Check the obstruction polarity separately. Garage Obstruction Polarity is its own property, because an obstruction beam is not a limit switch and is wired by whoever wired the door, not by whoever wired the panel. It takes two values — Same as the limit switches, the default, and Inverted - the opposite of the limit switches. How to tell in ten seconds: stand where you can see the door, with nothing under it, and read the obstruction column of Print Garage Table — or the Garage Doors property, which appends OBSTRUCTED when the input is bound and asserted. If the driver says obstructed while the beam is visibly clear, the polarity is backwards: move this property to the other value and read it again. Do it per site, not per habit — the two doors on one house are usually wired the same way, but nothing guarantees it. Getting it wrong is loud rather than dangerous — an obstruction here raises a trouble and fires Garage Door Obstructed, it never blocks an arm and never sounds the alarm — but a door permanently in trouble is a door nobody reads the trouble line on any more.
  7. Set Entry Delay (s) and Exit Delay (s) — both default 30, both accept 0–300. Set Arm Modes, and if the site wants a code, Code Required To Arm and Arm/Disarm Code. Set Chime to what the household wants — see The door chime.
  8. Wire the arm and disarm programming now, before testing — see Program the project. Without it the screen arms and the house does not.
  9. Run Refresh Zones, then Print Zone Table and Print Garage Table. Every zone and door you enabled should be listed with its name and type. If a name reads Zone 7 instead of the sensor's name, the auto-name did not resolve on this controller: type the name into Zone 7 Name.
  10. Prove the input path. Open a bound door or trip a bound motion sensor and watch the Security screen — the zone should show open and the tile should go NOT READY. Then read the Zone State Source property. That single property is the fastest answer to "is this actually working".
  11. Open the second screen and press things. Its tile appears on its own after the driver is added or updated — no wiring, see The second screen. Confirm the state disc matches the Security screen, the zone and garage lists match Print Zone Table and Print Garage Table, and the activity tail is moving. If a code is configured, type a wrong one on purpose: the refusal must appear on that screen. Then hand the homeowner the two verbs they will actually use — bypass a zone and unbypass it — from the zone list on this page, which is the only screen that carries them per zone, and show them what a bypassed zone costs (see Bypass). While you are there, press Chime Off and Chime On so they have seen the switch work.
  12. Enter the licence key. Put the key in License Key and read License Status back — it should name the controller as activated. Commissioning runs fine without one: License Enforcement defaults to Lenient, which keeps control enabled and simply nags. Move it to Strict only after a key has been minted and validated for this controller, and never before the site is otherwise finished — Strict on an unlicensed controller refuses arming, bypass, sirens, garage open and close, the chime and its two toggle verbs, and manual alarms. Disarm, cancel, clear-alarm and the emergencies are never refused either way; see Ownership, privacy, and licensing.

5 Which input path is live

Zone and garage state can reach the driver two ways, and both feed one state machine:

  • Path A — bound CONTACT_SENSOR connections. Zero programming. Bind the sensor or the limit switch, done. This is what steps 2 and 5 set up.
  • Path B — programming commands. Zone Opened(Zone) / Zone Closed(Zone) for zones, and Set Garage State(Garage, State) for doors, called from ordinary Composer programming — for UniFi sensors, driven off the Chowmain sensor driver's own Door Opened / Door Closed / Motion Detected / Motion Stopped events.

Path A delivered on the controller this driver was commissioned on — bound contacts reached the driver, zones auto-named from them, and the garage limits derived position. That is one project, on one class of sensor driver, so the driver still does not assume it: it reports it, on every site, and the first thing to read after commissioning is which path is actually live. Read the read-only Zone State Source property, or run Show Zone State Source for the same answer plus an explanation in the Lua output window:

Zone State Source readsWhat it meansWhat to do
None yet - no zone state has arrivedNothing has reported a zone or a garage limit since the driver startedOpen a bound door. If this line does not move, Path A is not delivering — build Path B.
BindingsPath A is liveNothing to do. No programming is needed for state.
ProgrammingOnly the Zone Opened / Zone Closed / Set Garage State commands are arrivingExpected if you built Path B. If you expected the bindings to work, they are not reaching this driver.
BothBoth paths are deliveringFine — they feed one state machine — but pick one so a zone is not reported twice.

Zone Source Detected fires the first time each path delivers, so you can be notified rather than watching a property.

If Path A is not delivering, build Path B: when the sensor reports open → call Zone Opened with that zone number; when it reports closed → call Zone Closed. Two lines per zone, guaranteed to work. For a door, wire its driver's fully-closed and fully-open feedback to Set Garage State with Closed, Open, Moving or Unknown. Nothing else changes — types, delays, bypass, alarms and the Security screen behave identically. Both of those inbound paths are deliberately exempt from the licence gate, so mirroring never stops.

Set Garage State takes six values, and the last two are a different kind of statement from the first four. Closed, Open, Moving and Unknown are position — they synthesise the two limit readings that position implies, through the polarity property, so a door driven from programming lands in exactly the same place by exactly the same rules as one driven from the bindings. Obstructed and Obstruction Cleared set the obstruction flag only: they raise or clear the obstruction (and with it the trouble and Garage Door Obstructed) and leave the door's derived position exactly where it was. That is the point — a beam breaking tells you something is under the door, not where the door is, and a command that moved the position because a beam broke would be inventing a fact. Anything the driver does not recognise is refused outright rather than coerced into a value that reads secure.

6 Zone types and garage doors

The entry delay belongs to the zone, not to the type: any Perimeter, Interior Follower or Glass Break zone can be given the delay by picking its (Delayed) variant, so a back door wired as a window, or a hallway motion you walk through on the way in, can both give you time to disarm. 24-Hour is the right type for leak, smoke, CO and environmental sensors: "the house is disarmed" is no reason to ignore water on the floor, and a delay would be the wrong answer there. An Entry Delay of 0 makes every delayed zone behave like its undelayed base type; an Exit Delay of 0 arms immediately. Entry/Exit zones opening during the exit delay are expected and do not alarm — but a zone still open when the exit delay expires refuses the arm rather than arming into a false siren. A (re)bind report — the state a sensor sends when Director binds it, or when you run Refresh Zones — never fires a zone event, but on an armed partition it still trips: a controller restart always comes back disarmed, so a seed report arriving on an armed house is a real sensor saying it is open.

An arm request never stops a response that is already running. Arming is refused, with ARM_FAILED, in exactly two states, whether the request comes from Navigator, a schedule or a programming rule. During an entry delay, because that countdown belongs to somebody who is already inside — accepting the arm would cancel it and drop into an exit delay, where nothing trips, and the house would reach ARMED having never alarmed. Anyone can stop an entry delay by disarming; nobody can stop one by arming over it. And during an alarm, because replacing a sounding alarm with an exit delay would swap the siren's state for "arming" and never fire Alarm Cleared — so a rule keyed on Alarm Cleared to stop the siren would never run while the siren ran on. Use Clear Alarm or Disarm. A second arm during the exit delay, or while already armed, is accepted normally and resolves to the mode asked for last, so changing your mind on the way out still works.

Clearing an alarm re-checks the house. An alarm cancels both delay timers, including an entry countdown that had nothing to do with it — a leak, a panic or a Trigger Alarm raised while somebody was walking in the front door. So when the alarm ends, the driver re-derives the truth from the zones instead of assuming the house is the one that was armed. If a zone that would really trip is still open, the entry delay restarts on that zone rather than the partition returning to a quiet ARMED that nothing is left to interrupt: the countdown is on the glass, a disarm still ends it, and if nobody acts it alarms. A still-open 24-Hour zone does not do this — it blocks no arm, so a wet leak sensor cannot loop a cleared alarm back into another one.

A garage door derives its state from its two limit inputs, and anything that is not Closed counts as open everywhere in the driver — for Zones Open, for arming, and for the alarm logic. It reads Closed only when the closed limit is made and the open limit is not; Open when the open limit is made and the closed one is not; Moving when neither is made; and Unknown when both report reached at once or when nothing has ever been heard, which also raises a trouble. A door reads Closed only because a limit switch positively said so.

Garage N Mode decides what that means. Disabled is inert and not published. Monitor only publishes the door so you can see it and program against it, but it never blocks an arm and never alarms. Secured blocks a clean arm exactly like an open door, and alarms instantly whenever it is positively not fully closed while the partition is armed — not only on the way out of Closed, so a door that was Unknown when the house armed and then reports its open limit still sounds. A door reading Unknown never sirens: a wiring or polarity fault is a trouble, not a door that moved. Secured (Delayed) is the same with the entry delay first — which is what you want on the door people actually walk through. A door that sits in Moving past Garage Close Timeout (s) raises a trouble and stays open. Enabled doors publish to Navigator as zone ids 33–36 using Control4's canonical GARAGE_DOOR zone type.

7 The door chime

The chime is the household half of Zone Opened: the back door opens, the house says so. It is a setting the driver holds and publishes, not a sound the driver makes — this driver has no audio path any more than it has a garage relay, so what a dealer wires is what anyone hears.

When it is due. The Chime property has three values and they are the whole rule. Off chimes nothing. Entry/Exit zones — chimes only zones typed Entry/Exit, which is to say the doors people actually walk through, and deliberately not the (Delayed) variants, which are windows and motion sensors a dealer granted a grace period rather than doors. All zones chimes every enabled zone that opens.

On top of that setting sits one more condition, and it is not negotiable: the partition must be disarmed. Not in an exit delay, not in an entry delay, not armed, not in alarm. That restriction is deliberate and not a convenience — on an armed house an opening zone is an alarm question, and a chime racing an entry countdown or talking over a siren is the wrong sound at the worst moment. Arming silences it; disarming brings it back. The chime is also a convenience in the licensing sense, so on a Strict unlicensed controller it stops along with the rest of them, quietly, without writing a Status line for every door in the house.

Turning it off without a laptop. Chime On and Chime Off sit in the functions menu on the Security screen and on the second screen, so a homeowner can silence the chime for an evening — dinner, a sleeping baby, a party with the patio door open — and turn it back on themselves. Only the one that would do something is offered: with the chime already off, the menu carries Chime On and not its opposite. Both screens show the current chime state, because a switch you cannot read is a switch nobody trusts. Both verbs write the Chime property, so the Composer grid, the Security screen and the second screen cannot end up disagreeing about whether the chime is on — and Chime On restores the value the dealer actually chose rather than guessing between the two "on" settings: whatever was in force when it was last switched off, or Entry/Exit zones if the driver has never seen it on. The dealer-set Chime property is the default the site starts from.

Wire the sound — to the Chime event, not to Zone Opened. The driver fires a dedicated Chime event, naming the zone, at exactly the moments above and at no others: the setting already matched, the partition was already disarmed, the licence was already checked. Wire the Announcements agent to that event and there is no condition left for you to write and no way for your condition to drift from the driver's. Play zone-open from the IntegrateIT security audio pack — for a chime, most households want the zone-open-tone variant rather than speech. Zone Opened still fires on every open regardless of the chime setting and regardless of the arm state, which is what you want for logging, lights or a rule of your own; it is the wrong trigger for a chime, because wiring it means re-implementing the disarmed check and the setting check in Composer and keeping both in step forever. Nothing plays until somebody wires it; until then the chime is a setting that nothing is listening to.

8 Bypass

Bypassing a zone tells the driver to stop counting it. That is a real reduction in the protection the house has, so it is worth being precise about what it costs and how long it lasts.

Who can do it. Bypass Zone(Zone) and Unbypass Zone(Zone) are programming commands, but the homeowner does not need programming. Three surfaces reach the same two verbs, and it is worth knowing which does what:

  • The second screen's zone list — tap a zone, bypass or unbypass it. This is the homeowner's path, and it is the only screen that carries the per-zone verbs, for the reason set out in The second screen: a Navigator functions button holds a fixed list of function names with nowhere to put a zone number, so Bypass Zone 7 cannot live there. The page has the zone list in front of it, so it can.
  • Navigator's bypass-and-arm dialog — offered at the moment an arm is refused, on the zones that refused it. That is the native screen's route to a bypass, and it is scoped to that arm.
  • Unbypass All Zones — the one bypass verb that needs no zone number, so it is reachable everywhere the others are not: the Actions tab, programming, and the second screen's functions whenever anything is actually bypassed.

24-Hour zones are the exception on purpose — the driver refuses to bypass one and says so, because a 24-Hour zone that could be bypassed is a Perimeter zone with a misleading name.

What it costs. A bypassed zone is excluded from arm admission — it stops blocking the arm, which is the whole point — and it stops tripping. It is not hidden: it still publishes as open, its tile on both screens still shows it open, and it drops off the Zones Open list only because that list answers "what would block an arm". A bypassed zone that would otherwise be your only sensor on that door is a door with nothing on it.

How long it lasts. There are three kinds, they do not last the same length of time, and the difference matters:

  • The dealer's bypass — Bypass Zone called deliberately — is sticky. It survives arms and disarms, and only Unbypass Zone or Unbypass All Zones takes it back.
  • The bypass you consented to in the arm dialog belongs to that arm, and dies with it. Disarming, or a new arm request, releases it — so the next arm is judged against the house as it actually is, never against the last request's consent.
  • An Interior Follower auto-bypassed by an Arm Home is the same: it belongs to that arm and is released when the arm ends.
A controller reboot clears every bypass, including the sticky one. No bypass is written to persistent storage — the zones are rebuilt from scratch at startup, in service, with no position claim until a sensor reports. That is the safe direction and it is deliberate; a driver that restored a bypass it could not re-justify would come back protecting less than it says. But it has a consequence worth planning for: the deliberate bypass a dealer put on a broken window sensor is gone after a power cut, and the first arm afterwards will refuse over that zone with nobody expecting it. Fix the sensor, or re-apply the bypass — do not rely on it outliving the controller.

Unbypass Zone and Unbypass All Zones release every flavour on that zone, not just the sticky one — otherwise the only way back to a live sensor is a full disarm. Both also cover the garage doors published as zones 33–36; "all zones" means all of them.

Unbypassing a zone that is open right now on an armed house puts it straight back into the alarm logic — and the driver re-runs the trip as if the sensor had just reported what it is reporting, rather than waiting for an edge that is never coming. Depending on the zone's type that means an instant alarm or an entry delay, immediately. That is correct: the alternative is ARMED standing over a known-open zone that nothing is watching. If you did not want the alarm, disarm first.

9 The arm-state truth

The UniFi system does not report its arm state back to Control4 today. The Chowmain UniFi Protect driver declares Enable Arm Alarm, Disable Arm Alarm and Set Current Arm Profile as commands, and declares no arm-state variable or event to read back. Arming from Control4 is one-way. If somebody disarms in the UniFi app, at a keypad, or with a fob, nothing tells this driver, and the Security screen will keep saying ARMED.

That is why the driver refuses to pretend. With Arm Confirmation at its default Track, show in display text, every arm this driver performs is marked UNCONFIRMED, and the Security screen's display text reads Armed Away - UNCONFIRMED (nothing outside Control4 has confirmed this). Unconfirmed does not change the partition state — an unconfirmed ARMED is still ARMED, because the fail-safe direction is to keep treating the house as armed, not to quietly disarm it. It changes only the claim. The same fact appears in the Arm Confirmation State property and the IIT_ARM_CONFIRMED variable.

A reboot never restores an arm. Not as ARMED, not as unconfirmed-ARMED, not at all. A controller restart brings the partition back disarmed and not-ready, with every zone Unknown until a sensor reports, and it stays not-ready until they do. The driver did not watch the house while Director was down, so it has nothing to restore: a cached "armed" would be the driver claiming to protect a house it has heard nothing about since before the reboot, which is the exact render this whole document exists to prevent. Nothing else survives either: every bypass is gone — the arm-scoped ones because the arm that owned them is gone, the sticky dealer one because nothing persists it (see Bypass) — and the arm confirmation goes back to having nothing to confirm. (The activity log does survive, on purpose. History that evaporates every time Director restarts is not much of a security log.)

That leaves a real gap on a house that was armed, and the driver says so rather than papering over it: on a restart it raises Arm State Unknown After Restart and a trouble, so the disagreement is visible on the Security screen, on the second screen and in the log until somebody resolves it. It fires once per restart, and only when an arm had actually completed before the controller went down — rebooting a disarmed house is an ordinary boot and says nothing.

The trouble clears itself the moment the arm question is genuinely settled, so nobody has to go and dismiss anything. Exactly four things settle it, and they are the four you would reach for:

  • an arm that completes — not one that is merely requested; an arm abandoned at the end of its exit delay leaves the question exactly as open as it found it, because a refused arm proves nothing about the house
  • a disarm that actually disarms something
  • pressing Disarm on a house this driver already reads as disarmed — the answer is "nothing to do", and that is an answer: somebody looked and confirmed it
  • Confirm Disarmed, including when this driver already believed the house disarmed — which is the ordinary reply from the programming this event exists to trigger, and the single most likely way the trouble gets cleared in practice

Anything else leaves it standing, deliberately. A cancelled arm, an exit fault, an alarm — none of them tell you what the house was doing while Director was down. Wire that event. The one line that matters is when Arm State Unknown After Restart fires → ask the real system what it is doing and reflect the answer — Confirm Armed(Mode) or Confirm Disarmed, or, on a site that would rather re-assert than ask, re-run the arm programming for the mode the house should be in. On a site with no feedback source at all, wire it to a push notification: somebody should learn that the controller rebooted while the house was armed, and that the panel no longer knows. Until the event is answered, the honest reading is the one on the screen — disarmed, not-ready, and saying why.

Upgrading to confirmed. Anything that genuinely knows the real arm state calls Confirm Armed(Mode) or Confirm Disarmed. The driver flips to Confirmed, fires Arm Confirmed, records what confirmed it and when, and restarts the Arm Confirmation Timeout (s) clock (default 60). If nothing confirms again inside that window it drops back to unconfirmed and fires Arm Confirmation Lost — wire that event if you want to know your feedback source went quiet. Set the timeout a little longer than whatever polls the real system. Both confirmation commands are inbound state mirroring, so they are never blocked by the licence gate.

Two upgrade paths exist today. If UniFi Protect is running its alarm manager in LOCAL mode, arm and disarm happen on the console rather than in the cloud and are visible to local automations and to the devices the Chowmain drivers expose — wire whatever reflects an arm or disarm there to Confirm Armed / Confirm Disarmed. If Chowmain later publishes an arm-state variable or event on the UniFi Protect driver, one Composer line per direction is the whole upgrade: when it reports armed → Confirm Armed; when it reports disarmed → Confirm Disarmed. A keypad, fob or door-code event that reliably means "somebody disarmed" is a legitimate confirmation source too. Until one of those is wired, leave the display honest. Two other settings exist: Track, show in display text and state type additionally writes the marker into the partition's state TYPE so the dial reads Away - unconfirmed — TYPE is author-defined in the Control4 contract and the eight reserved state strings are untouched either way, but nobody has yet watched Navigator render a TYPE outside its arm-states list, so it is opt-in — and Off - this driver's state is the truth suppresses the marker entirely, which belongs only on a site where something really does confirm.

10 Program the project

The recipe that makes it real — arm and disarm the UniFi system. The driver arms nothing on its own; these lines are what connect the Navigator screen to the hardware.

  • When Arm Requested fires → call the Chowmain UniFi Protect driver's Set Current Arm Profile with the profile this arm should use, then immediately its Enable Arm Alarm. Send the profile every single time, in the same programming block, right before the enable — never rely on a profile you set earlier and assume is still selected. Nothing reports the current profile back, a second integration or the UniFi app can change it, and an Enable Arm Alarm on top of a remembered-but-stale profile arms the house the wrong way with no error anywhere. Arm Requested fires before the exit delay on purpose, so the real system is arming while people are still walking out.
  • When Disarm Requested fires → call Disable Arm Alarm.
  • Use Armed Home / Armed Away instead of Arm Requested when the real system should arm only after the exit delay has actually completed. Both orderings are supported; pick one and be consistent.
  • When anything reports the real system armed or disarmed itself → call Confirm Armed / Confirm Disarmed. See The arm-state truth.

The garage doors are always two halves. This driver never fires a garage relay — that is structural, see Safety boundary — so every garage verb on it is a request that goes nowhere until you wire the other half. There are eight of them and you want all eight:

  • When Close Garage 1 Requested fires → call the garage door driver's close command for door 1. Repeat for doors 2, 3 and 4.
  • When Open Garage 1 Requested fires → call that driver's open command for door 1. Repeat for doors 2, 3 and 4.

Wire the close half and skip the open half and you get a Security screen whose Open Garage button silently does nothing — the driver raises the request, nothing answers it, and the door never moves. The open half is the one people notice missing; the close half is the one Close Garages And Arm depends on.

The order of the functions button is deliberate and not alphabetical. It is declared once, as a fixed list, and it reads: Clear Alarm, Close Garages And Arm, Play Siren, Stop Siren, then each door as a pair — Close Garage 1, Open Garage 1, Close Garage 2, Open Garage 2, and so on to door 4 — then Chime On and Chime Off. The rule inside it is that each door's close comes before that door's own open, and that the two chime verbs sit at the very end. The list is never reordered at runtime, so what a dealer reads on the bench is what a homeowner gets — and it is the order this driver fielded, so an update never moves a button somebody has already learned where to find. No Control4 reference driver declares more than two functions and no maximum is documented anywhere, which means nobody has ever watched Navigator truncate one of these lists — the cap is a hypothesis, not a measurement. The order is arranged for it anyway, as far as it can be without moving anything: if Navigator does truncate, it truncates the tail, and the tail is the chime toggles — a convenience that is also on the second screen and in the Composer property. Beyond that the ordering makes no promise it cannot keep. The tempting rearrangement (all four closes, then all four opens) would push Open Garage 1 from the sixth entry to the ninth on a driver already live in a house, spending a button people use today to insure against a failure nobody has seen. If the button does truncate on your controller, cut the list rather than reshuffle it, and tell us what you saw.

Close the garages, then arm. Close Garages And Arm(Mode) — also the second entry on the Security screen's functions button — asks every door that is not fully closed to close, waits for each to report its fully-closed limit, and arms only when they all have. It raises those same Close Garage N Requested events, so it works the moment the close half above is wired. The driver supplies the waiting, the timeout and the fail-safe: a door that has not made its closed limit inside Garage Close Timeout (s) abandons the arm, fires Not Ready To Arm and raises the bypass dialog rather than arming over an open door — and an alarm during the wait abandons it too. Open Garage On Arm chooses what a plain arm does when a door is open: refuse and offer bypass (the default, and the dialog Control4's own template documents), refuse and ask to close, close-then-arm automatically, or ignore garages entirely. Changing that setting on an armed partition re-runs every door through the alarm logic, because Ignore is the one value that lets a house arm over an open door and withdrawing it leaves the partition standing over a door it would never have armed across.

The panic recipe. When Panic Triggered fires → do the things that constitute the response: call the UniFi driver's Play Siren, send a push notification, turn every light in the house on, announce on the touch screens, start recording. Fire Emergency, Medical Emergency and Police Emergency each fire their own event and each deserves its own programming. Until you write it, the panic button changes a screen and nothing else.

Announcements — wire the audio pack. Every announcement moment already has its own event, so no event was invented to carry one. Wire the Announcements agent against these events, playing the matching file from the IntegrateIT security audio pack (distributed separately — it is not inside this driver package). Each file has a tone-only variant with a -tone suffix for sites that want a chime instead of speech:

Armed Home → armed-home · Armed Away → armed-away · Disarmed → disarmed · Exit Delay Started → exit-delay · Entry Delay Started → entry-delay · Alarm Triggered → alarm · Alarm Cleared → alarm-cleared · Zone Opened → zone-open · Zone Trouble → trouble · Low Battery → low-battery · Not Ready To Arm → not-ready · Panic Triggered → panic · Fire Emergency → fire-emergency · Medical Emergency → medical-emergency · Police Emergency → police-emergency · Garage Door Opened → garage-open · Chime → zone-open-tone. Every event description in Composer names its own file, so the wiring is visible without this page.

Note the last pair. Zone Opened fires on every open, armed or not, chime setting or not — that is the one to wire when you want a spoken announcement or a rule of your own. Chime fires only when the household actually asked for a chime on that zone and the house is disarmed, which is why it gets the tone rather than the speech. Wiring both to the same file is how a house ends up saying "back door" twice.

Push and email notifications. Control4 gives a driver no direct-send API — C4:SendEmail, C4:SendPushNotification and C4:NotifyEvent do not exist. The documented path is the agents: add the Push Notification and Email Notification agents to the project and wire them in programming against this driver's events, exactly as you would for any other driver. Both agents require a current 4Sight subscription on the account. Without 4Sight, push and email silently stop — no error reaches the driver, and no supported call can ask whether 4Sight is current. What still works without it: every event still fires, the activity log still records, and the history records still land in Control4's own history. What breaks: the push arriving on a phone and the email leaving the controller. If notifications stop, check 4Sight first.

The siren is two events, not a switch. Play Siren and Stop Siren — on both screens' functions menu, on the Actions tab, and as programming commands — raise Siren Requested and Siren Stop Requested and stop there, for the same reason the garage buttons do: this driver owns no siren. Wire both halves, and wire them to the same siren: when Siren Requested fires → call the UniFi driver's Play Siren (or whatever sounds on this site); when Siren Stop Requested fires → call the matching stop. Wiring the start and not the stop leaves a siren that only a person with the vendor's own app can silence, which is the one asymmetry worth avoiding here.

Other events worth wiring: Alarm Triggered and Alarm Cleared (lights, recording, valve shutoff — the alarm type is in Partition State), Entry Delay Started (announce "disarm now"), Chime (the door chime, already scoped to a disarmed house and the household's setting — see The door chime), Zone Opened / Zone Closed (every open and close, unconditionally — the raw signal, for logging, lights and rules of your own), Zone Bypassed / Zone Unbypassed (a zone left or returned to service, whoever did it and from whichever screen), Low Battery and Zone Trouble (a dying sensor should reach you before it goes silent), Arm State Unknown After Restart (the controller rebooted and the panel no longer knows what the house is doing — see The arm-state truth), Garage Door Opened / Closed / Moving / Obstructed (the door is named in Last Garage Door Event, written before the event fires, so a conditional inside the event reads the door that just moved).

Feeding data in. Set Zone Battery(Zone, Battery Percent) and Set Zone Trouble(Zone, Trouble Text) are how a sensor's own reported battery and health reach this driver — on UniFi, wire them from the Chowmain sensor driver's Battery Status and Connected State. Log Note(Note) writes a line of your own into the activity log and history: use it to record what the driver cannot see for itself, such as which person or which schedule acted.

Saying something of your own. Send Notification(Severity, Message) is programming's way into the same notification pipe the driver's own events use. Pick Info, Warning or Critical and give it a line of text; it lands in the activity log and in Control4's history under category Security, is debounced on exactly the same terms as everything else, and — like everything else — Critical is never debounced. Use it where a rule knows something the driver structurally cannot: "front gate held open 10 minutes", "arm skipped, cleaner is here". It is the same treatment an alarm gets, so spend Critical accordingly. Log Note is its quieter sibling: a log line, not a notification.

Putting zones back in service is Unbypass Zone(Zone) for one and Unbypass All Zones for the lot — both release every flavour of bypass and Unbypass All Zones covers the garage doors too. Read Bypass before you wire either into a schedule: on an armed house, returning an open zone to service can alarm immediately, by design.

Zone Opened, Bypass Zone, Open Garage, Set Zone Battery and the rest take their zone or garage number as a Composer parameter widget, so there is one command per verb, not one per zone. Actions cannot carry parameters — a Control4 XML limit — so the Actions tab gets parameterless equivalents for bench testing. There are four, and they are named on the tab exactly as follows: Bypass All Open Zones, Unbypass All Zones, Close All Garages and TEST: Trigger Burglary Alarm (LIVE). The TEST: prefix and the (LIVE) suffix are not decoration — that action really triggers the alarm, on the real partition, with everything wired to Alarm Triggered running. The four emergencies and Play Siren carry the same marking on the same tab for the same reason. Nothing on the Actions tab is a simulation.

12 The activity log and notifications

The driver keeps its own activity log — a ring buffer bounded by Activity Log Size (default 100, max 500), written to PersistData so it survives a driver restart and a controller reboot. Bounded on purpose: an unbounded log on a chattering sensor is a memory leak with a security label on it. Every line is timestamp · severity · subcategory · what happened · via <source>. Severity is Critical (the alarm and the four emergencies), Warning (not-ready, trouble, low battery, an obstruction, a lost arm confirmation) or Info (everything else). Subcategory is one of Arming, Alarm, Emergency, Zone, Garage, Trouble, Notification, System. The source is the part a dealer usually wants: Navigator (somebody at the native Security screen), WebView (somebody on the second screen — the same press, on the other surface, and worth telling apart when two people are in the house), Programming (a Composer rule or a programming command), Binding (a sensor or limit switch reported it), Restore (rebuilt from PersistData at boot) or Driver (the driver's own timer, such as an entry delay expiring). Read it three ways: the Activity Log property for a glance, Print Activity Log for the whole buffer in the Lua output window, and Clear Activity Log to start fresh. Log Note adds your own line.

The same moments are also written to Control4's own system history with C4:RecordHistory under category Security, which is the documented, supported way a driver reaches Control4's notification machinery and what makes these events visible in the Control4 app's history. Notification History chooses how much goes there: Off, Critical only, Critical and Warning (the default) or Everything — which adds every arm, disarm, delay, bypass, zone and garage transition, and is a lot of rows on a busy house. Notification Debounce (s) sets the minimum gap between two records saying the same thing about the same zone or door, because Composer's own help warns that notifications on high-frequency events cause performance problems and a chattering contact is exactly that. Critical records are never debounced — an alarm and the four emergencies always write, every time, no matter how fast they repeat. History and notification dispatch are never blocked by the licence gate either: a lapsed licence must not silence an alarm notification.

Notification Status is the only honest answer to "are my notifications working". It reports what can be proven from inside a driver — how many history records were written and when, which agent names resolved, when a send was last attempted, and the last error verbatim. A row saying an agent did not resolve is a real finding. A row saying a send was attempted is not a delivery receipt and never will be.

Notification Agents and Announcements each offer an experimental option that additionally tries to resolve those agents by name and drive them directly. Both are off by default and fenced: the agent names and command strings are unverified, the experimental path never replaces the documented programming path, every attempt is logged with exactly what was resolved and exactly what was sent, and the outcome lands in Notification Status. Run Probe Notification Agents to see what resolves on this controller, and Send Test Notification / Send Test Announcement to exercise it — the announcement test never fires a real security event to test itself.

13 Bench: watching Navigator draw the open fences

Three things in this driver are fenced because nobody has watched Navigator render them — not because the calls behind them are in doubt. Each is opt-in, each fails in the safe direction, and each closes the moment one dealer with a controller and ten minutes looks at a screen and reports what it drew. If you are already commissioning a project, you can close all three. Send what you saw — a photo of the screen is ideal — to support@integrateit.tech, and the fence comes out of the next build.

Fence 1 — the close-and-arm question. Does Navigator draw a REQUEST_ADDITIONAL_INFO prompt at all? The call is fully verified against Control4's own partition proxy; the rendering is not.

  1. Set Garage 1 Mode to Secured. It must be Secured or Secured (Delayed) — a Monitor only door never blocks an arm, so it never reaches the prompt and the test would pass by doing nothing.
  2. Set Open Garage On Arm to Refuse and ask to close.
  3. Call Set Garage State with garage 1 and Open (or open the real door).
  4. Press Arm on the Security screen, and watch it.

What should appear is a prompt reading "Close the garage door(s) and arm?" naming door 1. The arm is refused either way — the refusal is not conditional on the dialog appearing, so a Navigator that draws nothing leaves the house disarmed rather than armed, and the door cannot sound because the partition never armed. Answering yes runs Close Garages And Arm; answering no, or letting it sit longer than five minutes, leaves the house disarmed. Report which of the three you got: the prompt, nothing at all, or something malformed.

Fence 2 — the unconfirmed marker in the state TYPE. Does Navigator render a partition state TYPE that is not one of its arm-mode names? TYPE is author-defined in the Control4 contract and the eight reserved STATE strings are untouched either way, so this is legal by the letter of the spec and unwatched in practice.

  1. Set Arm Confirmation to Track, show in display text and state type.
  2. Get the house ready first — if you have just run Fence 1, put that door back to Closed and confirm the tile reads DISARMED_READY, or this test refuses instead of arming.
  3. Arm the partition — Home or Away, either one.
  4. Read the dial.

If it reads Away - unconfirmed, the fence comes out and this becomes a candidate default. If it renders oddly, blankly, or falls back to something generic, the fence stays and the setting keeps its warning. Either way the house is still ARMED and still treated as armed: the marker is a claim about confidence, never about state. Disarm afterwards and put the property back to Track, show in display text unless you like what you saw.

Fence 3 — the second screen's tile. How does the driver-hosted page render where people actually touch it?

  1. Add or update the driver and refresh Navigators. The tile is declared by the driver — there is nothing to bind.
  2. Open it on a touch screen and again in the phone app, which are different renderers and deserve separate looks.
  3. Confirm the state disc matches the Security screen through one full arm and disarm, that the zone and garage lists match Print Zone Table and Print Garage Table, and that the activity tail moves.
  4. If a code is configured, type a wrong one deliberately: the refusal must land on that screen, the keypad must stay up, and nothing must appear in the activity log.

Report the two screenshots and anything that rendered at the wrong size. The engine underneath is the same engine the native screen was commissioned against — what is unwatched here is the drawing, not the security.

15 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation built on Control4's documented DriverWorks security proxy protocol. It does not bundle another vendor's runtime, source code, brand assets, trial system, or licence, and it never talks to UniFi — or to any other vendor's cloud or LAN service — directly. Every interaction with the existing security hardware goes through Composer programming you write, using that hardware's own driver. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

Nothing about the house leaves the controller. Zone and garage names, their states, the partition state, the activity log, the arm code and the default user code live only in Director and the driver's own PersistData. The arm code is never printed, never logged, and never placed in a status line, and when Notification Email Address is set the driver passes it with command logging suppressed so the address does not land in the Director log. The shared IntegrateIT licence and update services are the only outbound path, and they carry the controller identity, driver slug, version, configured licence key, and update channel as documented in the reference below.

Lenient mode is the default: it allows commissioning without an activated key and keeps License Status visible. Strict mode refuses control — arming, bypass, sirens, garage open and close, the door chime and its toggle verbs, and manually triggered alarms — until a key has been minted and validated for that controller. Disarming, cancelling an arm and clearing an alarm are never refused while there is something to disarm: this driver can raise an alarm unlicensed, because panic is exempt, so it must never be able to start a siren it then refuses to stop, and it refuses loudly, naming the reason in the Security screen's display text rather than leaving the Navigator dial stuck with no explanation. Three things are deliberately exempt from that refusal: inbound state mirroring, because what a sensor or a limit switch did is not an action this driver is taking; the activity log, the history records and the notification path, because a lapsed licence must never silence an alarm notification; and the emergency path, because a lapsed licence must never silence a panic button. Installing this package does not itself mint or activate a controller licence.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
