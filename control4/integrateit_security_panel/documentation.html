1 Start here

IntegrateIT Security Panel puts the native Control4 Security screen into a room — the real one, with the arm dial, the emergency buttons, the zone list and the countdown, not a custom page made of buttons. It declares Control4's own securitypanel proxy (binding 5001) and one security partition proxy (binding 5002), plus the type-7 SECURITY_SYSTEM room binding that is what actually makes the Security tile appear in a room's Navigator. Everything on that screen is driven by this driver: 32 zones, up to 4 garage doors, arm Home and Away, entry and exit delays, bypass, trouble, an activity log, and a panic button wired to all four Navigator emergencies.

There is no panel hardware behind it. The driver holds the state and publishes it; arming the real system is Composer programming you write against the security equipment already on site — on this house, the Chowmain UniFi Protect driver's own Enable Arm Alarm / Disable Arm Alarm. That split is the whole design, and the Safety boundary section below is not boilerplate. Read it before you commission.

CONVENIENCE INTEGRATION ONLY — NOT AN ALARM PATH. This is not listed alarm signalling, it is not monitored, it does not dispatch, and it does not call a central station. The panic button summons nobody. Never present this driver to a homeowner as a monitored alarm system.
Ready for controlled commissioning. The proxy declaration, the eight reserved partition-state strings, the zone and garage state machines, delays, bypass, emergencies, the activity log, licensing and documentation pass automated simulation QA, and every proxy string in the driver was taken from Control4's own security proxy template or from a Control4-authored driver — never inferred from another IntegrateIT driver. Nothing here is bench-tested. A qualified dealer must add it to a real project and confirm the Security screen, the arm flow, the zone list and the garage doors on the actual Navigator touch screens and app before handoff.

What you get

  • The native Navigator Security screen — arm dial with Home and Away, zone list, countdown, emergency control, and a functions button carrying Clear Alarm, Close Garages And Arm, the siren, and per-door garage open and close
  • 32 zones, each one a Composer CONTACT_SENSOR connection plus a name and a type, that name themselves from the sensor bound to them, across nine zone types including delayed variants of Perimeter, Interior Follower and Glass Break — the entry delay is a property of the zone, not of the type
  • Up to 4 garage doors as first-class doors, each with Fully Closed, Fully Open and Obstruction inputs, four derived states and four arm behaviours
  • Arm confirmation: the driver marks an arm UNCONFIRMED until something outside Control4 says otherwise, and says so on screen
  • A panic button — Fire, Medical, Police and Panic, each firing its own programming event, never blocked by the licence gate
  • An activity log that survives a reboot, plus C4:RecordHistory records under category Security that carry the same moments into Control4's own history and app
  • Per-zone battery with a low-battery threshold, panel trouble reporting, and two independent input paths with a Zone State Source property that tells you in 30 seconds which one is really live

2 Safety boundary

This is a convenience and status layer over security equipment the customer already owns. It is not listed alarm signalling, monitoring, or life-safety equipment, and it must never be sold, labelled, or explained to a homeowner as one. The UniFi system, its own app, and any listed communicator remain the system of record.
  • The panic button summons nobody. Pressing Panic on the Navigator Security screen fires the Panic Triggered programming event and puts the partition into ALARM. That is all it does. No call is placed, no signal is transmitted, nobody is dispatched. Whatever happens next — a siren, a push notification, an announcement, lights to full — is Composer programming a dealer wrote, and if nobody wrote it, nothing happens. Wire it before you hand the project over, and tell the homeowner in plain words exactly what it does and does not do.
  • The driver arms nothing. Armed Home, Armed Away and Disarmed are events. The real system arms because your programming told it to. If that programming is missing or fails, the Navigator screen will read ARMED while the house is not.
  • The driver fires no garage relay, and that is structural. All twelve garage connections are CONTACT_SENSOR inputs. There is no relay output on this driver, so it is not capable of moving a door. Open Garage and Close Garage raise Open Garage N Requested / Close Garage N Requested and stop there; the garage door driver you wire them to owns the obstruction sensor, the limit switches and the pre-movement warning. Routing a door around those protections from a security driver would be indefensible on a pinch hazard, so the ability was left out rather than gated.
  • Unknown counts as open. A zone the driver has never heard from blocks arming rather than showing green, and a garage door that is not positively at its closed limit counts as open — for the zone list, for arming, and for the alarm logic. A panel that renders "I have no idea" as READY is the worst bug this driver could have.
  • The Arm/Disarm Code is a convenience check. It lives in the Composer project. It is not a graded security credential, it is never logged or printed, and left blank the driver validates nothing.

3 Wire and commission

  1. Add IntegrateIT Security Panel to the project and to the room that should show the Security screen. The room binding is autobind, so the Security tile normally appears on its own. If it does not, open Connections and confirm Room Selection Partition 1 is bound to the room, then refresh Navigators.
  2. Bind sensors to zones. In Connections, each UniFi sensor is its own child device of the Chowmain UniFi Protect driver with two CONTACT_SENSOR control outputs — Motion Sensor and Door Sensor. Drag each output onto Zone 1…Zone 32 on this driver. A multi-sensor exposing both motion and a door contact is two zones, one per output. Note which sensor went to which zone number; that is the only bookkeeping this step needs.
  3. Set each bound zone's type, and leave its name blank. Every zone ships as Disabled on purpose — a Disabled zone is inert, is never published to Navigator, and can never block arming, so nothing appears on the Security screen until you set Zone N Type. Leave Zone N Name blank and the driver adopts the name of the device bound to that connection, so you name the sensor once in Composer and the zone follows; type a name only to override it, or when nothing is bound.
  4. Bind the garage doors — both limit switches. Each door has three inputs: Garage N Fully Closed, Garage N Fully Open and Garage N Obstruction. Bind the closed and open limits from the garage door driver. The obstruction input is optional, and a door with nothing bound to it is treated as having no obstruction, not as unknown, so a door without an obstruction sensor is still armable. Then set Garage N Mode — every door starts Disabled. Leave Garage N Name blank to adopt the name of the device bound to the Fully Closed input.
  5. Check the limit polarity before you trust it. Garage Limit Switch Polarity decides which contact state means "the door got here". Run the Print Garage Table action: it prints, per door, the mode, the name, both raw contact states, the state the driver derived from them, the obstruction and the polarity in force. Cycle one door open and closed and read it again. Backwards on the default setting makes a closed door read as in-transit — loud, wrong and safe. Backwards the other way could let an open door read closed, which is the failure that matters.
  6. Set Entry Delay (s) and Exit Delay (s) — both default 30, both accept 0–300. Set Arm Modes, and if the site wants a code, Code Required To Arm and Arm/Disarm Code.
  7. Wire the arm and disarm programming now, before testing — see Program the project. Without it the screen arms and the house does not.
  8. Run Refresh Zones, then Print Zone Table and Print Garage Table. Every zone and door you enabled should be listed with its name and type. If a name reads Zone 7 instead of the sensor's name, the auto-name did not resolve on this controller: type the name into Zone 7 Name.
  9. Prove the input path. Open a bound door or trip a bound motion sensor and watch the Security screen — the zone should show open and the tile should go NOT READY. Then read the Zone State Source property. That single property is the fastest answer to "is this actually working".

4 Which input path is live

Zone and garage state can reach the driver two ways, and both feed one state machine:

  • Path A — bound CONTACT_SENSOR connections. Zero programming. Bind the sensor or the limit switch, done. This is what steps 2 and 5 set up.
  • Path B — programming commands. Zone Opened(Zone) / Zone Closed(Zone) for zones, and Set Garage State(Garage, State) for doors, called from ordinary Composer programming — for UniFi sensors, driven off the Chowmain sensor driver's own Door Opened / Door Closed / Motion Detected / Motion Stopped events.

Path A has never been confirmed on real hardware for this class of binding, so the driver does not assume it — it reports it. Read the read-only Zone State Source property, or run Show Zone State Source for the same answer plus an explanation in the Lua output window:

Zone State Source readsWhat it meansWhat to do
None yet - no zone state has arrivedNothing has reported a zone or a garage limit since the driver startedOpen a bound door. If this line does not move, Path A is not delivering — build Path B.
BindingsPath A is liveNothing to do. No programming is needed for state.
ProgrammingOnly the Zone Opened / Zone Closed / Set Garage State commands are arrivingExpected if you built Path B. If you expected the bindings to work, they are not reaching this driver.
BothBoth paths are deliveringFine — they feed one state machine — but pick one so a zone is not reported twice.

Zone Source Detected fires the first time each path delivers, so you can be notified rather than watching a property.

If Path A is not delivering, build Path B: when the sensor reports open → call Zone Opened with that zone number; when it reports closed → call Zone Closed. Two lines per zone, guaranteed to work. For a door, wire its driver's fully-closed and fully-open feedback to Set Garage State with Closed, Open, Moving or Unknown. Nothing else changes — types, delays, bypass, alarms and the Security screen behave identically. Both of those inbound paths are deliberately exempt from the licence gate, so mirroring never stops.

5 Zone types and garage doors

The entry delay belongs to the zone, not to the type: any Perimeter, Interior Follower or Glass Break zone can be given the delay by picking its (Delayed) variant, so a back door wired as a window, or a hallway motion you walk through on the way in, can both give you time to disarm. A (Delayed) zone behaves exactly like its base type in every other way.

24-Hour is the right type for leak, smoke, CO and environmental sensors: "the house is disarmed" is no reason to ignore water on the floor, and a delay would be the wrong answer there. An Entry Delay of 0 makes every delayed zone behave like its undelayed base type; an Exit Delay of 0 arms immediately. Entry/Exit zones opening during the exit delay are expected and do not alarm — but a zone still open when the exit delay expires refuses the arm rather than arming into a false siren. A (re)bind report — the state a sensor sends when Director binds it, or when you run Refresh Zones — never fires a zone event, but on an armed partition it still trips: a controller restart always comes back disarmed, so a seed report arriving on an armed house is a real sensor saying it is open.

An arm request never stops a response that is already running. Arming is refused, with ARM_FAILED, in exactly two states, whether the request comes from Navigator, a schedule or a programming rule. During an entry delay, because that countdown belongs to somebody who is already inside — accepting the arm would cancel it and drop into an exit delay, where nothing trips, and the house would reach ARMED having never alarmed. Anyone can stop an entry delay by disarming; nobody can stop one by arming over it. And during an alarm, because replacing a sounding alarm with an exit delay would swap the siren's state for "arming" and never fire Alarm Cleared — so a rule keyed on Alarm Cleared to stop the siren would never run while the siren ran on. Use Clear Alarm or Disarm. A second arm during the exit delay, or while already armed, is accepted normally and resolves to the mode asked for last, so changing your mind on the way out still works.

Clearing an alarm re-checks the house. An alarm cancels both delay timers, including an entry countdown that had nothing to do with it — a leak, a panic or a Trigger Alarm raised while somebody was walking in the front door. So when the alarm ends, the driver re-derives the truth from the zones instead of assuming the house is the one that was armed. If a zone that would really trip is still open, the entry delay restarts on that zone rather than the partition returning to a quiet ARMED that nothing is left to interrupt: the countdown is on the glass, a disarm still ends it, and if nobody acts it alarms. A still-open 24-Hour zone does not do this — it blocks no arm, so a wet leak sensor cannot loop a cleared alarm back into another one.

A garage door derives its state from its two limit inputs, and anything that is not Closed counts as open everywhere in the driver — for Zones Open, for arming, and for the alarm logic. It reads Closed only when the closed limit is made and the open limit is not; Open when the open limit is made and the closed one is not; Moving when neither is made; and Unknown when both report reached at once or when nothing has ever been heard, which also raises a trouble. A door reads Closed only because a limit switch positively said so.

Garage N Mode decides what that means. Disabled is inert and not published. Monitor only publishes the door so you can see it and program against it, but it never blocks an arm and never alarms. Secured blocks a clean arm exactly like an open door, and alarms instantly whenever it is positively not fully closed while the partition is armed — not only on the way out of Closed, so a door that was Unknown when the house armed and then reports its open limit still sounds. A door reading Unknown never sirens: a wiring or polarity fault is a trouble, not a door that moved. Secured (Delayed) is the same with the entry delay first — which is what you want on the door people actually walk through. A door that sits in Moving past Garage Close Timeout (s) raises a trouble and stays open. Enabled doors publish to Navigator as zone ids 33–36 using Control4's canonical GARAGE_DOOR zone type.

6 The arm-state truth

The UniFi system does not report its arm state back to Control4 today. The Chowmain UniFi Protect driver declares Enable Arm Alarm, Disable Arm Alarm and Set Current Arm Profile as commands, and declares no arm-state variable or event to read back. Arming from Control4 is one-way. If somebody disarms in the UniFi app, at a keypad, or with a fob, nothing tells this driver, and the Security screen will keep saying ARMED.

That is why the driver refuses to pretend. With Arm Confirmation at its default Track, show in display text, every arm this driver performs is marked UNCONFIRMED, and the Security screen's display text reads Armed Away - UNCONFIRMED (nothing outside Control4 has confirmed this). Unconfirmed does not change the partition state — an unconfirmed ARMED is still ARMED, because the fail-safe direction is to keep treating the house as armed, not to quietly disarm it. It changes only the claim. The same fact appears in the Arm Confirmation State property and the IIT_ARM_CONFIRMED variable. An arm restored after a controller reboot comes back UNCONFIRMED, never Confirmed — the driver did not watch the house while it was down and will not pretend it did.

Upgrading to confirmed. Anything that genuinely knows the real arm state calls Confirm Armed(Mode) or Confirm Disarmed. The driver flips to Confirmed, fires Arm Confirmed, records what confirmed it and when, and restarts the Arm Confirmation Timeout (s) clock (default 60). If nothing confirms again inside that window it drops back to unconfirmed and fires Arm Confirmation Lost — wire that event if you want to know your feedback source went quiet. Set the timeout a little longer than whatever polls the real system. Both confirmation commands are inbound state mirroring, so they are never blocked by the licence gate.

Two upgrade paths exist today. If UniFi Protect is running its alarm manager in LOCAL mode, arm and disarm happen on the console rather than in the cloud and are visible to local automations and to the devices the Chowmain drivers expose — wire whatever reflects an arm or disarm there to Confirm Armed / Confirm Disarmed. If Chowmain later publishes an arm-state variable or event on the UniFi Protect driver, one Composer line per direction is the whole upgrade: when it reports armed → Confirm Armed; when it reports disarmed → Confirm Disarmed. A keypad, fob or door-code event that reliably means "somebody disarmed" is a legitimate confirmation source too. Until one of those is wired, leave the display honest. Two other settings exist: Track, show in display text and state type additionally writes the marker into the partition's state TYPE so the dial reads Away - unconfirmed — TYPE is author-defined in the Control4 contract and the eight reserved state strings are untouched either way, but nobody has yet watched Navigator render a TYPE outside its arm-states list, so it is opt-in — and Off - this driver's state is the truth suppresses the marker entirely, which belongs only on a site where something really does confirm.

7 Program the project

The recipe that makes it real — arm and disarm the UniFi system. The driver arms nothing on its own; these lines are what connect the Navigator screen to the hardware.

  • When Arm Requested fires → call the Chowmain UniFi Protect driver's Set Current Arm Profile with the profile this arm should use, then immediately its Enable Arm Alarm. Send the profile every single time, in the same programming block, right before the enable — never rely on a profile you set earlier and assume is still selected. Nothing reports the current profile back, a second integration or the UniFi app can change it, and an Enable Arm Alarm on top of a remembered-but-stale profile arms the house the wrong way with no error anywhere. Arm Requested fires before the exit delay on purpose, so the real system is arming while people are still walking out.
  • When Disarm Requested fires → call Disable Arm Alarm.
  • Use Armed Home / Armed Away instead of Arm Requested when the real system should arm only after the exit delay has actually completed. Both orderings are supported; pick one and be consistent.
  • When anything reports the real system armed or disarmed itself → call Confirm Armed / Confirm Disarmed. See The arm-state truth.

Close the garages, then arm. Close Garages And Arm(Mode) — also the second entry on the Security screen's functions button — asks every door that is not fully closed to close, waits for each to report its fully-closed limit, and arms only when they all have. Wire it as two halves: when Close Garage 1 Requested fires → call the garage door driver's close command for door 1, and the same for doors 2–4. The driver supplies the waiting, the timeout and the fail-safe: a door that has not made its closed limit inside Garage Close Timeout (s) abandons the arm, fires Not Ready To Arm and raises the bypass dialog rather than arming over an open door — and an alarm during the wait abandons it too. Open Garage On Arm chooses what a plain arm does when a door is open: refuse and offer bypass (the default, and the dialog Control4's own template documents), refuse and ask to close, close-then-arm automatically, or ignore garages entirely. Changing that setting on an armed partition re-runs every door through the alarm logic, because Ignore is the one value that lets a house arm over an open door and withdrawing it leaves the partition standing over a door it would never have armed across.

The panic recipe. When Panic Triggered fires → do the things that constitute the response: call the UniFi driver's Play Siren, send a push notification, turn every light in the house on, announce on the touch screens, start recording. Fire Emergency, Medical Emergency and Police Emergency each fire their own event and each deserves its own programming. Until you write it, the panic button changes a screen and nothing else.

Announcements — wire the audio pack. Every announcement moment already has its own event, so no event was invented to carry one. Wire the Announcements agent against these events, playing the matching file from the IntegrateIT security audio pack (distributed separately — it is not inside this driver package). Each file has a tone-only variant with a -tone suffix for sites that want a chime instead of speech:

Armed Home → armed-home · Armed Away → armed-away · Disarmed → disarmed · Exit Delay Started → exit-delay · Entry Delay Started → entry-delay · Alarm Triggered → alarm · Alarm Cleared → alarm-cleared · Zone Opened → zone-open · Zone Trouble → trouble · Low Battery → low-battery · Not Ready To Arm → not-ready · Panic Triggered → panic · Fire Emergency → fire-emergency · Medical Emergency → medical-emergency · Police Emergency → police-emergency · Garage Door Opened → garage-open. Every event description in Composer names its own file, so the wiring is visible without this page.

Push and email notifications. Control4 gives a driver no direct-send API — C4:SendEmail, C4:SendPushNotification and C4:NotifyEvent do not exist. The documented path is the agents: add the Push Notification and Email Notification agents to the project and wire them in programming against this driver's events, exactly as you would for any other driver. Both agents require a current 4Sight subscription on the account. Without 4Sight, push and email silently stop — no error reaches the driver, and no supported call can ask whether 4Sight is current. What still works without it: every event still fires, the activity log still records, and the history records still land in Control4's own history. What breaks: the push arriving on a phone and the email leaving the controller. If notifications stop, check 4Sight first.

Other events worth wiring: Alarm Triggered and Alarm Cleared (lights, recording, valve shutoff — the alarm type is in Partition State), Entry Delay Started (announce "disarm now"), Zone Opened / Zone Closed (chime), Low Battery and Zone Trouble (a dying sensor should reach you before it goes silent), Garage Door Opened / Closed / Moving / Obstructed (the door is named in Last Garage Door Event, written before the event fires, so a conditional inside the event reads the door that just moved).

Feeding data in. Set Zone Battery(Zone, Battery Percent) and Set Zone Trouble(Zone, Trouble Text) are how a sensor's own reported battery and health reach this driver — on UniFi, wire them from the Chowmain sensor driver's Battery Status and Connected State. Log Note(Note) writes a line of your own into the activity log and history: use it to record what the driver cannot see for itself, such as which person or which schedule acted. Zone Opened, Bypass Zone, Open Garage, Set Zone Battery and the rest take their zone or garage number as a Composer parameter widget, so there is one command per verb, not one per zone. Actions cannot carry parameters — a Control4 XML limit — so the Actions tab gets parameterless equivalents (Bypass All Open Zones, Close All Garages, Trigger Alarm (Burglary)) for bench testing.

9 The activity log and notifications

The driver keeps its own activity log — a ring buffer bounded by Activity Log Size (default 100, max 500), written to PersistData so it survives a driver restart and a controller reboot. Bounded on purpose: an unbounded log on a chattering sensor is a memory leak with a security label on it. Every line is timestamp · severity · subcategory · what happened · via <source>. Severity is Critical (the alarm and the four emergencies), Warning (not-ready, trouble, low battery, an obstruction, a lost arm confirmation) or Info (everything else). Subcategory is one of Arming, Alarm, Emergency, Zone, Garage, Trouble, Notification, System. The source is the part a dealer usually wants: Navigator (somebody at a touch screen or in the app), Programming (a Composer rule or a programming command), Binding (a sensor or limit switch reported it), Restore (rebuilt from PersistData at boot) or Driver (the driver's own timer, such as an entry delay expiring). Read it three ways: the Activity Log property for a glance, Print Activity Log for the whole buffer in the Lua output window, and Clear Activity Log to start fresh. Log Note adds your own line.

The same moments are also written to Control4's own system history with C4:RecordHistory under category Security, which is the documented, supported way a driver reaches Control4's notification machinery and what makes these events visible in the Control4 app's history. Notification History chooses how much goes there: Off, Critical only, Critical and Warning (the default) or Everything — which adds every arm, disarm, delay, bypass, zone and garage transition, and is a lot of rows on a busy house. Notification Debounce (s) sets the minimum gap between two records saying the same thing about the same zone or door, because Composer's own help warns that notifications on high-frequency events cause performance problems and a chattering contact is exactly that. Critical records are never debounced — an alarm and the four emergencies always write, every time, no matter how fast they repeat. History and notification dispatch are never blocked by the licence gate either: a lapsed licence must not silence an alarm notification.

Notification Status is the only honest answer to "are my notifications working". It reports what can be proven from inside a driver — how many history records were written and when, which agent names resolved, when a send was last attempted, and the last error verbatim. A row saying an agent did not resolve is a real finding. A row saying a send was attempted is not a delivery receipt and never will be.

Notification Agents and Announcements each offer an experimental option that additionally tries to resolve those agents by name and drive them directly. Both are off by default and fenced: the agent names and command strings are unverified, the experimental path never replaces the documented programming path, every attempt is logged with exactly what was resolved and exactly what was sent, and the outcome lands in Notification Status. Run Probe Notification Agents to see what resolves on this controller, and Send Test Notification / Send Test Announcement to exercise it — the announcement test never fires a real security event to test itself.

11 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation built on Control4's documented DriverWorks security proxy protocol. It does not bundle another vendor's runtime, source code, brand assets, trial system, or licence, and it never talks to UniFi — or to any other vendor's cloud or LAN service — directly. Every interaction with the existing security hardware goes through Composer programming you write, using that hardware's own driver. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

Nothing about the house leaves the controller. Zone and garage names, their states, the partition state, the activity log, the arm code and the default user code live only in Director and the driver's own PersistData. The arm code is never printed, never logged, and never placed in a status line, and when Notification Email Address is set the driver passes it with command logging suppressed so the address does not land in the Director log. The shared IntegrateIT licence and update services are the only outbound path, and they carry the controller identity, driver slug, version, configured licence key, and update channel as documented in the reference below.

Lenient mode is the default: it allows commissioning without an activated key and keeps License Status visible. Strict mode refuses control — arming, bypass, sirens, garage open and close, and manually triggered alarms — until a key has been minted and validated for that controller. Disarming, cancelling an arm and clearing an alarm are never refused while there is something to disarm: this driver can raise an alarm unlicensed, because panic is exempt, so it must never be able to start a siren it then refuses to stop, and it refuses loudly, naming the reason in the Security screen's display text rather than leaving the Navigator dial stuck with no explanation. Three things are deliberately exempt from that refusal: inbound state mirroring, because what a sensor or a limit switch did is not an action this driver is taking; the activity log, the history records and the notification path, because a lapsed licence must never silence an alarm notification; and the emergency path, because a lapsed licence must never silence a panic button. Installing this package does not itself mint or activate a controller licence.

Refused, with ARM_FAILED, while an entry delay is counting down or while the partition is in alarm: an arm request starts protecting the house and is never a way to stop a response already running. L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

  • Initial scaffold (template: blank).
  • Added a deterministic invariant fuzzer to tests.lua — three seeded walks over the whole input alphabet, asserting the six prime invariants after every input. It found five defects that three rounds of case-writing had not, each now pinned by its own named regression case:
  • a (re)bind seed report on an ARMED partition published the zone as open and tripped nothing, leaving the panel armed over a live open sensor;
  • a garage door reaching Open from Unknown while armed never tripped, because the trip demanded the door had left fully closed;
  • clearing an alarm judged the house with the arm-admission test, which excuses an Interior Follower in Home — including one the dealer had put back in service — and returned the partition to a quiet ARMED over it;
  • the exit-fault check had the same hole, for a follower released mid-delay;
  • turning Open Garage On Arm away from "Ignore" on an armed partition left it standing over a door it would never have armed across.
  • Two more defects, both found by an adversarial round that attacked the families the fuzzer was written for, and both fixed here with mutation-proven cases:
  • R4-2 (high). An arm request could DISARM a house. armPartition() admits an already-ARMED partition, installCycle() then replaced the live completed cycle with a pending one and dropped into EXIT_DELAY — which trips nothing by design — and every path that gave up on the pending arm went to restingState(), never back to the arm it superseded. A nightly "Arm Away" schedule firing on a house that was already Armed Away therefore opened sixty seconds of no protection, every night; and if anything was open when the delay expired the house ended DISARMED with no Disarmed event at all, so no dealer rule ran and nobody's phone buzzed. Three changes: a same-mode re-arm on an ARMED partition is now a no-op that disturbs nothing; a cycle records the completed arm it displaced; and abandonArm() and ARM_CANCEL hand the house back to that arm instead of to disarmed. The invariant is "an arm request may never leave the house less protected than it found it".
  • R4-1 (high). Losing ONE of a door's two limit contacts derived MOVING — a positive position claim — out of a hole. invalidateGarageReading(g, why, "closed") nils only closedRaw; deriveGarageState() then saw c=nil, o=false and fell through to MOVING, which evaluateGarageTrip reads as positively-not-closed. Pulling a limit binding in ComposerPro on an armed house sounded a burglary alarm on a door that never moved. The door now tracks whether a limit was never bound (single-contact install, survivor is authoritative, still trips) or lost (no position claim, derives UNKNOWN, blocks the next arm, never sirens).
  • Two new fuzzer invariants, because both defects were invisible to the six that shipped: I7 — an input that cannot be an intrusion (a binding change, a reboot) may never sound a siren; I8 — once ARMED, only a disarm-shaped input or a reboot may end it. I7 catches R4-1 at gate size in ~50 inputs. I8 is a long-odds net at 7,500 inputs (the round that found R4-2 needed 288,000), so the named regression cases, not the fuzzer, are what pin R4-2.
  • I8 also caught its own author: latching only on the STATE meant Confirm Disarmed, which ends an arm while deliberately leaving the partition state alone, left the latch set and blamed the next input that surfaced it. The latch now clears on a disarming input too.
  • Press the same arm button twice to skip the countdown. Daniel's ask, and it needed no new command: a second request for the mode ALREADY counting down IS that second press, whichever surface it came from — Navigator, a keypad, an experience button, a schedule. It completes through finishArming(), not straight to ARMED, so the exit-fault check still runs and an instant arm over a door somebody left open is refused exactly as loudly as a timed one. Entry delay is untouched on purpose: skipping the walk-out time must not mean walking back into an instant-trip front door. That completes a three-way split on one request — EXIT_DELAY + same mode arms now, ARMED + same mode does nothing, either + a different mode is a mode change with its own delay.
  • The fuzzer caught the first draft of that within seconds of it landing: it fired Arm Requested, which announced an ACCEPTANCE that had not been judged. A zone opened between the two presses is caught by finishArming() so the driver was never unsafe, but the wire said an arm had been accepted over an open zone with no consent, and I1 said so at step 2379. The second press is not a new request — the request was made and judged at the first press — so it fires nothing, and what follows (Armed, or Not Ready To Arm) is the honest account.
  • N9 — a routine arm could evict the alarm from the activity log. The ring was while #gLog > cap do table.remove(gLog, 1) end: oldest out, whatever it was. installCycle() fires one Zone Bypassed per zone whose effective bypass moved and fire() writes a ring line for each, so on a house full of Interior Followers ONE ordinary Arm Home wrote enough lines to bury the alarm before it — at the manifest minimum of 10 entries, PRINT_ACTIVITY_LOG showed thirteen lines and not one said "Alarm Triggered". Critical entries are now evicted only when nothing else is left to drop, so an alarm survives any amount of routine traffic and is lost only to a newer alarm. The dealer's chosen log size is still honoured exactly; only WHICH line leaves has changed.
  • N10 — free text is capped at 180 characters. A 20,000-character Log Note produced a 20,069-character Activity Log property, which was then rewritten into PersistData on every subsequent event. A log entry is a line, not a document.
  • Doc precision: Zones Open lists zones that are open and not bypassed, and the troubleshooting row no longer claims "the open zone is never hidden" — it is never hidden from its own tile or from ZONE_STATE, only from that row, which exists to list what would block an arm.
