1 Start here

IntegrateIT Code Agent is a headless Control4 driver that runs a short, dealer-authored automation script written entirely in Composer properties. You type up to eight steps into the Step 1 … Step 8 properties; the driver compiles them against a closed vocabulary of eight verbs — SET, ADD, IF, GOTO, WAIT, FIRE, LOG, STOP — and refuses anything else at parse time. There is no code file, no download, no network trigger, and no Lua evaluation. The script keeps named registers, compares them, waits, and raises one of four Agent Events; your existing Composer programming does the real work in response. There is no Navigator tile — the agent computes and raises events, and nothing more.

The agent is an interpreter over a fixed verb list, not an evaluator. It never compiles or runs dealer text as code, never opens a socket or a URL, and has no remote trigger — a run starts only from Composer programming on this controller. Everything that actually moves in the house stays in your programming, gated by Control4's own model.
Release candidate — simulator-verified, physical-controller acceptance still pending. The parser, the closed vocabulary, the step budget, single-flight execution, the stale-WAIT-timer identity check, the mid-run plan snapshot, register rollback on every abort path, persistence, and licensing all pass automated QA. A qualified dealer must still commission on a real controller and confirm the events drive the intended programming.

What you get

  • Eight Composer-authored steps over a closed verb vocabulary — no code files, no downloads
  • Named registers with SET, arithmetic with ADD, and six-operator comparison with IF
  • GOTO loops made safe by a hard per-run step budget that always terminates
  • Four FIRE-able Agent Events plus Run Started / Completed / Aborted / Script Rejected for programming
  • Fail-closed parsing: one bad step refuses the whole script, so a half-valid program never runs its valid prefix
  • Register rollback on every abort — manual, script edit, budget exhaustion, a bad ADD, or a restart mid-run
  • A rolling audit of the most recent steps and the run outcome in AGENT_LOG
  • MAC-locked IntegrateIT licensing, Lenient or Strict

2 The execution contract

This driver's whole promise is what it cannot do, so it states it plainly:

  • No code execution. Dealer text is tokenized and matched against the fixed verb list; it is never compiled, loaded, or evaluated. An unrecognized verb is a parse rejection, not a pass-through — a Lua expression like os.execute("id") fails the allowlist exactly like any typo.
  • No blast radius. The agent cannot drive a device, open a socket, fetch a URL, or touch the filesystem. Its only outputs are its own registers, its own read-only properties, its eight events (four Agent Events plus the four run-lifecycle ones), and six programming variables. Anything that MOVES is your programming reacting to those events.
  • No remote surface. There is no listener, URL handler, or poll. A run begins only when Composer programming — or the Actions tab — calls Run Script on this controller.
  • Fail-closed, all-or-nothing. One bad step invalidates the entire script, including the valid steps above it, and Script Status names the first refused step. A run requested against an invalid script finds no plan at all and raises Script Rejected.
  • Bounded. GOTO makes loops expressible, so every run carries a hard step budget (Max Steps Per Run, default 64). Skipped steps spend fuel too, so IF + GOTO cannot spin for free. When the budget hits zero the run aborts and rolls back — a controller cannot be wedged by a bad script.
  • Reversible. Registers are snapshotted at run start; every abort restores that snapshot, so an aborted run leaves no half-applied state. A completed run keeps its writes; an aborted one does not. Registers update live as each step runs, so a value read mid-run is provisional until the run reaches STOP or the end of the list.

3 Wire and commission

  1. Add IntegrateIT Code Agent to a room. It is headless — no Navigator tile, no connections to bind.
  2. Type your steps into Step 1 … Step 8, one verb per line, in order — the verb grammar is The script language immediately below.
  3. Watch Script Status. It reads Valid - N step(s) when the script compiles, or Invalid - step N: … naming the first step it refused. An invalid script does not partly run.
  4. Set Max Steps Per Run — the hard budget for one run (1–256, default 64). Lower it when you loop deliberately; the default is generous for an eight-line script.
  5. Set Max Wait (sec) (1–3600, default 300) to the longest WAIT anyone may author. A longer WAIT is refused when it is typed, not when it runs. Tightening this later re-validates the current script.
  6. Choose Persist Registers (register values survive a Director restart only when Yes) and On Script Edit (whether editing a Step mid-run aborts the run or lets it finish against the plan it started with).
  7. Optionally enter a License Key — the driver runs in Lenient mode without one (see Licensing).
  8. In Programming, call Run Script where the logic should start, and react to Agent Event 1…4. Run it once and watch Run State, Registers, and your event programming react — that is the proof it works.

A worked example — hold the path lights for two minutes after the last person leaves, but only in the evening:

StepLineMeaning
1IF Evening = 1Only continue in the evening; otherwise step 2 is skipped.
2FIRE 1Programming reacts: dim the path lights.
3WAIT 120Hold two minutes.
4FIRE 2Programming reacts: all off.
5STOPDone.

Your programming sets Evening through the Set Register command (REGISTER = Evening, VALUE = 1) before it calls Run Script.

4 The script language

A step is one whole-word verb, a space, then its arguments. FIRE1 is refused; FIRE 1 is the step — a token welded to a verb is rejected under its whole name, never quietly split. Blank lines and lines beginning with # are comments: skipped, never errors.

VerbFormWhat it does
SETSET <register> <value>Store text in a register. The value is the rest of the line, up to 64 printable characters.
ADDADD <register> <number>Add a finite number to a register. An unset register reads as 0; a register holding text the sum cannot parse aborts the run rather than overwriting it.
IFIF <register> <op> <value>Compare with = <> > < >= <=. The value is the rest of the line, exactly like SET. When the test is false, the one step after it is skipped.
GOTOGOTO <1-8>Jump to another step by its Step-property number. A GOTO into an empty step is refused at parse time.
WAITWAIT <seconds>Suspend the run for a whole number of seconds, 1 to Max Wait (default 300), then resume where it left off.
FIREFIRE <1-4>Raise Agent Event 1 through 4 for programming to react to.
LOGLOG <text>Write 1 to 120 printable characters to the audit log and the Lua output window.
STOPSTOPEnd the run successfully. Takes no argument.

Register names are identifiers — a letter followed by letters, digits, or underscores, up to 16 characters, with no dots, brackets, or spaces. Comparisons run as numbers when both sides parse as numbers, otherwise as text; an unset register reads as empty text, so a comparison against it is always defined and never crashes the run. Note that ADD reads an unset register as 0 while IF reads it as empty — the two verbs read "unset" differently on purpose. A non-finite ADD amount (1e400) is refused at parse time, and a sum that accumulates to infinity aborts the run rather than parking a poisoned value.

5 Program the project

The Actions tab exposes Validate Script, Run Script, Abort Run, Reset Registers, and Print Configuration. Composer Programming gets three commands under those same names — Run Script, Abort Run, and Set Register — and all three are refused while a run is in flight.

Set Register is the one with a caveat worth reading. A Control4 command carries no parameter fields into Composer Programming, so firing it from programming supplies no REGISTER and it refuses with Set Register refused: no REGISTER parameter supplied. It takes its REGISTER / VALUE pair only when another driver calls it. Seed a register from a Composer scene by putting the seed in the script itself — a leading SET step — rather than by trying to pass parameters in.

Hang your logic off the events:

  • When Agent Event 1 fires → dim the path lights. A FIRE 1 step is the driver-to-project hand-off; author the actual device control here.
  • When Run Aborted fires → notify or re-arm. The run hit its budget, a bad ADD, a manual abort, or a mid-run edit; the registers are already back to their pre-run values.
  • When Script Rejected fires → stop and look at Script Status. It names the first refused step by number, so a typo surfaces as a diagnosis rather than as a run that quietly never happened.

AGENT_RUNNING is the variable to gate automation on — it is true only while a run is Running or Waiting. Only a completed run keeps its register writes, so treat any value read during a run as provisional until Run Completed fires. 8 Ownership, privacy, and licensing

This package is an original IntegrateIT driver. It bundles no other vendor's runtime, source, brand assets, or license. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

Nothing the agent does leaves the controller. There is no network surface — no socket, no URL, no telemetry — so your script text, register values, and audit log stay on the controller. The only outbound traffic is the shared IntegrateIT license and update services, which use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below; the license key is never written to the audit log or printed by any diagnostic.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks Run Script, Abort Run, Reset Registers, and Set Register until the Ops Portal has minted and validated a key for this controller; Validate Script and Print Configuration stay available either way, because inspecting a script changes nothing. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means

Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

  • The three programming commands were declared as RUN_SCRIPT / ABORT_RUN / SET_REGISTER, so Composer Programming listed them in SCREAMING_SNAKE while the guide called them Run Script / Abort Run / Set Register — a dealer following the documentation looked for a command that was not in the list under that name. The declared names are now the human ones, the convention every other driver in the fleet follows. **If an existing project has RUN_SCRIPT, ABORT_RUN, or SET_REGISTER dragged into a programming script, re-drag it as Run Script / Abort Run / Set Register after the update** — Composer binds programming to the declared name, so a renamed command leaves the old line orphaned. Nothing else breaks: the runtime still answers the old spellings, so any driver-to-driver call and any queued command keeps working, and there was no way to hold both names in the list without leaving every dealer a permanently duplicated command tree.
  • Set Register refusals now name the real cause. A Control4 command carries no parameter fields into Composer Programming, so firing it from programming supplies no REGISTER and it refused with "invalid register name" — blaming the dealer for a field they were never given. It now reads "no REGISTER parameter supplied", and the guide states that the parameterized path is the driver-to-driver one.
  • Documentation corrections: the outputs list said "four Agent Events" and omitted the four run-lifecycle events; the Registers status row said "empty after a rollback" when a rollback restores the pre-run values.
  • Documentation rendering: emphasis written as *emphasis* in the source now renders as emphasis in the packaged Documentation tab instead of shipping as literal asterisks. Protocol strings that legitimately contain a star, quoted inside code, stay exactly as written.

Numeric properties now fall back to their documented default when non-finite, and the transmit chokepoint refuses a non-finite value by name.

v0.1.12026-07-26
  • Documentation rebuilt to the IntegrateIT commissioning-guide standard: uniform sections, honest contracts, verified claim-by-claim against the code.
  • **Parser: a verb must be a whole word.** `FIRE1` used to split into `FIRE 1` and run. The allowlist claims a closed vocabulary, so a token welded to a verb is now refused under its whole name rather than quietly reinterpreted.

  • **T8 now covers a restart mid-run.** Registers were committed to PersistData as each step ran, so a controller that died mid-run came back holding half an unfinished run's writes. The pre-run snapshot is now parked for the life of the run and restored on boot if the run never reached an ending.
