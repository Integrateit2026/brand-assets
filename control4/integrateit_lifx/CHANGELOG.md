## [0.5.0] - 2026-07-30
- Light effects. **Flash**, **Pulse** and **Breathe** drive the waveform engine that already lives in LIFX firmware over SetWaveform (type 103) — you hand the light a target color, a period, a cycle count and a shape, and the light animates the transition itself. No controller timers, no burst of frames, and all three put the light back exactly where they found it. The 21-byte payload is packed byte-exactly and was verified against two independent official sources that agree field for field: lan.developer.lifx.com (changing-a-device#setwaveform---packet-103, plus the dedicated Waveforms page for the semantics) and LIFX's own machine-readable definition at github.com/LIFX/public-protocol, whose protocol.yml declares `light.LightSetWaveform` at `size_bytes: 21` with exactly this field order — reserved u8, transient BoolInt, HSBK, period u32, cycles float32, skew_ratio i16, waveform u8. The Waveform enum (SAW 0, SINE 1, HALF_SINE 2, TRIANGLE 3, PULSE 4) is confirmed identically on three official surfaces: the field-types page, the Waveforms page, and protocol.yml's `LightWaveform`.
- **Flash and Breathe both send SINE, and that is the honest answer rather than a shortcut.** LIFX documents five waveforms, and TWO of them return to the current color *within every cycle* — the vendor's own transient rule names exactly that pair ("the waveform is SINE or TRIANGLE"): SINE, "the color will cycle smoothly from current color to `color` and then end back at current color", and TRIANGLE, "light interpolates linearly from current color to `color`, then back to current color". Flash and Breathe take SINE because it is the SMOOTH one of the two, which is what reads as a flash or a breath; TRIANGLE's linear ramp is equally documented and simply has no command here. What rules HALF_SINE out is firmer than a preference: it is documented as one-directional — "light interpolates smoothly from current color to `color`" — so what it does BETWEEN cycles is documented nowhere, and a Flash built on it would have undefined behavior the moment a dealer set Effect Cycles above 1. This factory does not ship undocumented behavior behind a dealer-facing property, so Flash and Breathe are the same documented shape at two tempos (Effect Period (ms) defaulting to 800, Breathe Period (ms) to 4000) and the driver says so out loud instead of inventing a second mechanism and dressing it up as different. Two period properties land in the one u32 `period` field the wire actually has — better two honest presets than one value multiplied behind the dealer's back.
- **transient is set on all three, and the docs say precisely why that matters unevenly.** The vendor's rule is exact: "if `transient == true` or the waveform is `SINE` or `TRIANGLE` then the device will return to the original color after the effect. Otherwise the device will not revert." So on Flash and Breathe the flag is REDUNDANT — SINE returns on its own. On Pulse it is LOAD-BEARING: PULSE is neither SINE nor TRIANGLE, so without that one byte the light would be left sitting on the effect color when the cycles ran out. Both facts are in the code comments and the Documentation tab rather than smoothed into a single vague claim, because the difference is exactly what a dealer needs to know before trusting Pulse to hand a room back.
- Pulse exposes the duty cycle as a **Effect Duty %** property mapped through LIFX's own documented scale. skew_ratio is "a signed Int16 that is scaled from 0 to 1" across the full i16 span, and for PULSE the duty cycle is "1 - skew_ratio as a percentage of the cycle duration" — the fraction of each cycle spent on the new color. So Duty D% goes onto the wire as `round((1 - D/100) * 65535) - 32768`, which reproduces the vendor's own scaling table EXACTLY at 0%, 25%, 50% and 100%. At 75% it lands on -16384 where the table prints -16383; that row is itself rounded (-16383 scales to 0.25002) and -16384 is the nearer wire value for exactly 0.25, one LSB out of 65536 — 0.0015%. The driver prefers the value that inverts the documented formula, and both the reasoning and the discrepancy are written down rather than papered over. Non-PULSE waveforms still pack skew_ratio at its documented offset, at mid-scale 0, because LIFX assigns the field no meaning outside PULSE — the same rule skyType and cloudSaturationMin already follow in the tile-effect payload.
- **The float32 problem, solved honestly instead of generally.** `cycles` is an IEEE-754 single and this factory packs bytes with arithmetic in portable Lua 5.1 — no bit library, no string.pack. Rather than write a general float codec that would quietly round, denormalize, or mangle what it cannot represent, the driver packs the subset it can PROVE: an integer in [1, 2^24] has an exact float32 representation, and its three fields are pure integer arithmetic — sign 0, exponent found by repeated doubling (never `math.log`, which can be off by one at a power of two), mantissa `(v / 2^e - 1) * 2^23`. Effect Cycles therefore offers whole numbers only, 1-255, and the constraint is stated plainly in the property description, the changelog and the Documentation tab rather than hidden. The packer is pinned in the suite against the constants every float reference agrees on — 1.0 = 0x3F800000, 2.0 = 0x40000000, 3.0 = 0x40400000, 5.0 = 0x40A00000, 10.0 = 0x41200000, 255.0 = 0x437F0000 — and separately against little-endian byte ORDER, because a byte-swapped packer would satisfy a hex comparison and still be wrong on the wire. A value it cannot encode exactly is refused BY NAME; it never sends an approximation of the number the dealer typed. That refusal is the codec's CONTRACT rather than a dealer-facing path, and the distinction is worth stating precisely because the hardening below closes the hole it was originally written for: LuaJIT's `tonumber` parses "nan", and a NaN survives both range clamps (NaN < 1 and NaN > 255 are each false), so before this release the codec's own domain check really was the last thing standing between a non-finite property and four bytes of wire. With the non-finite guard now in `intProp`, Effect Cycles is clamped to 1-255 and a non-numeric or non-finite entry falls back to the default 3 — so nothing a dealer can type in Composer reaches the domain check any more, and the refusal Status is unreachable from the property surface. The codec keeps refusing anyway, for any future caller that does not arrive through a clamped property. The suite proves the reachable half: a non-finite Effect Cycles sends the default 3.0 (0x40400000) and never NaN bytes.
- SetWaveformOptional (119) is implemented because it is officially documented and it earns its place: LIFX describes it as behaving "like SetWaveform (103) but allows you to keep certain parts of the original HSBK values during the transition" via four trailing BoolInts, and protocol.yml declares `light.LightSetWaveformOptional` at `size_bytes: 25`. That is what makes the one behavior most installs actually want possible — **flash the porch light without turning it a different color**. The new Effect Channels property routes an effect through 103 (full HSBK), or through 119 with `set_brightness` alone, or through 119 with hue/saturation/kelvin and brightness left untouched. An unrecognized selection falls back to full-color 103 rather than sending 119 with no flags set, which would modulate nothing at all.
- Effects are a capability family and follow this driver's rule for every family before them: **refused until the device positively proves it is a light.** Waveforms are plain Light messages — LIFX attaches no "requires the device has the X capability" note to 103/119 the way it does to SetInfrared and SetHevCycle — so "is this thing a light" is the entire question, and the IS_LIGHT register introduced in 0.4.0 already answers it. This is deliberately STRICTER than the core Power / Set Color gate, which passes while the question is still open so that every bulb this driver has ever controlled behaves exactly as it did in 0.1.0; a new family gets no such grandfathering. A confirmed LIFX Switch refuses all three by name in LIFX's own word for it and points at the relay commands; an unconfirmed device refuses too, and names Refresh State as the action that settles it. 103 and 119 were also added to the LIGHT_TYPES set that reads StateUnhandled (223), so a device that declines an effect frame teaches the driver the same thing a declined Light Get does — leaving them out would have let a 223 for an effect frame mean nothing.
- **No event, no variable, and that is a finding rather than an omission.** LIFX documents both 103 and 119 as returning a LightState (107) — but that is the ordinary response-to-a-Set reporting the light's state at that instant, NOT a report that the effect finished, and protocol.yml carries no GetWaveform and no StateWaveform of any kind. Nothing in the protocol says an effect started, finished, or was accepted, so nothing here claims it: an effect is fire-and-forget, and the Documentation tab says so in those words. There is also no documented message that CANCELS a running effect, so no Stop command was invented — the honest guidance is to keep cycles x period short, and that is what the docs say.
- Effects deliberately schedule **no catch-up poll**, unlike every other control path in this driver. All three return the light to the color it started on, so there is no new state to catch up to — and a poll fired 400ms into a flash would publish a color the light is merely PASSING THROUGH and fire a Color Changed for it, then fire another when the light landed back where it began. The normal poll interval still re-reads state, so nothing goes stale. The suite proves both halves: that Set Color does schedule its follow-up read (so the comparison is not vacuous) and that Flash does not, and that Flash fires no Color Changed. What that ordinary poll ALSO does is exactly the thing the previous sentence calls spurious, and the Documentation tab now says so instead of leaving a dealer to find out: a default Breathe is 4000ms x 3 cycles = 12 seconds of animation against a 10-second default Poll Interval, so at least one ordinary poll always lands mid-effect and publishes an intermediate HUE/SAT/BRIGHTNESS with a Color Changed for it. That is a deliberate trade rather than an oversight — reachability (DEVICE_ONLINE, Went Online/Offline) is driven entirely by those poll replies and an effect can run for hours (300000ms x 255 cycles), so pausing the poll would either report a healthy light unreachable or freeze its reachability for the duration. The suite now pins that behavior too, so the doc's claim is a tested claim rather than an assurance.
- **String sweep: the runtime finally speaks the same language as the 0.4.0 docs.** 0.4.0 taught this driver that a bound LIFX Switch is not a bulb, and its own new relay strings said "device" — but thirteen older runtime Status and Debug strings still said "bulb", so a dealer commissioning a Switch was told to bind a bulb, watched it scan "for LIFX bulbs", and read "No bulb bound" from a driver that had just explained the device has no lamp. Those thirteen are now "device", counted exactly: SIX `No bulb bound` -> `No device bound` refusals (the shared Actuate chokepoint, the extended-zone and matrix chunk writers, the poll's own Device Status line, Unbind, and OnDeviceInit), TWO `Bind a bulb first` -> `Bind a device first` lines (Detect Clean (HEV) and Detect MultiZone, which now match the Detect Matrix and Detect Relays wording 0.4.0 already used), and five singletons — `Discovered N device(s)`, `Scanning the subnet for LIFX devices…`, `run Rescan to find devices`, `no device bound — nothing to poll`, and `no devices answered — check that the device is powered`. (The file now holds NINE `No device bound` strings in total: those six, the two 0.4.0 relay paths that already read "device", and the new effect writer.) "Bulb" is KEPT in exactly FOUR places, where it is family-true and would be less accurate as "device" — the single-zone zone refusal, both HEV refusals, and `Clean cycle start (bulb's configured default duration)` — because only bulbs have zones-or-not and only LIFX Clean bulbs have HEV LEDs. Dealer-facing wording in driver.json is NOT swept here and still says "bulb" in places the runtime no longer does, including the `Rescan (Discover Bulbs)` and `Ping Bulb (Echo)` command names: a Composer command name is a programming binding, so renaming one is a fielded break and its own decision, not a wording cleanup. One suite pin moved with them (`No bulb bound` -> `No device bound`, marked in the test with a one-line deliberate-change comment); no behavior changed and no other check moved.
- New Flash / Pulse / Breathe commands and eight new properties — Effect Hue, Effect Saturation, Effect Brightness, Effect Period (ms), Breathe Period (ms), Effect Cycles, Effect Duty %, Effect Channels. The effect color is its own triple rather than borrowing Set Color's, so a doorbell flash does not disturb what Set Color is pointed at; Kelvin is shared exactly as the gradient endpoints already share it. No new variables and no new events. Single-bulb, MultiZone, Matrix, HEV and Relay behavior are unchanged: the complete 0.4.0 suite passes against this body with exactly ONE deliberate exception, the string pin above, and the suite now stands at 846 checks. Four of those pins came out of an adversarial re-verification of this release and each one was confirmed to bite: the frame length ON THE WIRE (57 bytes for 103, 61 for 119, header size field included, because a payload-only assertion would pass a driver with a miscounted header), LAW 1 across all seven numeric effect properties rather than `cycles` alone, Effect Cycles clamping rather than reaching the codec's refusal, and the ordinary poll publishing a passing-through color mid-effect. Every sharp new claim was confirmed to fail the suite when deliberately broken — eleven mutations, all caught: a byte-swapped float32 packer, Flash switched to HALF_SINE, transient dropped, the duty formula un-inverted, the effect guard grandfathering an unconfirmed device, 103/119 removed from LIGHT_TYPES, a catch-up poll added, the float32 domain check removed, Breathe borrowing Flash's period, the 119 set_* flags reordered, and skew_ratio leaked onto a SINE waveform. (That last one initially slipped through and the test was strengthened to catch it: the default Effect Duty % of 50 maps to skew_ratio 0, which is also the mid-scale value a non-PULSE waveform sends, so the case now runs at 25% where a leak is visible.)
- Known limits: still one LIFX device per driver instance, still broadcast reachability, still polled feedback rather than push. Effects treat a strip or matrix as ONE zone — LIFX documents that plainly — so a whole Z, Beam or Ceiling flashes as a single color; per-zone motion is still MultiZone Move or Matrix Effect. SAW and TRIANGLE are documented waveforms no command sends. Effect Cycles is integers only, by the float32 reasoning above. No effect can be cancelled, read back, or confirmed on the wire. Effect Duty % is ignored by Flash and Breathe. One pre-existing driver-wide defect found while building this feature and FIXED here, at the property layer, rather than only in front of the new field: a non-finite value typed into any RANGED_INTEGER property used to survive both range clamps (LuaJIT's `tonumber` parses "nan" and turns "1e400" into inf; `math.floor(nan)` is still nan; every clamp comparison against nan is false), and on the existing integer paths LuaJIT then coerced it to zero bytes rather than erroring — a silent zero period or a silent zero timer interval, not a crash, which is worse. `intProp` now rejects nil, NaN and both infinities and falls back to the property's documented default, so EVERY numeric property in this driver is covered at once — not just the new `cycles`. The suite pins it across all seven effect properties. This build remains simulation-verified: no physical LIFX hardware has been on the bench.

## [0.4.0] - 2026-07-29
- Relay power for the LIFX Switch. Relay On and Relay Off pack SetRPower (type 817) as relay_index u8 + level u16 — the fixed 3 bytes — and Relay Toggle reads before it writes (below). The layout was verified against two independent official sources that agree byte for byte: lan.developer.lifx.com (querying-the-device-for-data#getrpower---packet-816, changing-a-device#setrpower---packet-817, information-messages#staterpower---packet-818) and LIFX's own machine-readable definition at github.com/LIFX/public-protocol, whose protocol.yml declares `relay.RelayGetPower` at 1 byte and `relay.RelaySetPower`/`relay.RelayStatePower` at 3. Only two levels are ever sent: LIFX documents that "Current models of the LIFX switch do not have dimming capability, so the two valid values are `0` for `off` and `65535` for `on`", so intermediate values — undefined for a relay — are not offered and there is no relay-level property. The registry does now list a "LIFX Dimmer Switch" (pid 226); the LAN protocol still documents no dimming semantics for SetRPower, so the driver does not invent any for it.
- Relay capability follows the 0.2.0/0.3.0 dual-path rule exactly. A StateVersion product id in the embedded relays subset of the official products registry (LIFX Switch 70/71/84/89/115, LIFX Switch US 116, LIFX Dimmer Switch 226 — every product with `features.relays: true` under vendor 1) OR any StateRPower reply flips RELAYS to yes and fires Relays Detected. Until something positively confirms, RELAYS stays unknown and every relay command is refused locally, by name, naming Detect Relays as the action that settles it. Detect Relays re-opens its own family only, and the probe asks about relay 0 — the one index the protocol actually names ("The relay on the switch starting from `0`").
- **A relay is not a light, and the driver now says so out loud.** LIFX documents the Switch as a "non light" that ignores Light messages and answers StateUnhandled (223) instead of a State, and every one of those seven relay products carries `color: false`, `matrix: false`, `multizone: false`, `hev: false` and no `temperature_range` at all in the registry — no light features whatsoever, checked product by product rather than inferred from "it has relays". So a confirmed switch refuses Power On/Off/Toggle, Set Color and Set White by name and points at the relay commands instead, rather than writing frames the device is documented to throw away. IS_LIGHT is its own variable — unknown, yes (it answered a State; only a light does) or no — and it is never decided by the relay verdict.
- That honesty also fixed a reachability bug the feature would otherwise have shipped with. The driver polls Light Get; a Switch answers StateUnhandled, which 0.3.0 ignored entirely — so a perfectly healthy switch answering every single poll would have sat at DEVICE_ONLINE false forever. A refusal IS an answer: StateUnhandled now counts as proof of life, and a confirmed non-light is polled on its relay (or, while its relays are still unconfirmed, with EchoRequest — the device message every LIFX device answers) instead of being asked for light state that will never come.
- StateUnhandled is read for WHICH type came back, not treated as one signal, because the two readings point in opposite directions. An unhandled *Light* message proves the device is not a light. An unhandled *relay* message proves it has no relays. Treating any 223 as "not a light" would have branded every ordinary LIFX bulb a switch the moment it declined this driver's relay probe — so the driver reads the u16 and concludes only what that specific type supports, and nothing at all from any other type.
- The non-light verdict is one-way, and only from an open question. A device that has ANSWERED a State(107) has positively proven what it is, so a later StateUnhandled for a Light message cannot demote it — the same monotonicity the relay half of the split already had. This matters more than it looks: the demotion also switches the poll off Light Get, so without the guard it sealed itself in. One forged frame on this unauthenticated LAN (or one firmware hiccup) would have left a healthy bulb answering the EchoRequest keepalive, sitting at DEVICE_ONLINE true, and refusing every Power / Set Color / Set White until someone re-bound the driver — the driver would never again have asked the one question whose answer clears it. Caught in adversarial review before ship; the repro is in the suite.
- Relay Toggle is honest or it does not run. LIFX has no toggle verb, and the last position this driver saw may be seconds old or may be about a different relay — so Relay Toggle sends GetRPower and writes the inverse only when THAT read is answered, matched on the (source, sequence, target) triple LIFX documents for correlating a reply to its request. A reply about a different relay, or a late answer to an earlier read, releases nothing. A read that goes unanswered inside the 2s window is a refusal that says the relay was left untouched — never a write from stale state, because a blind toggle on a relay feeding a real load is exactly the command that must not fire on a guess.
- Relay state is per-relay, because it has to be. RELAY_INDEX / RELAY_LEVEL / RELAY_POWER describe the relay that just reported, and Relay Changed compares a relay against ITSELF using a table keyed by the protocol's own u8 index — a single scalar would have fired a phantom "changed" the moment someone pointed Relay Index at a different relay that happens to sit the other way. Adoption is silent, like every other state in this driver: the first report from a relay is not a change. RELAY_INDEX starts empty rather than "0", because 0 is a real relay index and publishing it before anything has reported would claim a reading the driver does not have.
- Deliberately NOT claimed: the relay count. LIFX publishes it nowhere official — not in the LAN protocol, not on the LIFX Switch page, and not in the products registry, which carries no relay-count field at all. So Relay Index exposes the full 0-255 span the protocol's own u8 relay_index allows instead of hard-coding a count from a third-party library, and the variables report only what a real StateRPower said. For the same reason the state variables are indexed rather than RELAY_1..4: a fixed set of four would have been an invented count wearing the costume of a fact.
- Also not claimed: what the load is doing. A relay closes a circuit feeding a DUMB fixture. The driver knows the relay's POSITION, which is all the switch reports, and cannot know whether anything is lit — a burnt-out lamp, a pulled fixture and a lamp switched off at its own body all read identically as a closed relay. Documented plainly rather than papered over. The switch's physical BUTTONS are not read either: LIFX documents button messages, but this build implements the three relay messages only, so a press surfaces only as the Relay Changed that follows it when that button drives a relay.
- Flood posture inherited from 0.3.0: exactly one relay message per poll and one per command, never a sweep across indices the driver has no count for. Every relay control path re-checks the license at wire-write time like the single-bulb, zone, matrix and clean paths before it, and an unlicensed toggle does not even read.
- New variables RELAYS, IS_LIGHT, RELAY_INDEX, RELAY_LEVEL and RELAY_POWER; new Relays Detected and Relay Changed events; new Relay On / Relay Off / Relay Toggle commands; new Detect Relays action; and the Relay Index property. Single-bulb, MultiZone, Matrix and HEV behavior are unchanged — the complete 0.3.0 suite (537 checks) passes unmodified against this body, and the four sharpest new claims (per-relay change tracking, toggle sequence-matching, toggle refusal on an unanswered read, and the StateUnhandled split) were each confirmed to fail the suite when deliberately broken.
- Known limits: still one LIFX device per driver instance, still broadcast reachability, still polled feedback rather than push. No dimming, no relay count, no button messages, no load feedback. Relay writes are sent with the same res/ack posture as every other Set here — LIFX's own guidance is that a State reply to a Set is "usually not useful" — so a write is confirmed by the read-back that follows it, not on the wire. This build remains simulation-verified: no physical LIFX Switch has been on the bench.

## [0.3.0] - 2026-07-27
- Matrix/Tile for LIFX Tile, Candle, Ceiling, Path, Spot, Tube, Luna and Mirror. Set Matrix Color paints every zone of every tile in the chain one HSBK color over Set64 (type 715): a 522-byte payload — tile_index u8, length u8, fb_index u8, x u8, y u8, width u8, duration u32, then a fixed 64-entry HSBK array. Set64 carries no colors_count, so a uniform paint fills all 64 slots and lets firmware consume the ones that exist; one message goes out per tile (length = 1), and on devices wider than 64 zones one per band of whole rows — an 8x8 Tile is a single message, a 13x26 Ceiling is seven, each with y advanced by floor(64/width) rows.
- Matrix Effect On/Off runs a firmware effect over SetTileEffect (type 719), a 188-byte payload packed byte-exactly: two reserved, instanceid u32, type u8, speed u32, duration u64, two 4-byte reserved fields, then the 32-byte parameter block (skyType u8, 3 reserved, cloudSaturationMin u8, 3 reserved, 24 reserved), palette_count u8, and a fixed 16-entry palette. Only the officially documented effect types are ever sent — MORPH (2), FLAME (3), SKY (5) and OFF (0); the registry's RESERVED1 (1) and RESERVED2 (4) are unreachable by design. MORPH gets a two-entry palette from the start and end color properties; FLAME's colors are firmware-fixed and SKY has its own palette semantics, so both go out with palette_count 0 rather than a palette this driver invented.
- Matrix capability and matrix GEOMETRY are tracked as two separate facts, because they are. A StateVersion product id in the embedded matrix subset of the official products registry (Tile 55, Candle C 57/68/137/138/185/186/215/216, Spot 171/172/221, Path 173/174/222/229, Ceiling 176/177/201/202/265/266, Tube 217/218, Luna 219/220, Mirror 267/268) flips MATRIX to yes and fires Matrix Detected — but it says nothing about how big the matrix is, so TILE_COUNT/TILE_WIDTH/TILE_HEIGHT stay 0 and Set Matrix Color is refused until a StateDeviceChain (702) reply reports them. Set64 addresses zones by row using the device's own width; painting on a guessed width would smear the result, so it does not paint. Matrix Effect needs no geometry and unlocks immediately.
- StateDeviceChain is parsed at its documented 882 bytes — start_index u8, sixteen 55-byte Tile records, tile_devices_count u8 — reading only the chain count and the first tile's width/height at tile-relative +16/+17. The accelerometer triple and the two user-position floats are deliberately not decoded. A payload that is not the documented length still counts as confirmation (only a matrix device sends one) but yields no geometry rather than a guess. Neither does a count above the sixteen Tile records the payload can physically hold: 255 tiles is a garbled reply, not a chain, and geometry the driver would not trust is geometry it does not publish. Set Matrix Color is bounded on top of that — it counts the messages a reported grid would need BEFORE building any, and refuses by name past a 256-message ceiling. The biggest chain the wire format allows (16 tiles) of the widest real matrix (Ceiling 13x26, 7 bands each) is 112 messages, so no real hardware can reach it; a garbled 702 that would otherwise have turned one button press into tens of thousands of datagrams now gets a status line instead, because LIFX documents that an excessive message rate causes unexpected device behavior.
- SetUserPosition (703) is deliberately NOT implemented. Its float tile coordinates have no source the driver can read, the message returns nothing even with res_required set, and a wrong value would silently corrupt the chain layout the LIFX app itself depends on — installer geometry the driver can neither derive nor verify is not something it should write. Reading the matrix back (Get64/State64) and reading a running effect back (StateTileEffect) are also out: nothing claims which effect is active, because nothing asks.
- HEV clean cycles for LIFX Clean. Start Clean Cycle and Stop Clean Cycle pack SetHevCycle (type 143) as enable BoolInt + duration_s u32 — the fixed 5 bytes. Clean Cycle Duration (s) defaults to 0 on purpose: the protocol defines 0 as "use the duration stored on the bulb", so the default defers to the device instead of overriding it. Apply Clean Defaults writes SetHevCycleConfiguration (146, the same 5-byte shape, different meaning) and then reads it back, so the read-only Clean Configuration property always shows what the BULB reports rather than what was typed above it.
- Cycle state is honest in both directions. StateHevCycle (144) drives CLEAN_CYCLE_ACTIVE and a live CLEAN_REMAINING_S countdown on every poll of a confirmed Clean bulb; Clean Cycle Started fires the first time a running cycle is observed (the same rule reachability already uses — a cycle we can now see IS a transition), and Clean Cycle Finished only ever fires for a cycle the driver actually saw running. When one ends the driver asks GetLastHevCycleResult (148) and publishes the bulb's own word in CLEAN_LAST_RESULT: SUCCESS, BUSY, INTERRUPTED_BY_RESET, INTERRUPTED_BY_HOMEKIT, INTERRUPTED_BY_LAN, INTERRUPTED_BY_CLOUD or NONE. An interrupted cycle names which controller interrupted it and is never flattened into "failed". last_power is reported by the protocol as relevant only while a cycle runs, so it goes to Debug rather than to a variable that would be meaningless between cycles, and the end-of-cycle indication is exposed as the boolean the protocol actually defines — there is no brightness or power level for it to claim.
- Both new families follow the 0.2.0 rule exactly: unknown until the device itself confirms, every refusal local and by name with the reason and the Detect action that would settle it, and nothing speculative on the wire. Detect Matrix and Detect Clean (HEV) mirror Detect MultiZone and re-open their own family only. Every new control path re-checks the license at wire-write time, like the single-bulb and zone commands before them.
- Probing got quieter, not louder. Each capability question is now asked only while its own family is open — a bulb that has identified itself generates no probe traffic at all, where 0.2.0 kept asking GetVersion and GetExtendedColorZones. Matrix is the one family that stays open after confirmation, until the chain geometry arrives.
- New variables MATRIX, TILE_COUNT, TILE_WIDTH, TILE_HEIGHT, HEV, CLEAN_CYCLE_ACTIVE, CLEAN_REMAINING_S and CLEAN_LAST_RESULT; new Matrix Detected, HEV Detected, Clean Cycle Started and Clean Cycle Finished events; new Set Matrix Color, Matrix Effect On/Off and Start/Stop Clean Cycle commands; new Detect Matrix, Detect Clean (HEV) and Apply Clean Defaults actions; and the matrix effect, sky, and clean-cycle properties. Single-bulb and MultiZone behavior, and the 0.1.0 reachability-honesty and rebind-reset fixes, are unchanged — every one of the 347 checks that covered them passes untouched.
- Known limits: still one LIFX device per driver instance, still broadcast reachability, still polled feedback rather than push. Matrix paints ONE color across the whole chain — per-zone matrix patterns, animations, Get64/State64 readback, StateTileEffect readback, and SetUserPosition are not written. SKY is documented by LIFX as LIFX Ceiling on firmware 4.4+ only and the driver cannot read a firmware version, so an unsupported device silently ignores it and no reply exists to say so. Matrix effects and Set64 return nothing even with res_required set, so no matrix write is ever confirmed on the wire — the follow-up state poll is what re-reads the light. The LIFX Switch relay (SetRPower, 817) and the legacy SetColorZones (501) path remain out of scope, and this build is still simulation-verified, not bench-tested on matrix or Clean hardware.

## [0.2.0] - 2026-07-26
- MultiZone for LIFX Z / Beam strips over SetExtendedColorZones (type 510). Set Zone Color paints a Zone Start..Zone End range one HSBK color; Set Zone Gradient ramps start->end color across the strip. Both pack the fixed 664-byte payload (duration u32, apply u8, zone_index u16, colors_count u8, 82-entry HSBK array) little-endian; strips longer than 82 zones auto-chunk with apply=NO_APPLY on every message but the last and apply=APPLY on the final one, so the whole strip lands in one atomic update.
- Honest capability detection: on bind and while still unknown, the driver asks GetVersion (32) and GetExtendedColorZones (511). A StateVersion product id in the embedded multizone subset (LIFX Z 31/32, Beam 38, per the official products registry) or any StateExtendedColorZones (512) reply flips MULTIZONE to yes, publishes the real ZONES_COUNT, and fires MultiZone Detected. An unlisted product id is treated as single-zone. Until something positively confirms, capability stays unknown and zone commands are refused.
- Single-zone bulbs refuse every zone/effect command by name — nothing reaches the wire — and the refusal states the reason (single-zone, or capability not yet confirmed; run Detect MultiZone).
- MultiZone Move On/Off runs the LIFX Move effect via SetMultiZoneEffect (508) at the configured Move Speed. Every multizone control path re-checks the license at wire-write time, exactly like the single-bulb commands.
- New variables MULTIZONE (unknown/yes/no) and ZONES_COUNT, new MultiZone Detected event, and new Set Zone Color / Set Zone Gradient / MultiZone Move On/Off commands, Detect MultiZone action, and the zone/gradient/move-speed properties. Single-bulb behavior and the 0.1.0 reachability-honesty and rebind-reset fixes are unchanged.

## [0.1.0] - 2026-07-26
- Initial release candidate: single-bulb control over the LIFX LAN protocol (UDP binary, port 56700, lan.developer.lifx.com). No cloud, no LIFX account, no token on the wire.
- Broadcast discovery: Rescan sends GetService (type 2, tagged) to the subnet broadcast address and collects StateService (type 3) replies, keyed and de-duplicated by the responder's serial. Paste a serial into Discovered Device and run Bind Selected Device; the bound target is persisted across reboots and driver upgrades.
- Control: Power On/Off/Toggle via SetLightPower (type 117) with a transition duration; Set Color via SetColor (type 102, HSBK) from Hue/Saturation/Brightness; Set White via SetColor with saturation 0 from Kelvin/Brightness. Every control path re-checks the license at wire-write time.
- Feedback: Light Get (type 101, res_required) is polled; the State (type 107) reply is parsed into POWER, HUE, SAT, BRIGHTNESS, KELVIN and DEVICE_ONLINE, firing Turned On/Off, Color Changed and Went Online/Offline. Replies are correlated by source + sequence; unknown→known baseline adoption fires no state events.
- Keepalive: EchoRequest (type 58) proves reachability between polls; a missing reply within the poll window flips the bulb Offline.
- Wire hygiene: the RX path tolerates arbitrary datagram boundaries and junk (bounded frame walk, no resync loops), drops sends while the socket is offline, and never logs raw frame bytes — Debug prints the frame type + sequence only. The LIFX LAN protocol carries no secret, so nothing secret can leak; the IntegrateIT license key is never printed.
- Fix (reachability honesty): a lost LAN socket now drops reachability (`ApplyReach(false)`) instead of stranding `DEVICE_ONLINE` asserted true. Because polling stops when the socket goes offline, the missed-poll path could never fire again to correct the variable — automation told to gate on `DEVICE_ONLINE` would have seen a frozen "online" for a bulb the driver could no longer reach.
- Fix (rebind reachability): binding a new serial now resets reachability to unknown and publishes `DEVICE_ONLINE` false, instead of inheriting the previously-bound bulb's last reply. A freshly-bound (possibly dead) target no longer reports online until it actually answers.
- Known limits: single bulb per instance; broadcast reachability required (same subnet); no multi-zone/tile/HEV/relay extensions; polled feedback, not push; serial-only discovery labels.
