1 Start here

IntegrateIT LIFX puts a single LIFX Wi-Fi device into a Control4 project over the vendor's published LAN protocol (lan.developer.lifx.com) — packed little-endian frames over UDP on port 56700. There is no cloud service, no LIFX account, and no token or password anywhere on the wire: the LAN protocol is unauthenticated by design and runs entirely on your local network. You Rescan to discover devices, Bind one by its serial, then drive power, color, and white temperature with polled state feedback — or, on a LIFX Switch, the relays feeding the dumb loads wired to it.

control and discovery are sent to the subnet broadcast address and targeted by the bulb's serial — the controller and the bulb must be on the same subnet/VLAN with UDP broadcast permitted. There is no unicast IP to type in; if broadcast is filtered or the bulb is on another subnet, it will neither be found nor controlled.
automated QA covers boot, the discover → bind lifecycle, the LIFX frame encode/decode (36-byte header, HSBK), byte-exact packing of every zone, matrix, clean-cycle, relay, and waveform message (including the cycles float32 against known IEEE-754 constants), capability detection and every refusal, reply correlation and de-duplication, reachability, and the license gate — all against the Control4 API simulator. A qualified dealer must still run Rescan against real devices and confirm the printed serials match the physical units before relying on the binding, and must confirm matrix, clean, and relay behavior on the actual hardware. This build is simulation-verified, not bench-tested.

What you get

  • Rescan (Discover Bulbs) — broadcast GetService and list every LIFX device that answers, by serial (a LIFX Switch answers like any other).
  • Bind Selected Device — persist one device as this instance's target (survives reboots and upgrades).
  • Power On / Off / Toggle with a configurable transition (fade) duration.
  • Set Color (Hue / Saturation / Brightness → HSBK) and Set White (Kelvin + Brightness).
  • MultiZone for confirmed LIFX Z / Beam strips: Set Zone Color over a zone range, Set Zone Gradient end-to-end, and MultiZone Move On/Off — single-zone bulbs refuse these by name.
  • Matrix for confirmed Tile / Candle / Ceiling / Path / Spot / Tube / Luna / Mirror: Set Matrix Color across the whole chain and Matrix Effect On/Off (MORPH, FLAME, SKY).
  • Clean cycles for a confirmed LIFX Clean: Start / Stop Clean Cycle, the bulb's own stored defaults, and a live remaining-seconds countdown.
  • Relays for a confirmed LIFX Switch: Relay On / Relay Off / Relay Toggle on the relay you select, with the switch's own reported position published back and a Relay Changed event when someone presses the physical button.
  • Light effects on any confirmed light: Flash, Pulse and Breathe over the firmware waveform engine, in your own effect color, always returning the light to where it was — and optionally on brightness alone, so a flash does not change the color.
  • Polled POWER, HUE, SAT, BRIGHTNESS, KELVIN, DEVICE_ONLINE, plus MULTIZONE, ZONES_COUNT, MATRIX, TILE_COUNT/TILE_WIDTH/TILE_HEIGHT, HEV, CLEAN_CYCLE_ACTIVE, CLEAN_REMAINING_S, CLEAN_LAST_RESULT, RELAYS, IS_LIGHT, RELAY_INDEX, RELAY_LEVEL, and RELAY_POWER variables.
  • Turned On/Off, Color Changed, Went Online/Offline, Device Bound, Discovery Complete, MultiZone/Matrix/HEV/Relays Detected, Clean Cycle Started/Finished, and Relay Changed events.

2 The feedback contract

Feedback is polled, not pushed. The driver sends Light Get (type 101) on the poll interval and parses the bulb's State (type 107) reply into the variables. A change you make from the LIFX app appears on the next poll (default 10s), not instantly — this driver does not subscribe to unsolicited/streamed state, and anything claiming instant third-party feedback over the LAN protocol would be faking it.

State is honest about what it knows. At boot the last-known power and color are unknown; the first poll adopts the bulb's current state silently — it fires no Turned On/Off or Color Changed, because there was no prior value to change from. Only a genuine change between polls fires those events. Reachability is the one first-observation exception: when the bound bulb first answers, that is a real transition and Went Online fires; if no reply arrives within the poll window, Went Offline fires and DEVICE_ONLINE goes false.

Replies are matched to our requests by the protocol's source (a fixed client id echoed back) and sequence, and de-duplicated by type:sequence:serial, so a duplicate or late datagram on a broadcast LAN can never double-fire an event or double-count a discovered bulb.

3 Wire and commission

  1. Power the LIFX device and confirm it is joined to the same Wi-Fi/LAN as the controller (same subnet, broadcast permitted).
  2. Add this driver to the device's room. It opens a UDP broadcast socket on port 56700 at startup.
  3. Run the Rescan (Discover Bulbs) action. Watch the Lua output window: each device prints as its 12-hex serial (udp 56700) — a LIFX Switch answers discovery like any other LIFX device.
  4. Copy one serial into the Discovered Device property (for example d073d5112233).
  5. Run Bind Selected Device. Bound Device now shows that serial and IS_BOUND flips true; polling begins.
  6. Run Power On (or Set Color) and watch the bulb react, then confirm POWER/DEVICE_ONLINE update on the next poll.
  7. Reboot the controller and confirm Bound Device still names the same serial — the binding is persisted, not re-discovered.

4 MultiZone strips (Z / Beam)

A LIFX Z or Beam is a strip of individually addressable zones. This driver drives those zones over the vendor's extended-zone message, but only after it has positively confirmed the bound bulb is multizone — it never assumes.

Capability is detected honestly, from the device itself:

  • On bind and on each poll while still unknown, the driver asks GetVersion (32) and GetExtendedColorZones (511). A StateVersion (33) whose product id is a known multizone model (LIFX Z 31/32, Beam 38 — the embedded subset of LIFX's official products registry), or a StateExtendedColorZones (512) reply, flips MULTIZONE to yes, publishes the real ZONES_COUNT, and fires MultiZone Detected.
  • A product id we recognize as a plain bulb sets MULTIZONE to no.
  • If nothing has answered yet, MULTIZONE stays unknown and zone commands are refused — the Status line says capability isn't confirmed and to run Detect MultiZone. Run it manually against a Z/Beam if you don't want to wait for the poll.

Once confirmed:

  • Set Zone Color paints zones Zone Start .. Zone End (0-based, inclusive) one HSBK color from Hue/Saturation/Brightness/Kelvin.
  • Set Zone Gradient ramps from the start color (Hue/Saturation/Brightness) to the end color (Hue End / Saturation End / Brightness End), Kelvin shared, spread across the detected zone count — or the Zones (strip length) you configured until the bulb reports its own.
  • MultiZone Move On/Off starts/stops the LIFX Move effect at Move Speed (ms).
a single strip can carry more than 82 zones, but one extended-zone message holds at most 82 HSBK colors. Longer strips are split automatically: every message but the last is sent with apply = NO_APPLY and the final one with apply = APPLY, so the whole strip lands in one atomic update rather than visibly repainting in bands.
extended zones need recent strip firmware. An older LIFX Z may need a firmware update (in the LIFX app) before SetExtendedColorZones takes effect; the legacy SetColorZones (501) path is intentionally not written. A single-zone bulb refuses every zone command by name — nothing is sent to the wire.

5 Matrix devices (Tile, Candle, Ceiling, …)

A LIFX Tile, Candle, Ceiling, Path, Spot, Tube, Luna or Mirror is a grid of zones, and several can be chained. The same unknown-until-confirmed rule applies: GetVersion (32) matched against the matrix subset of LIFX's official products registry, or a StateDeviceChain (702) reply, flips MATRIX to yes and fires Matrix Detected. Until then every matrix command is refused and the Status line points at Detect Matrix.

Confirmation and geometry are two separate facts, and the driver keeps them separate:

  • A product-id match proves the device *has* a matrix. It says nothing about its size, so TILE_COUNT, TILE_WIDTH and TILE_HEIGHT stay 0 — meaning "the device has not told us".
  • Only StateDeviceChain reports the real chain length and each tile's zone width and height. The driver keeps asking for it until it arrives.
  • Set Matrix Color paints every zone of every tile one HSBK color, and is refused while the geometry is 0 — Set64 addresses zones by row using the device's own width, so painting on a guessed width would smear the result. Matrix Effect On/Off carries no geometry and is allowed as soon as MATRIX reads yes.

One Set64 message reaches at most 64 zones on one tile, so the driver sends one message per tile and, on devices wider than 64 zones, one per band of whole rows: an 8×8 Tile is a single message, a 13×26 Ceiling is seven.

Matrix Effect On starts a firmware effect chosen by the Matrix Effect property. MORPH blends the Hue/Saturation/Brightness color with the Hue End/Saturation End/Brightness End color (a two-entry palette). FLAME's colors are fixed in firmware, so no palette is sent. SKY uses Sky Type and Cloud Saturation Min.

LIFX documents the SKY effect as LIFX Ceiling on firmware 4.4 or newer only. This driver cannot read a firmware version, so it sends what you selected and a device that does not support SKY simply ignores it — there is no reply to tell us otherwise, and anything claiming to confirm the effect took hold would be faking it.

6 Clean cycles (HEV)

A LIFX Clean bulb carries HEV LEDs on top of the normal white/color LEDs. HEV is unknown until the product id matches the registry's HEV subset (LIFX Clean A19 1100lm / 1200lm) or the bulb answers an HEV message — then HEV Detected fires and the cycle commands unlock. A bulb without HEV refuses them by name.

  • Start Clean Cycle runs the HEV LEDs for Clean Cycle Duration (s). Leaving that at 0 is not "unset": the protocol defines 0 as *use the duration stored on the bulb*, which is why it is the default.
  • Stop Clean Cycle ends a running cycle early.
  • Apply Clean Defaults writes Clean Default Duration (s) and Clean End Indication to the bulb, then reads them back — the read-only Clean Configuration property always shows what the *bulb* reports, never what was typed above it.
  • While a cycle runs, each poll refreshes CLEAN_REMAINING_S. Clean Cycle Started fires the first time a running cycle is observed; Clean Cycle Finished only ever fires for a cycle the driver actually saw running.
  • When a cycle ends, the driver asks the bulb *why* and publishes its own word in CLEAN_LAST_RESULT: SUCCESS, BUSY, INTERRUPTED_BY_RESET, INTERRUPTED_BY_HOMEKIT, INTERRUPTED_BY_LAN, INTERRUPTED_BY_CLOUD, or NONE. An interrupted cycle says which controller interrupted it and is never flattened into "failed".
a clean cycle is the bulb running its HEV LEDs. Follow LIFX's own guidance for occupied rooms; this driver schedules the cycle, it does not supervise the room. The end-of-cycle indication is a boolean in the protocol — a short flash, with no brightness or power level to set, so none is offered.

7 Relays (LIFX Switch)

A LIFX Switch is not a light. LIFX says so itself: it is a wall device whose electrical relays feed *dumb* fixtures — a plain lamp, a fan, whatever the electrician wired to it — and LIFX documents it as a "non light" that ignores Light messages entirely. This driver treats it as exactly that.

Capability is confirmed the same way as every other family: a GetVersion (32) whose product id is in the relays subset of LIFX's official products registry (LIFX Switch 70/71/84/89/115, LIFX Switch US 116, LIFX Dimmer Switch 226), or any StateRPower (818) reply, flips RELAYS to yes and fires Relays Detected. Until then relay commands are refused and the Status line points at Detect Relays.

Once confirmed:

  • Relay On / Relay Off close and open the relay at Relay Index (SetRPower, level 65535 / 0).
  • Relay Toggle reads the relay first and writes the inverse of what the switch actually reports — see the warning below.
  • Each poll re-reads the selected relay, so a press of the switch's own button surfaces as Relay Changed. RELAY_INDEX, RELAY_LEVEL and RELAY_POWER always describe the relay that most recently reported.
a relay position is not proof that anything is lit. The switch tells this driver whether the relay is closed or open, and nothing else. A burnt-out lamp, a fixture that has been pulled, and a lamp switched off at its own body all read identically as a closed relay. Program on the relay's position, not on an assumption about the room.
there is no dimming. LIFX documents that current switch models cannot dim and that 0 and 65535 are the only valid relay levels, so those are the only two values this driver ever sends and no relay-level property is offered. The registry does list a "LIFX Dimmer Switch" (pid 226) — the LAN protocol still documents no dimming semantics for SetRPower, so the driver does not invent any for it.
no relay count is claimed. LIFX does not publish how many relays a Switch has — not in the LAN protocol, not on its own LIFX Switch page, not in the products registry, which has no relay-count field. So Relay Index offers the full 0-255 range the protocol's own u8 relay_index allows rather than a number this driver made up. Point it at a relay that does not exist and the switch simply will not answer; the variables only ever report a real reply.
because the Switch is a non-light, Power On/Off/Toggle, Set Color and Set White are refused by name on it once it has identified itself. That is not a limitation of this driver — the device is documented to discard those messages and answer StateUnhandled (223) instead. Its poll reads the relay rather than asking for light state that will never arrive, and those refusals still count as proof of life, so a switch answering every poll never sits at DEVICE_ONLINE false.

The switch's physical buttons are not read. LIFX documents button messages; this driver implements the three relay messages only. A button wired to a relay shows up as the Relay Changed that follows the press — a button configured to drive a cloud scene produces nothing here at all.

8 Light effects: flash, pulse, breathe

The LAN protocol carries a waveform engine in the light's own firmware: hand it a target color, a period, a cycle count and a shape, and the light animates the transition itself — no timers on the controller, no burst of frames. Three commands drive it, and all three put the light back exactly where they found it.

The effect color is its own Effect Hue / Effect Saturation / Effect Brightness triple, with Kelvin shared from Set White exactly as the gradient endpoints share it. That separation is deliberate: a doorbell flash should not have to borrow — or disturb — whatever Set Color is pointed at.

  • Flash — swings the light toward the effect color and back, Effect Cycles times, each cycle lasting Effect Period (ms). 200–800 ms reads as a flash.
  • Pulse — snaps straight to the effect color and back, spending Effect Duty % of each cycle on the effect color. Sharper and more urgent than a Flash.
  • Breathe — the same shape as Flash run slowly, on its own Breathe Period (ms). 2000–6000 ms reads as breathing.

Why Flash and Breathe send the same waveform. Both send SINE. Of the five documented waveforms, two return to the current color *within every cycle* — and LIFX's own transient rule names exactly those two: SINE ("the color will cycle smoothly from current color to color and then end back at current color") and TRIANGLE ("light interpolates linearly from current color to color, then back to current color"). Flash and Breathe take SINE because it is the smooth one of the pair, which is what reads as a flash or a breath; TRIANGLE's linear ramp is just as documented and simply has no command here. What rules HALF_SINE out is firmer: it is documented as one-directional ("light interpolates smoothly from current color to color"), so what it does *between* cycles is documented nowhere — a Flash built on it would have undefined behavior the moment you set Effect Cycles above 1. The protocol has one sine shape and one period field, so this driver offers two honest tempo presets instead of inventing a second mechanism and dressing it up as a different one.

Why transient is always set. LIFX's rule is exact: "if transient == true or the waveform is SINE or TRIANGLE then the device will return to the original color after the effect. Otherwise the device will not revert to the original color after the effect." So on Flash and Breathe (both SINE) the flag is redundant — the waveform returns on its own. On Pulse it is load-bearing: PULSE is neither SINE nor TRIANGLE, so without transient the light would be *left* sitting on the effect color when the cycles ran out. One byte is the whole difference, and it is set on all three so every effect in this driver behaves the same way.

Effect Channels decides how much of the color an effect is allowed to move:

Effect ChannelsPacketWhat moves
Full color (HSBK)SetWaveform (103)Hue, saturation, brightness and Kelvin — 103 always applies all four.
Brightness onlySetWaveformOptional (119)Brightness alone. Usually what you want: flash the porch light without turning it a different color.
Color only (keep brightness)SetWaveformOptional (119)Hue, saturation and Kelvin; the light keeps the level it was already at.

LIFX documents 119 as behaving "like SetWaveform (103) but allows you to keep certain parts of the original HSBK values during the transition", via four trailing set_hue / set_saturation / set_brightness / set_kelvin flags. That is the entire difference between the two packets, and it is the only reason this driver sends 119 at all.

effects are fire-and-forget, and nothing here pretends otherwise. LIFX documents both 103 and 119 as returning a LightState (107) — but that is the ordinary response-to-a-Set reporting the light's state *at that instant*, not a report that the effect finished. The protocol defines no GetWaveform, no StateWaveform, and no message that cancels a running effect. So no variable and no event claims an effect is running, finished, or was even accepted; the only way to keep an effect short is to keep Effect Cycles × period short. An effect also schedules no catch-up poll — every effect here returns the light to the color it started on, so a poll fired mid-flight would publish a color the light is merely passing through and fire a spurious Color Changed for it. What the driver does not do is suppress the *ordinary* Poll Interval (s) read, and on a long effect you should expect that read to land mid-flight: a default Breathe is Breathe Period (ms) 4000 × Effect Cycles 3 = 12 seconds of animation against the default 10-second poll, so at least one ordinary poll always lands inside it. When it does, HUE / SAT / BRIGHTNESS publish the intermediate color the light is passing through and one Color Changed fires for it, then another when the light lands back where it began. That is a deliberate trade, not an oversight: reachability (DEVICE_ONLINE, Went Online / Went Offline) is driven entirely by those poll replies, and an effect can legitimately run for hours (Effect Period (ms) 300000 × 255 cycles), so pausing the poll for the duration would either report a healthy light unreachable or freeze its reachability for as long as the effect ran. If Composer programming branches on Color Changed or reads BRIGHTNESS, keep Effect Cycles × period shorter than Poll Interval (s) — or gate that programming so a transient effect color cannot trigger it. Note that Brightness only does not avoid this: brightness is part of the published color, so a brightness-only effect fires Color Changed the same way.
Effect Cycles is whole numbers only (1–255). The protocol carries that field as an IEEE-754 float32, and this driver packs bytes with arithmetic in portable Lua 5.1 — no bit library. Rather than ship a general float codec that would quietly round or mangle what it cannot represent, it packs the subset it can *prove*: an integer in the exactly-representable range, byte-verified against the known constants (1.0 = 0x3F800000, 2.0 = 0x40000000, 3.0 = 0x40400000, 10.0 = 0x41200000). The property itself is clamped to 1–255, and a non-numeric or non-finite entry falls back to the default of 3 rather than reaching the wire, so nothing you can type in Composer can reach the codec's edge. The codec still refuses anything outside its exact-integer domain by name instead of sending an approximation — that refusal is the contract that protects any future caller which does not arrive through a clamped property.
on a strip or a matrix, an effect treats the whole device as one zone. LIFX says so plainly: "For devices that support multiple zones, these effects will treat all zones as one zone and the entire device will perform the waveform effect as a single color." A whole Z, Beam or Ceiling flashes as one color — per-zone effects are not something the waveform messages offer.
SAW and TRIANGLE are documented waveforms that no command here sends, and Effect Duty % is ignored by Flash and Breathe because LIFX gives skew_ratio a meaning only for PULSE. The field is still packed at its documented offset on every effect, at the mid-scale value, rather than carrying a number this driver invented a meaning for.

9 Protocol on the wire

Every frame is a 36-byte header + payload, all little-endian. The header carries a size, a 16-bit protocol/flags field (protocol 1024 | addressable | tagged), the 32-bit source, the 6-byte target serial, res/ack flag bits, an 8-bit sequence, and a 16-bit message type. Color is HSBK — four u16 values (hue, saturation, brightness, Kelvin).

  • Discovery — GetService (2, tagged, target = all) → each bulb answers StateService (3) naming its UDP service and port.
  • Power — SetLightPower (117): level u16 (0 or 65535) + duration u32.
  • Color / White — SetColor (102): reserved byte + HSBK + duration u32. White is HSBK with saturation 0.
  • Effects — SetWaveform (103), 21 bytes: reserved u8, transient BoolInt, HSBK, period u32 (ms per cycle), cycles float32, skew_ratio i16, waveform u8. SetWaveformOptional (119) is those same 21 bytes plus four trailing BoolInt flags — set_hue, set_saturation, set_brightness, set_kelvin — for 25. Both layouts were verified against LIFX's prose docs *and* its machine-readable protocol.yml, which declare exactly 21 and 25 bytes. Waveform enum: SAW 0, SINE 1, HALF_SINE 2, TRIANGLE 3, PULSE 4.
  • Feedback — Light Get (101, res_required) → State (107): HSBK + power.
  • Keepalive — EchoRequest (58) → EchoResponse (59).
  • Capability — GetVersion (32) → StateVersion (33): product id; GetExtendedColorZones (511) → StateExtendedColorZones (512): zones_count; GetDeviceChain (701) → StateDeviceChain (702): 882 bytes — start_index, sixteen 55-byte Tile records, tile count; GetHevCycle (142) → StateHevCycle (144). Each question is asked only while its own family is unresolved, so an identified bulb stops generating probe traffic.
  • MultiZone — SetExtendedColorZones (510): duration u32, apply u8, zone_index u16, colors_count u8, then a fixed 82-entry HSBK array. SetMultiZoneEffect (508) runs the Move effect.
  • Matrix — Set64 (715), 522 bytes: tile_index u8, length u8, fb_index u8, x u8, y u8, width u8, duration u32, then a fixed 64-entry HSBK array (there is no colors_count — the device maps the array by its own width, so a uniform paint fills all 64 slots). SetTileEffect (719), 188 bytes: two reserved, instanceid u32, type u8, speed u32, duration u64, a 32-byte parameter block carrying skyType and cloudSaturationMin, palette_count u8, then a fixed 16-entry palette.
  • HEV — SetHevCycle (143) and SetHevCycleConfiguration (146) are both 5 bytes: a BoolInt then a u32 of seconds. StateHevCycle (144) reports duration_s, remaining_s, and last_power; StateLastHevCycleResult (149) is a single enum byte.
  • Relays — GetRPower (816) is 1 byte (relay_index u8); SetRPower (817) and StateRPower (818) are 3 (relay_index u8 + level u16). Level is 0 or 65535 only. StateUnhandled (223) is a single u16 naming the message type the device declined — an unhandled *Light* type proves the device is not a light, an unhandled *relay* type proves it has no relays, and the driver concludes nothing from any other value.

The LAN protocol has no error packets — malformed or excessively frequent frames simply cause "unexpected device behavior," so the driver paces itself on fixed timers (no retry storms) and turn Debug Mode → Print on to watch each frame's type and sequence (never raw bytes) in the Lua output window.

10 Program the project

  • When Discovery Complete fires → notify the installer that the scan finished, then read the printed serials.
  • When Went Offline fires → surface a "bulb unreachable" notification or fall back to another light.
  • When Turned On fires → run a room scene; use the BRIGHTNESS/KELVIN variables to mirror the bulb's level elsewhere.
  • When MultiZone Detected fires (or gate on MULTIZONE == yes) → enable a strip scene: set Set Zone Gradient for a sunrise wash, or MultiZone Move On for a moving accent.
  • When the theater goes to Watching and MATRIX == yes and TILE_WIDTH is not 0 → run Set Matrix Color at a low blue for a sconce wash; on Stop, Matrix Effect On with Matrix Effect = MORPH for ambient motion.
  • When the last person leaves and HEV == yes → run Start Clean Cycle; when Clean Cycle Finished fires, branch on CLEAN_LAST_RESULT — announce a completed cycle on SUCCESS, and notify the homeowner on any INTERRUPTED_BY_*.
  • While CLEAN_CYCLE_ACTIVE is true → hold the room's lighting scenes off and mirror CLEAN_REMAINING_S onto a touchscreen so nobody re-enters mid-cycle.
  • When RELAYS == yes → put Relay On / Relay Off on a keypad button for the dumb fixture wired to the switch, and gate the scene on RELAY_POWER rather than on any assumption about the lamp itself.
  • When Relay Changed fires → someone (a Composer command, the switch's own button, or another controller) moved that relay; branch on RELAY_INDEX to tell which one, and re-sync any keypad LED that mirrors it.
  • Gate on IS_LIGHT == no before offering a color or dim UI for this instance — a bound LIFX Switch has no lamp of its own, and those commands are refused on it by design.
  • When the doorbell rings → Flash the porch light. Set Effect Hue 0, Effect Saturation 100, Effect Brightness 100, Effect Period (ms) 600, Effect Cycles 3, then on the doorbell's press event run this instance's Flash command. The porch light flashes red three times over 1.8 seconds and lands back on whatever color and level it was already at — no "restore" step to program, because the waveform's transient flag is what returns it. If the homeowner would rather the light not change color at all, set Effect Channels to Brightness only and the same Flash pulses the level alone. Gate the whole thing on IS_LIGHT == yes if the instance might be bound to a Switch.
  • When the alarm partition goes to Alarm and IS_LIGHT == yes → run Pulse with Effect Duty % at 75 and a short Effect Period (ms): three-quarters of every cycle sits on the alarm color, which reads as urgent rather than decorative.
  • When the theater goes to Watching → run Breathe once at a low Effect Brightness as a "we're starting" cue, and let it settle back to the scene on its own.

13 Ownership, privacy, and licensing

Nothing leaves the controller and nothing leaves the LAN. The LIFX LAN protocol is unauthenticated — there is no token, password, or cloud key to store, so none can be logged or leaked; the only caution is that anyone on the same broadcast domain can address the bulb, so keep it on a trusted segment. The bound target (a serial) lives in PersistData on the controller and is only ever logged as its plain serial. Every control path — Set/Toggle/Color/White, the Flash / Pulse / Breathe effects, the zone and matrix commands, the clean-cycle commands, the relay commands, and Bind/Unbind — is gated by the license and re-checked again at wire-write time, so in Strict mode an unlicensed controller sends nothing (an unlicensed Relay Toggle does not even read); the default Lenient mode lets a dealer commission before a key is minted. Capability probes and state polls are read-only and run regardless of the license. The driver self-updates from the IntegrateIT channel.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

V Version history

v0.5.0 current2026-07-30
  • Light effects. **Flash**, **Pulse** and **Breathe** drive the waveform engine that already lives in LIFX firmware over SetWaveform (type 103) — you hand the light a target color, a period, a cycle count and a shape, and the light animates the transition itself. No controller timers, no burst of frames, and all three put the light back exactly where they found it. The 21-byte payload is packed byte-exactly and was verified against two independent official sources that agree field for field: lan.developer.lifx.com (changing-a-device#setwaveform---packet-103, plus the dedicated Waveforms page for the semantics) and LIFX's own machine-readable definition at github.com/LIFX/public-protocol, whose protocol.yml declares `light.LightSetWaveform` at `size_bytes: 21` with exactly this field order — reserved u8, transient BoolInt, HSBK, period u32, cycles float32, skew_ratio i16, waveform u8. The Waveform enum (SAW 0, SINE 1, HALF_SINE 2, TRIANGLE 3, PULSE 4) is confirmed identically on three official surfaces: the field-types page, the Waveforms page, and protocol.yml's `LightWaveform`.
  • **Flash and Breathe both send SINE, and that is the honest answer rather than a shortcut.** LIFX documents five waveforms, and TWO of them return to the current color *within every cycle* — the vendor's own transient rule names exactly that pair ("the waveform is SINE or TRIANGLE"): SINE, "the color will cycle smoothly from current color to `color` and then end back at current color", and TRIANGLE, "light interpolates linearly from current color to `color`, then back to current color". Flash and Breathe take SINE because it is the SMOOTH one of the two, which is what reads as a flash or a breath; TRIANGLE's linear ramp is equally documented and simply has no command here. What rules HALF_SINE out is firmer than a preference: it is documented as one-directional — "light interpolates smoothly from current color to `color`" — so what it does BETWEEN cycles is documented nowhere, and a Flash built on it would have undefined behavior the moment a dealer set Effect Cycles above 1. This factory does not ship undocumented behavior behind a dealer-facing property, so Flash and Breathe are the same documented shape at two tempos (Effect Period (ms) defaulting to 800, Breathe Period (ms) to 4000) and the driver says so out loud instead of inventing a second mechanism and dressing it up as different. Two period properties land in the one u32 `period` field the wire actually has — better two honest presets than one value multiplied behind the dealer's back.
  • **transient is set on all three, and the docs say precisely why that matters unevenly.** The vendor's rule is exact: "if `transient == true` or the waveform is `SINE` or `TRIANGLE` then the device will return to the original color after the effect. Otherwise the device will not revert." So on Flash and Breathe the flag is REDUNDANT — SINE returns on its own. On Pulse it is LOAD-BEARING: PULSE is neither SINE nor TRIANGLE, so without that one byte the light would be left sitting on the effect color when the cycles ran out. Both facts are in the code comments and the Documentation tab rather than smoothed into a single vague claim, because the difference is exactly what a dealer needs to know before trusting Pulse to hand a room back.
  • Pulse exposes the duty cycle as a **Effect Duty %** property mapped through LIFX's own documented scale. skew_ratio is "a signed Int16 that is scaled from 0 to 1" across the full i16 span, and for PULSE the duty cycle is "1 - skew_ratio as a percentage of the cycle duration" — the fraction of each cycle spent on the new color. So Duty D% goes onto the wire as `round((1 - D/100) * 65535) - 32768`, which reproduces the vendor's own scaling table EXACTLY at 0%, 25%, 50% and 100%. At 75% it lands on -16384 where the table prints -16383; that row is itself rounded (-16383 scales to 0.25002) and -16384 is the nearer wire value for exactly 0.25, one LSB out of 65536 — 0.0015%. The driver prefers the value that inverts the documented formula, and both the reasoning and the discrepancy are written down rather than papered over. Non-PULSE waveforms still pack skew_ratio at its documented offset, at mid-scale 0, because LIFX assigns the field no meaning outside PULSE — the same rule skyType and cloudSaturationMin already follow in the tile-effect payload.
  • **The float32 problem, solved honestly instead of generally.** `cycles` is an IEEE-754 single and this factory packs bytes with arithmetic in portable Lua 5.1 — no bit library, no string.pack. Rather than write a general float codec that would quietly round, denormalize, or mangle what it cannot represent, the driver packs the subset it can PROVE: an integer in [1, 2^24] has an exact float32 representation, and its three fields are pure integer arithmetic — sign 0, exponent found by repeated doubling (never `math.log`, which can be off by one at a power of two), mantissa `(v / 2^e - 1) * 2^23`. Effect Cycles therefore offers whole numbers only, 1-255, and the constraint is stated plainly in the property description, the changelog and the Documentation tab rather than hidden. The packer is pinned in the suite against the constants every float reference agrees on — 1.0 = 0x3F800000, 2.0 = 0x40000000, 3.0 = 0x40400000, 5.0 = 0x40A00000, 10.0 = 0x41200000, 255.0 = 0x437F0000 — and separately against little-endian byte ORDER, because a byte-swapped packer would satisfy a hex comparison and still be wrong on the wire. A value it cannot encode exactly is refused BY NAME; it never sends an approximation of the number the dealer typed. That refusal is the codec's CONTRACT rather than a dealer-facing path, and the distinction is worth stating precisely because the hardening below closes the hole it was originally written for: LuaJIT's `tonumber` parses "nan", and a NaN survives both range clamps (NaN < 1 and NaN > 255 are each false), so before this release the codec's own domain check really was the last thing standing between a non-finite property and four bytes of wire. With the non-finite guard now in `intProp`, Effect Cycles is clamped to 1-255 and a non-numeric or non-finite entry falls back to the default 3 — so nothing a dealer can type in Composer reaches the domain check any more, and the refusal Status is unreachable from the property surface. The codec keeps refusing anyway, for any future caller that does not arrive through a clamped property. The suite proves the reachable half: a non-finite Effect Cycles sends the default 3.0 (0x40400000) and never NaN bytes.
  • SetWaveformOptional (119) is implemented because it is officially documented and it earns its place: LIFX describes it as behaving "like SetWaveform (103) but allows you to keep certain parts of the original HSBK values during the transition" via four trailing BoolInts, and protocol.yml declares `light.LightSetWaveformOptional` at `size_bytes: 25`. That is what makes the one behavior most installs actually want possible — **flash the porch light without turning it a different color**. The new Effect Channels property routes an effect through 103 (full HSBK), or through 119 with `set_brightness` alone, or through 119 with hue/saturation/kelvin and brightness left untouched. An unrecognized selection falls back to full-color 103 rather than sending 119 with no flags set, which would modulate nothing at all.
  • Effects are a capability family and follow this driver's rule for every family before them: **refused until the device positively proves it is a light.** Waveforms are plain Light messages — LIFX attaches no "requires the device has the X capability" note to 103/119 the way it does to SetInfrared and SetHevCycle — so "is this thing a light" is the entire question, and the IS_LIGHT register introduced in 0.4.0 already answers it. This is deliberately STRICTER than the core Power / Set Color gate, which passes while the question is still open so that every bulb this driver has ever controlled behaves exactly as it did in 0.1.0; a new family gets no such grandfathering. A confirmed LIFX Switch refuses all three by name in LIFX's own word for it and points at the relay commands; an unconfirmed device refuses too, and names Refresh State as the action that settles it. 103 and 119 were also added to the LIGHT_TYPES set that reads StateUnhandled (223), so a device that declines an effect frame teaches the driver the same thing a declined Light Get does — leaving them out would have let a 223 for an effect frame mean nothing.
  • **No event, no variable, and that is a finding rather than an omission.** LIFX documents both 103 and 119 as returning a LightState (107) — but that is the ordinary response-to-a-Set reporting the light's state at that instant, NOT a report that the effect finished, and protocol.yml carries no GetWaveform and no StateWaveform of any kind. Nothing in the protocol says an effect started, finished, or was accepted, so nothing here claims it: an effect is fire-and-forget, and the Documentation tab says so in those words. There is also no documented message that CANCELS a running effect, so no Stop command was invented — the honest guidance is to keep cycles x period short, and that is what the docs say.
  • Effects deliberately schedule **no catch-up poll**, unlike every other control path in this driver. All three return the light to the color it started on, so there is no new state to catch up to — and a poll fired 400ms into a flash would publish a color the light is merely PASSING THROUGH and fire a Color Changed for it, then fire another when the light landed back where it began. The normal poll interval still re-reads state, so nothing goes stale. The suite proves both halves: that Set Color does schedule its follow-up read (so the comparison is not vacuous) and that Flash does not, and that Flash fires no Color Changed. What that ordinary poll ALSO does is exactly the thing the previous sentence calls spurious, and the Documentation tab now says so instead of leaving a dealer to find out: a default Breathe is 4000ms x 3 cycles = 12 seconds of animation against a 10-second default Poll Interval, so at least one ordinary poll always lands mid-effect and publishes an intermediate HUE/SAT/BRIGHTNESS with a Color Changed for it. That is a deliberate trade rather than an oversight — reachability (DEVICE_ONLINE, Went Online/Offline) is driven entirely by those poll replies and an effect can run for hours (300000ms x 255 cycles), so pausing the poll would either report a healthy light unreachable or freeze its reachability for the duration. The suite now pins that behavior too, so the doc's claim is a tested claim rather than an assurance.
  • **String sweep: the runtime finally speaks the same language as the 0.4.0 docs.** 0.4.0 taught this driver that a bound LIFX Switch is not a bulb, and its own new relay strings said "device" — but thirteen older runtime Status and Debug strings still said "bulb", so a dealer commissioning a Switch was told to bind a bulb, watched it scan "for LIFX bulbs", and read "No bulb bound" from a driver that had just explained the device has no lamp. Those thirteen are now "device", counted exactly: SIX `No bulb bound` -> `No device bound` refusals (the shared Actuate chokepoint, the extended-zone and matrix chunk writers, the poll's own Device Status line, Unbind, and OnDeviceInit), TWO `Bind a bulb first` -> `Bind a device first` lines (Detect Clean (HEV) and Detect MultiZone, which now match the Detect Matrix and Detect Relays wording 0.4.0 already used), and five singletons — `Discovered N device(s)`, `Scanning the subnet for LIFX devices…`, `run Rescan to find devices`, `no device bound — nothing to poll`, and `no devices answered — check that the device is powered`. (The file now holds NINE `No device bound` strings in total: those six, the two 0.4.0 relay paths that already read "device", and the new effect writer.) "Bulb" is KEPT in exactly FOUR places, where it is family-true and would be less accurate as "device" — the single-zone zone refusal, both HEV refusals, and `Clean cycle start (bulb's configured default duration)` — because only bulbs have zones-or-not and only LIFX Clean bulbs have HEV LEDs. Dealer-facing wording in driver.json is NOT swept here and still says "bulb" in places the runtime no longer does, including the `Rescan (Discover Bulbs)` and `Ping Bulb (Echo)` command names: a Composer command name is a programming binding, so renaming one is a fielded break and its own decision, not a wording cleanup. One suite pin moved with them (`No bulb bound` -> `No device bound`, marked in the test with a one-line deliberate-change comment); no behavior changed and no other check moved.
  • New Flash / Pulse / Breathe commands and eight new properties — Effect Hue, Effect Saturation, Effect Brightness, Effect Period (ms), Breathe Period (ms), Effect Cycles, Effect Duty %, Effect Channels. The effect color is its own triple rather than borrowing Set Color's, so a doorbell flash does not disturb what Set Color is pointed at; Kelvin is shared exactly as the gradient endpoints already share it. No new variables and no new events. Single-bulb, MultiZone, Matrix, HEV and Relay behavior are unchanged: the complete 0.4.0 suite passes against this body with exactly ONE deliberate exception, the string pin above, and the suite now stands at 846 checks. Four of those pins came out of an adversarial re-verification of this release and each one was confirmed to bite: the frame length ON THE WIRE (57 bytes for 103, 61 for 119, header size field included, because a payload-only assertion would pass a driver with a miscounted header), LAW 1 across all seven numeric effect properties rather than `cycles` alone, Effect Cycles clamping rather than reaching the codec's refusal, and the ordinary poll publishing a passing-through color mid-effect. Every sharp new claim was confirmed to fail the suite when deliberately broken — eleven mutations, all caught: a byte-swapped float32 packer, Flash switched to HALF_SINE, transient dropped, the duty formula un-inverted, the effect guard grandfathering an unconfirmed device, 103/119 removed from LIGHT_TYPES, a catch-up poll added, the float32 domain check removed, Breathe borrowing Flash's period, the 119 set_* flags reordered, and skew_ratio leaked onto a SINE waveform. (That last one initially slipped through and the test was strengthened to catch it: the default Effect Duty % of 50 maps to skew_ratio 0, which is also the mid-scale value a non-PULSE waveform sends, so the case now runs at 25% where a leak is visible.)
  • Known limits: still one LIFX device per driver instance, still broadcast reachability, still polled feedback rather than push. Effects treat a strip or matrix as ONE zone — LIFX documents that plainly — so a whole Z, Beam or Ceiling flashes as a single color; per-zone motion is still MultiZone Move or Matrix Effect. SAW and TRIANGLE are documented waveforms no command sends. Effect Cycles is integers only, by the float32 reasoning above. No effect can be cancelled, read back, or confirmed on the wire. Effect Duty % is ignored by Flash and Breathe. One pre-existing driver-wide defect found while building this feature and FIXED here, at the property layer, rather than only in front of the new field: a non-finite value typed into any RANGED_INTEGER property used to survive both range clamps (LuaJIT's `tonumber` parses "nan" and turns "1e400" into inf; `math.floor(nan)` is still nan; every clamp comparison against nan is false), and on the existing integer paths LuaJIT then coerced it to zero bytes rather than erroring — a silent zero period or a silent zero timer interval, not a crash, which is worse. `intProp` now rejects nil, NaN and both infinities and falls back to the property's documented default, so EVERY numeric property in this driver is covered at once — not just the new `cycles`. The suite pins it across all seven effect properties. This build remains simulation-verified: no physical LIFX hardware has been on the bench.
v0.4.02026-07-29
  • Relay power for the LIFX Switch. Relay On and Relay Off pack SetRPower (type 817) as relay_index u8 + level u16 — the fixed 3 bytes — and Relay Toggle reads before it writes (below). The layout was verified against two independent official sources that agree byte for byte: lan.developer.lifx.com (querying-the-device-for-data#getrpower---packet-816, changing-a-device#setrpower---packet-817, information-messages#staterpower---packet-818) and LIFX's own machine-readable definition at github.com/LIFX/public-protocol, whose protocol.yml declares `relay.RelayGetPower` at 1 byte and `relay.RelaySetPower`/`relay.RelayStatePower` at 3. Only two levels are ever sent: LIFX documents that "Current models of the LIFX switch do not have dimming capability, so the two valid values are `0` for `off` and `65535` for `on`", so intermediate values — undefined for a relay — are not offered and there is no relay-level property. The registry does now list a "LIFX Dimmer Switch" (pid 226); the LAN protocol still documents no dimming semantics for SetRPower, so the driver does not invent any for it.
  • Relay capability follows the 0.2.0/0.3.0 dual-path rule exactly. A StateVersion product id in the embedded relays subset of the official products registry (LIFX Switch 70/71/84/89/115, LIFX Switch US 116, LIFX Dimmer Switch 226 — every product with `features.relays: true` under vendor 1) OR any StateRPower reply flips RELAYS to yes and fires Relays Detected. Until something positively confirms, RELAYS stays unknown and every relay command is refused locally, by name, naming Detect Relays as the action that settles it. Detect Relays re-opens its own family only, and the probe asks about relay 0 — the one index the protocol actually names ("The relay on the switch starting from `0`").
  • **A relay is not a light, and the driver now says so out loud.** LIFX documents the Switch as a "non light" that ignores Light messages and answers StateUnhandled (223) instead of a State, and every one of those seven relay products carries `color: false`, `matrix: false`, `multizone: false`, `hev: false` and no `temperature_range` at all in the registry — no light features whatsoever, checked product by product rather than inferred from "it has relays". So a confirmed switch refuses Power On/Off/Toggle, Set Color and Set White by name and points at the relay commands instead, rather than writing frames the device is documented to throw away. IS_LIGHT is its own variable — unknown, yes (it answered a State; only a light does) or no — and it is never decided by the relay verdict.
  • That honesty also fixed a reachability bug the feature would otherwise have shipped with. The driver polls Light Get; a Switch answers StateUnhandled, which 0.3.0 ignored entirely — so a perfectly healthy switch answering every single poll would have sat at DEVICE_ONLINE false forever. A refusal IS an answer: StateUnhandled now counts as proof of life, and a confirmed non-light is polled on its relay (or, while its relays are still unconfirmed, with EchoRequest — the device message every LIFX device answers) instead of being asked for light state that will never come.
  • StateUnhandled is read for WHICH type came back, not treated as one signal, because the two readings point in opposite directions. An unhandled *Light* message proves the device is not a light. An unhandled *relay* message proves it has no relays. Treating any 223 as "not a light" would have branded every ordinary LIFX bulb a switch the moment it declined this driver's relay probe — so the driver reads the u16 and concludes only what that specific type supports, and nothing at all from any other type.
  • The non-light verdict is one-way, and only from an open question. A device that has ANSWERED a State(107) has positively proven what it is, so a later StateUnhandled for a Light message cannot demote it — the same monotonicity the relay half of the split already had. This matters more than it looks: the demotion also switches the poll off Light Get, so without the guard it sealed itself in. One forged frame on this unauthenticated LAN (or one firmware hiccup) would have left a healthy bulb answering the EchoRequest keepalive, sitting at DEVICE_ONLINE true, and refusing every Power / Set Color / Set White until someone re-bound the driver — the driver would never again have asked the one question whose answer clears it. Caught in adversarial review before ship; the repro is in the suite.
  • Relay Toggle is honest or it does not run. LIFX has no toggle verb, and the last position this driver saw may be seconds old or may be about a different relay — so Relay Toggle sends GetRPower and writes the inverse only when THAT read is answered, matched on the (source, sequence, target) triple LIFX documents for correlating a reply to its request. A reply about a different relay, or a late answer to an earlier read, releases nothing. A read that goes unanswered inside the 2s window is a refusal that says the relay was left untouched — never a write from stale state, because a blind toggle on a relay feeding a real load is exactly the command that must not fire on a guess.
  • Relay state is per-relay, because it has to be. RELAY_INDEX / RELAY_LEVEL / RELAY_POWER describe the relay that just reported, and Relay Changed compares a relay against ITSELF using a table keyed by the protocol's own u8 index — a single scalar would have fired a phantom "changed" the moment someone pointed Relay Index at a different relay that happens to sit the other way. Adoption is silent, like every other state in this driver: the first report from a relay is not a change. RELAY_INDEX starts empty rather than "0", because 0 is a real relay index and publishing it before anything has reported would claim a reading the driver does not have.
  • Deliberately NOT claimed: the relay count. LIFX publishes it nowhere official — not in the LAN protocol, not on the LIFX Switch page, and not in the products registry, which carries no relay-count field at all. So Relay Index exposes the full 0-255 span the protocol's own u8 relay_index allows instead of hard-coding a count from a third-party library, and the variables report only what a real StateRPower said. For the same reason the state variables are indexed rather than RELAY_1..4: a fixed set of four would have been an invented count wearing the costume of a fact.
  • Also not claimed: what the load is doing. A relay closes a circuit feeding a DUMB fixture. The driver knows the relay's POSITION, which is all the switch reports, and cannot know whether anything is lit — a burnt-out lamp, a pulled fixture and a lamp switched off at its own body all read identically as a closed relay. Documented plainly rather than papered over. The switch's physical BUTTONS are not read either: LIFX documents button messages, but this build implements the three relay messages only, so a press surfaces only as the Relay Changed that follows it when that button drives a relay.
  • Flood posture inherited from 0.3.0: exactly one relay message per poll and one per command, never a sweep across indices the driver has no count for. Every relay control path re-checks the license at wire-write time like the single-bulb, zone, matrix and clean paths before it, and an unlicensed toggle does not even read.

Single-bulb, MultiZone, Matrix and HEV behavior are unchanged — the complete 0.3.0 suite (537 checks) passes unmodified against this body, and the four sharpest new claims (per-relay change tracking, toggle sequence-matching, toggle refusal on an unanswered read, and the StateUnhandled split) were each confirmed to fail the suite when deliberately broken.

Relay writes are sent with the same res/ack posture as every other Set here — LIFX's own guidance is that a State reply to a Set is "usually not useful" — so a write is confirmed by the read-back that follows it, not on the wire.   • Matrix/Tile for LIFX Tile, Candle, Ceiling, Path, Spot, Tube, Luna and Mirror.
