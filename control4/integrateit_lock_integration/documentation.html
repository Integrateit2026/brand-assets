1 Start here

IntegrateIT Lock Integration turns Control4 relay outputs into supervised control of an electric strike, maglock, or motorized deadbolt. It energizes a relay to lock or unlock, reports the authoritative locked/unlocked state from a position contact, and adds two behaviors purpose-built for locks: an auto-relock timer that re-secures the opening after an unlock, and a fire/egress safety interlock that refuses to lock — and forces the opening to release — while a fire-alarm or egress input is active.

Unlike the IntegrateIT Garage driver, this is not a door-travel state machine. It models a lock — *secure* versus *release* — confirmed by a contact, with life-safety release taking priority over any lock command.

Ready for controlled commissioning. The package, Lua 5.1 runtime, relay control, contact supervision, auto-relock, interlock, jam detection, license gates, persistence, and documentation pass automated QA. A qualified dealer must still complete a fresh install and an observed lock, unlock, auto-relock, and interlock cycle on the target controller, relay hardware, lock, position contact, and fire/egress source.

What you get

  • Single-momentary control (one output) or separate lock and unlock outputs
  • Momentary or maintained relay drive, with an invert option for fail-safe vs fail-secure wiring
  • Position-contact feedback as the authoritative lock state, with dealer-set polarity
  • Auto-relock timer (0 disables; any value re-locks that many seconds after an unlock)
  • Fire/egress safety interlock: an active safety input refuses Lock and forces release
  • Lock Jammed supervision when the status contact never confirms a commanded state
  • Composer events, programming variables, diagnostics, persistence, and a relay-safe license gate

2 Safety boundary

A lock is a life-safety device. On any egress or fire-rated opening, the fire-alarm relay MUST drop the maglock in hardware, independent of this or any driver. This driver's interlock is a supervisory automation layer, not a listed life-safety release. Never make it the only path that unlocks an egress door. The driver supervises relay control and contact feedback; it does not replace a listed access-control panel or a fire-alarm relay interlock.

Before enabling control:

  1. Prove the lock, the manual release, and the fire/egress drop using the panel and the hardware itself — with Control4 disconnected.
  2. Confirm the Control4 relay is electrically isolated and rated for the lock's control input.
  3. For a maglock, wire the fire-alarm relay to physically de-energize the lock. Bind that same signal to the Egress/Safety Input so the driver's interlock mirrors it.
  4. Set the status contact so Lock Status reads the true measured state before you rely on programming.

With a bound status contact the reported state is *measured*. With no contact, Lock Status is *assumed* from the last command, jam supervision is unavailable, and nothing observes the real bolt — anything claiming otherwise would be faking it. Clearing the egress input does not re-lock the opening; a lock must be commanded, so a fire release never silently re-secures a door behind an occupant.

3 Wire and commission

  1. Add IntegrateIT Lock Integration to the room containing the opening.
  2. Match the driver to the lock hardware using the lock-type matrix below, then set Relay Configuration, Relay Output Mode, and Invert Relay Logic accordingly. Bind the relay output(s) using the connection map further down.
  3. Set Pulse Length (ms) to the momentary duration the lock expects (default 1000 ms). Ignored in Maintained mode.
  4. Bind the Lock Status Contact and set Lock Contact Active State to the electrical state that means Locked. Confirm Lock Status tracks the real bolt/strike.
  5. Bind the Egress/Safety Input to the fire/egress signal and leave Use Safety Interlock at Yes. Assert the signal and confirm the driver fires Safety Interlock Active and releases the opening.
  6. Set Auto-Relock (s) if the opening should re-secure itself after an unlock (0 keeps it manual). Set Confirm Timeout (s) for how long the contact has to confirm before Lock Jammed fires.
  7. Enter a License Key for production (the driver runs in Lenient mode without one), clear the area, and observe a full lock, unlock, auto-relock, and interlock cycle before handoff.

4 Match the driver to the lock hardware

The relay settings must reflect what the lock does *electrically* — pulse versus maintained, and energize-to-lock versus energize-to-release. Choosing wrong mis-drives the hardware: a Momentary "Lock" on a maglock energizes it for one pulse then releases it, so it never stays locked; a non-inverted pulse on a fail-secure strike momentarily buzzes it open on a Lock command.

  • Relay Output Mode — Maintained holds the Lock Output energized to keep the opening secured and de-energizes it to release. Use it for any maintained device (a maglock is the canonical case). Momentary pulses the relay for Pulse Length (ms) then releases; use it for strikes and toggle deadbolts.
  • Invert Relay Logic — swaps the energize and release commands for every output. Leave No when energizing the relay should *lock* the opening (fail-safe). Set Yes when energizing the relay should *release* it (fail-secure).
  • Relay Configuration — Single Momentary pulses the SAME Lock Output for both lock and unlock, so it only suits toggle-on-pulse hardware or a Maintained maglock. Anything that needs distinct lock and unlock triggers uses Separate Lock/Unlock, which pulses the Lock Output to lock and the dedicated Unlock Output to unlock.
For a maglock, set Relay Output Mode to Maintained. In Momentary mode the driver only pulses the relay, so the maglock would drop out after the pulse and never stay locked. The fire-alarm relay must still de-energize the maglock in hardware, independent of this driver.

5 Wire the Control4 bindings

BindingNameUse
1Lock OutputRelay that locks the opening; also the single output in Single Momentary mode
2Unlock OutputRelay that releases the opening in Separate Lock/Unlock mode
3Lock Status ContactPosition contact reporting the authoritative locked/unlocked state
4Egress/Safety InputFire-alarm or egress signal that drives the safety interlock

The Egress/Safety Input is treated as asserted when its contact is CLOSED. On (re)bind, Director sends a STATE_ snapshot; the driver seeds its state from the snapshot silently — it fires no event and drives no relay until a real transition arrives. At boot the driver also polls both feedback contacts (GET_STATE) so an egress input already asserted at power-up is honored and Lock Status is measured from the first cycle rather than assumed.

6 Program the project

Use the specific state events for automation. Lock Jammed and Safety Interlock Active are the two you should never leave unhandled on a real opening:

  • When Lock Jammed fires → notify the homeowner and flash a light. A bolt the status contact never confirmed within Confirm Timeout (s) is either mechanically stuck or mis-wired, and it must not fail silently.
  • When Safety Interlock Active fires → announce or log the egress release. Never program anything that re-locks in response — the release is deliberate, and the opening must stay released until the egress input clears and someone commands a lock.
  • When Unlocked fires for an expected guest → run a welcome scene, and set Auto-Relock (s) so the opening re-secures itself without a second program. Auto-Relock Scheduled fires when that timer is armed.

Lock Status holds Locked, Unlocked, or Unknown. It is safe to drive automation from Locked and Unlocked only when a status contact is bound and verified — those are measured. Without a contact the value is assumed from the last command, and Lock Jammed can never fire because there is nothing to confirm against. State persists across a controller reboot; a bound contact re-measures it on the first snapshot after boot.

Print Diagnostics writes the state, last action, relay configuration, pulse length, auto-relock, interlock setting, contact polarity, confirm timeout, and IntegrateIT identity to the Lua output window. It never prints the license key.

9 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation built on the documented Control4 relay and contact-sensor contracts. It does not bundle another vendor's runtime, source code, brand assets, trial system, or license. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

The lock runtime drives local relays and reads local contacts. It does not send lock state, project identity, or Control4 credentials to any device vendor — nothing about the opening leaves the controller for a third party. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below. The license key is stored as driver configuration and is never written to the log or the diagnostic summary.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all relay control until the Ops Portal has minted and validated a key for that controller — but the fire/egress safety release is never gated by licensing, because a life-safety release must always run. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.
