1 Start here

IntegrateIT Bond Ceiling Fan brings a single Smart by Bond ceiling fan — device type CF — into Control4 over the Bond Home local HTTP API v2 (the vendor's own published local API, github.com/bondhome/api-v2). There is no cloud hop: the driver talks straight to the Bond Bridge (or a Smart by Bond radio) on your LAN, authenticated by the local token you copy from the Bond Home app. Where the generic Bond driver can only fire a press, this one models the fan as a first-class device — graded speed clamped to the fan's real maximum, summer/winter direction, Breeze, and light — and it reflects changes made from a handheld remote or the Bond app back into Control4 through the Bond Push UDP Protocol (BPUP), so programming reacts to the fan itself, not just to Control4.

The Bond local API is plain, unencrypted HTTP on port 80, and BPUP push is unencrypted UDP on port 30007, authenticated only by the local token. Keep the Bond on a trusted LAN segment. The driver refuses a non-LAN Bond address unless Allow WAN Bond is set to Yes, and it never writes the token to the log.
Release candidate, verified against the Control4 API simulator. The package, Lua 5.1 runtime, action framing, /state and BPUP frame parsing, the transition-only event diffing, the LAN guard, the license gate, timer hygiene, persistence, and this documentation pass automated QA. A qualified dealer must still complete a fresh install and an observed control test against a real Bond Bridge and physical fan on the target controller — acceptance on physical hardware is not yet attached to this release.

What you get

  • One Bond ceiling fan per instance over the local v2 HTTP API — no cloud dependency
  • Graded speed: Set Fan Speed (clamped to Fan Max Speed), Speed Up, Speed Down
  • Power On/Off/Toggle Power, Toggle Direction, Breeze On/Off, Toggle Light, Set Brightness
  • Real push feedback: the BPUP UDP listener (port 30007) reflects remote/app changes without polling, with hash-gated HTTP polling as the fallback
  • POWER, SPEED, DIRECTION, BREEZE, LIGHT, and DEVICE_ONLINE variables with transition-only events
  • Honest feature detection — an action the fan was not learned with is refused, never a silent no-op
  • A non-CF device is refused by name, pointing at the IntegrateIT driver that models it where one exists
  • List Bond Devices, Test Connection, and Print Configuration actions to commission without guesswork

2 The feedback contract

State feedback is push-first, poll-as-fallback, and the Feedback Mode property always says which path is live.

  • Push (BPUP). The driver opens a UDP socket to the bridge on port 30007 and sends the keep-alive datagram to subscribe. The bridge then pushes a JSON state frame whenever the fan changes — from a remote, the Bond app, or another controller — and the driver applies it immediately. It resubscribes on a timer, ahead of the bridge's 125-second silence drop.
  • Poll fallback. If push goes silent (roughly two keep-alive intervals with no frame), or you set State Feedback to Poll only, the driver polls GET /v2/devices/<id>/state on the Poll Interval (s) and only re-applies when the state hash (_) changed. A frame or poll arriving flips Feedback Mode back to Push (BPUP) when push resumes.
  • Boot is silent, then honest. After a controller reboot POWER, SPEED, DIRECTION, BREEZE, and LIGHT are unknown until the first frame or poll lands. That first observation *adopts* the fan's current state silently — it does not fire a spurious event. Events fire only on a genuine change between two observed states.
  • Reachability is a real signal. A push frame, or any HTTP reply (even a 401/404), proves the fan answered, so DEVICE_ONLINE goes true and Went Online fires. Only a transport failure with no response marks the fan Offline and fires Went Offline.
  • Commands are not acknowledgements. Bond returns no new state inline with a command, so after a successful action the driver schedules a fast follow-up poll (~400 ms) to catch the variables up.
Unsupported features are refused, not faked. Toggle Light, Set Brightness, Breeze On/Off, and Toggle Direction are offered only when the fan was learned with those actions. On a fan without them the command sets Status to "not supported by this fan" and sends nothing — anything claiming otherwise would be faking it.
One device type, enforced. This driver controls Bond ceiling fans (CF) and nothing else. The bridge reports each device's type in the record this driver already reads, so once that record has been read, a Device ID pointing at any other type is refused before anything reaches the wire — not warned about, refused. MS, FP, GX, and LT are named along with the IntegrateIT driver that owns them; HT, SW, and BD are named for what they are, with no driver invented for you to go looking for; anything else is refused flatly. The refusal outranks the feature list, because a fireplace that advertises TurnOn is still a fireplace — and on a fireplace TurnOn is the flame. In the seconds after load, before that record has been read, a command is still attempted and the bridge's own answer surfaced: refusing on no evidence would be inventing a verdict. A record that comes back with no type field at all is a different case and is refused, because Bond's own schema marks the field required.

3 Wire and commission

  1. In the Bond Home app, open the fan → Settings → Advanced Settings and note the Local Token and the Bond's IP address. Reserve that IP in your router's DHCP table so it cannot change.
  2. Add IntegrateIT Bond Ceiling Fan to the fan's room. Enter Bond IP Address and Bond Token.
  3. Run the List Bond Devices action. It prints every device id, name, and type on the bridge, marks the CF entries as belonging to this driver, and names the dedicated driver for anything else. Paste a CF id into Device ID.
  4. Run Test Connection. On success it prints the fan name and type, refuses in plain language if the type is not CF, and populates Device Type, Fan Max Speed, and Supported Features from the fan's record and properties.
  5. Leave State Feedback on Push + Poll fallback unless UDP 30007 is blocked on your network; set Poll Interval (s) for the fallback cadence.
  6. In Programming, wire the commands to keypads and scenes, and optionally react to the events or read the variables.
  7. Optionally enter a License Key (see Ownership, privacy, and licensing) — the driver runs in Lenient mode without one.
  8. Prove it: change the fan from its handheld remote and watch Feedback Mode read Push (BPUP), SPEED/POWER update, and the matching event fire — with no polling delay.

4 The Bond CF API on the wire

The transport is HTTP on port 80 with a BOND-Token request header; push is UDP on port 30007. Every control command is a PUT /v2/devices/<id>/actions/<Action>; state and metadata are GET reads.

CommandWire action (PUT …/actions/…)Body
Power On / Off / ToggleTurnOn / TurnOff / TogglePower{}
Set Fan SpeedSetSpeed{"argument":N}
Speed Up / DownIncreaseSpeed / DecreaseSpeed{}
Toggle DirectionToggleDirection{}
Breeze On / OffBreezeOn / BreezeOff{}
Toggle LightToggleLight{}
Set BrightnessSetBrightness{"argument":N} (1-100)
  • Set Fan Speed sends the Fan Speed property (1-10), clamped to the fan's reported maximum (Fan Max Speed, learned from GET …/properties).
  • Feature learning: GET /v2/devices/<id> lists the actions the fan was learned with. The driver reads that list into Supported Features (light / breeze / direction) and gates those commands on it.
  • Reads: GET /v2/devices (enumerate), GET /v2/devices/<id> (name/type/actions), GET …/properties (max_speed), GET …/state (power, speed, light, direction, breeze). 401 means a wrong token, 404 a wrong device id.
  • BPUP frame: the bridge pushes {"B":<serial>,"t":"devices/<id>/state","s":200,"b":{"_":<hash>,"power":1,"speed":2}}\n. The driver reassembles \n-delimited frames tolerant of arbitrary datagram boundaries, applies only frames carrying this fan's state topic, and ignores the rest.

  • React to a physical remote instantly: because push is live, starting the fan from its handheld fires Turned On within the push latency, not the poll interval — use it to raise the room lights or set a scene.
  • Drive speed from a keypad: set the Fan Speed property (say 6), then call Set Fan Speed — the driver clamps to Fan Max Speed and sends SetSpeed. Or bind buttons to Speed Up / Speed Down.

Control is gated by the license: under Strict enforcement an unlicensed controller sends no action to the fan. Push and poll feedback stay live regardless — watching your own fan report is not a licensed feature. The default Lenient mode allows commissioning while License Status carries the nag.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of Bond's published local HTTP API v2 and Bond Push UDP Protocol (github.com/bondhome/api-v2, documents Olibra publishes so external equipment can drive Bond devices). It bundles no other vendor's runtime, source, brand assets, trial, or license. Bond and Smart by Bond are trademarks of Olibra LLC; IntegrateIT is not affiliated with Olibra, and this driver is not a Bond product.

Nothing leaves the LAN. The driver talks only to the Bond address you configure — HTTP on port 80 and UDP on port 30007 — and to nowhere else; no fan state, customer identity, or Control4 credential is sent to any device vendor. The Bond Token is treated as a secret: it travels only in the request header and is never written to the Lua log, not even with Debug Mode on. A public or routable destination is refused outright unless Allow WAN Bond is deliberately set to Yes.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all fan control until the Ops Portal has minted and validated a key for that controller; push and poll feedback continue either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

v0.1.12026-07-29
  • A corrupted Fan Speed or Brightness property can no longer put a malformed body on the wire. Values like nan or inf slipped past the range clamp (every comparison against nan is false) and were transmitted literally as {"argument":nan}, which is not valid JSON.
  • A corrupted Poll Interval (s) can no longer stall state feedback. It became a nan-millisecond timer that never fired again, so the fan's published state silently stopped tracking.
  • A corrupted numeric property now falls back to that property's documented default, in the same spirit as the existing range clamp.
  • The single point where a Bond action is transmitted now refuses a non-finite argument outright, so no future command can reopen this.
  • Security fix (LAN guard bypass): the boot-time metadata reads FetchProps (GET /properties) and FetchDeviceDoc (GET /v2/devices/<id>) had no LAN-destination check, so a Bond IP pointed at a public/WAN host still received two token-bearing GETs from OnDeviceInit even with Allow WAN Bond = No — leaking the BOND-Token header off-LAN at load. The LAN guard now runs at the single BondHttp transport chokepoint, so every Bond HTTP call (control, poll, and boot reads) is refused for a non-LAN destination unless Allow WAN Bond is Yes. Regression test added (a public IP boots with zero token-bearing requests).
