1 Start here

IntegrateIT UniFi Access brings one UniFi Access door into Control4 over Ubiquiti's official local Developer API — JSON over HTTPS on the console hosting the Access application (port 12445), authenticated by a Bearer token the console owner mints themselves (Ubiquiti's published api_reference.pdf). There is no cloud hop and no vendor account round-trip: the driver talks straight to the console on your LAN. A configurable poll reads the door's lock relay and position sensor and publishes them as variables and events, and a deliberate, double-gated Unlock Door command is the only thing this driver ever writes back.

This is an access-convenience surface — status, programming hooks, and a deliberate remote unlock — not a life-safety or security-rated system. Status is polled, commands travel a network, and Access's own policies stay authoritative. Never make this driver the sole control for any door where a failed, delayed, or replayed command has safety or security consequences.
Ready for controlled commissioning. The package, Lua runtime, Developer API framing, envelope + door parsing, the LAN guard, the unlock double-gate, the license gate, and this documentation pass automated simulation QA (hardwareStatus: simulation-verified). A qualified dealer must still complete a fresh install and an observed door test against a real UniFi console, Access hub, and door before relying on it — no bench-tested claim is made.

What you get

  • One door per instance, polled over the local Developer API — GET /doors/<id> diffed into state, no cloud dependency
  • DOOR_LOCKED, DOOR_POSITION (Open / Closed / Unknown), DOOR_NAME, and DEVICE_ONLINE variables, republished on every poll
  • Door Opened/Closed, Door Locked/Unlocked, Went Online/Offline, and Remote Unlock Sent events for Composer programming
  • Unlock Door double-gated: the IntegrateIT license AND a dealer-set Allow Remote Unlock switch — monitor-only out of the box
  • List Doors, Test Connection, Refresh State Now, and Print Configuration commissioning actions; hubless doors flagged as not remotely unlockable
  • A LAN-only destination guard (WAN refused unless opted in), self-signed-aware TLS with an opt-in strict mode, and an API token that is never written to the log

2 Safety boundary

A remotely triggered strike lets someone in. Treat Allow Remote Unlock as a decision the site owner makes, not a default. Egress hardware, anti-passback, schedules, and Access's own permissions remain the authority on who may open this door — this driver is a convenience layer on top of them, never a replacement.

The only mutating path in this version is Unlock Door, and it is gated three deep before a strike ever pulses:

  1. The IntegrateIT license. Under Strict enforcement an unlicensed controller sends no unlock; the read poll keeps running, because monitoring your own door is not a licensed feature.
  2. Allow Remote Unlock = Yes. Ships No. While it is No the driver is monitor-only and the command refuses even from Composer programming — nothing pulses a strike until a human flips it.
  3. The hub-bind rule. A door not bound to an Access hub cannot be unlocked through the API at all (a UniFi platform rule). When the last poll saw is_bind_hub false, the command refuses locally with no HTTP sent, and List Doors flags that door.

What "unlock" means here is exactly what UniFi permits remotely: a momentary unlock on a hub-bound door via PUT /doors/<id>/unlock. The driver does not lock on command, does not manage credentials, schedules, or access policies, and cannot force a door Access itself would refuse. The unlock is sent with an empty body, so the console logs it under the API token's own name — the documented default actor — leaving a truthful audit trail on the UniFi side. A non-LAN console address is refused before anything reaches the wire — on the unlock path and on every poll — unless Allow WAN Console is set to Yes.

3 The feedback contract

State is polled, never pushed, and the driver never invents a reading:

  • A badge-in, a manual unlock, or a door swing appears on the next poll (default 5 s), not instantly. Ubiquiti's WebSocket notifications and webhooks are documented but out of scope for this version.
  • Change events fire only when a state moves from a known value to a different one. The first poll after boot adopts the door's current lock and position silently — no spurious Door Opened or Door Unlocked on startup. Reachability is the exception: the first observation is itself a real transition, so it does fire Went Online / Went Offline.
  • door_position_status reports open or close; a door with no wired position sensor (DPS) reports it as an empty string or a JSON null — both normalize to DOOR_POSITION = Unknown, and position events never fire for that door. A DPS that drops mid-life clears back to Unknown rather than pinning the last Open/Closed reading forever.
  • Reachability is honest about the transport: any HTTP response — even a 401 — means the console answered, so Went Online fires; only a genuine transport failure (no response) marks it Offline.
  • After a controller reboot every state restarts unknown; nothing that happened while the driver was down is observable. The next poll re-primes the truth.

4 Wire and commission

  1. On the UniFi console, open Access → Settings → General → Advanced → API Token and create a token. Give it the view:space scope (add edit:space only if remote unlock will be used) and copy it immediately — it is shown once. Reserve the console's IP in DHCP so it does not move.
  2. Add IntegrateIT UniFi Access to the door's room. Set Console Address to the console's LAN IP and paste the token into API Token. Leave Console Port at 12445 unless you changed it on the console.
  3. Run the List Doors action. It prints every door id, name, and state this token can see, and flags any door that cannot be remotely unlocked. Paste the correct id into Door ID.
  4. Run Test Connection — it should report the Developer API reachable and the door count. Adjust Poll Interval (s) if the 5 s default is too fast or slow.
  5. Watch the Device Status property fill in with the door's live lock/position state, and confirm DOOR_LOCKED / DOOR_POSITION track the door as you cycle it by hand — that proves the poll.
  6. Only if the site owner approves Control4-initiated unlocks, set Allow Remote Unlock to Yes and wire the Unlock Door command in Programming. Enter a License Key for production (the driver runs in Lenient mode without one).
The Developer API needs the Access application at v1.9.1 or newer and is removed on consoles migrated to UniFi Identity Enterprise. One driver instance monitors exactly one door — add another instance per door.

5 Protocol on the wire

Every call is JSON over HTTPS to https://<console>:<port>/api/v1/developer, with the Bearer token in the Authorization header only — never in a log line. Debug Mode → Print logs the unlock as method + path (PUT /doors/<id>/unlock) plus its HTTP result, and any transport error; the token is never printed. The background poll is deliberately quiet — run Refresh State Now when you want a poll's HTTP status on the screen.

CallPurpose
GET /doorsEnumerate doors — Test Connection, List Doors
GET /doors/<id>Poll one door's lock relay + position (the state poll)
PUT /doors/<id>/unlockMomentary unlock — empty {} body, so the token is the logged actor

Every response is wrapped in Ubiquiti's envelope, {"code":"SUCCESS","msg":…,"data":…}. A poll is trusted only when the HTTP status is 200 and the envelope code is SUCCESS; anything else is surfaced, not swallowed. The door parse reads only anchored fields — name, door_lock_relay_status (lock/unlock), door_position_status (open/close/empty/null), and is_bind_hub (accepted as a JSON boolean or a quoted string, since the reference declares the field String while the sample emits a boolean); List Doors additionally reads each door's id and full_name. Documented error envelopes map to plain status text:

  • CODE_AUTH_FAILED / CODE_ACCESS_TOKEN_INVALID → "Auth failed — check the API Token"
  • CODE_UNAUTHORIZED → "Token lacks permission — re-issue with the needed scopes"
  • any other non-SUCCESS code → "Access error (…)"; a non-200 with no envelope → "Console error (HTTP …)"

Two commands are wireable: Unlock Door, gated as described above, and Refresh State, which polls immediately instead of waiting out the interval. Three ways these wire into Composer:

  • When Door Opened fires → announce it or start a timer. React to the door actually swinging, whichever system opened it — badge, app, or Control4.
  • When a delivery is expected → Unlock Door, then watch Remote Unlock Sent. The event confirms the console accepted the pulse; the driver re-polls within half a second so DOOR_LOCKED catches up.
  • When Went Offline fires → notify the rack owner. A console that stops answering is worth surfacing before someone finds the door unresponsive.

Control is license-gated: under Strict enforcement an unlicensed controller writes no unlock, while polling and events stay live. The default Lenient mode allows commissioning with License Status carrying the nag.

The driver talks only to the UniFi console you configure, on your LAN, and sends door state and unlock commands nowhere else. The API Token is the entire credential: it is sent only in the Authorization header, is never written to the Lua log even in Debug, and Print Configuration reports only its length. A non-LAN console is refused unless you explicitly set Allow WAN Console = Yes. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks the remote unlock until the Ops Portal has minted and validated a key for that controller; polling and feedback continue either way. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
