1 Start here

IntegrateIT Shelly Cover gives Control4 full control of a single Gen2+ Shelly Cover component — one roller, shade, awning, or gate motor — over the device's own local JSON-RPC 2.0 API (POST /rpc), with no Shelly Cloud account and no issued credentials. It is the dedicated cover driver the generic IntegrateIT Shelly driver deliberately does not try to be: Open, Close, Stop, Go To Position (0–100), and Calibrate, with real two-way position feedback read straight from the device. The protocol is Shelly's published Cover component (documented at shelly-api-docs.shelly.cloud); the driver reads Cover.GetStatus back after every action and on a poll timer, and publishes position, state, and faults as Control4 variables and events so programming reacts to what the hardware actually did.

Shelly hardware ships with its local authentication off by default, so on that default anyone on the LAN can drive the cover. Keep these devices on a trusted, segmented network, and treat the cover as switching a real motor on a physical load. Enable the device's own auth before exposing it to an untrusted network — but note Gen2+ digest is not implemented in this version (see On the wire), so an auth-enabled device is unreachable by this driver until it ships.
Ready for controlled commissioning — simulation-verified, not yet hardware bench-tested. Gen2+ detection, the full cover control surface, two-way position/state feedback, exactly-once movement events, calibration honesty, obstruction reporting, the LAN-only safeguard, 429 backoff, the digest capability gate, and the license gate all pass the IntegrateIT driver-factory QA simulation. A qualified dealer must still commission against a real Shelly Cover on the target controller and confirm each action moves the hardware.

What you get

  • Cover control: Open, Close, Stop, Go To Position (0–100 via Target Position (%)), and Calibrate
  • Real reported position in POSITION (0–100) and Position (%), updated only from Cover.GetStatus — never a value the driver invented
  • Movement events with exactly-once semantics: Motion Started / Motion Stopped, plus Fully Open / Fully Closed and Position Changed
  • Honest calibration: an uncalibrated device shows position Unknown, and a Go To Position the device refuses raises Calibration Needed
  • Safety reporting: obstruction / overpower / overtemp / safety-switch faults published to LAST_ERROR with an Obstruction Detected event
  • Reachability tracking (DEVICE_ONLINE) with Went Online / Went Offline
  • LAN-only destination safeguard; the device password is password-typed and never written to the Control4 log
  • MAC-locked IntegrateIT licensing with Lenient or Strict enforcement

2 The feedback contract

This is a real-position device, and the driver treats it like one: every value it publishes was reported by the cover, never assumed.

  • Position and state are read back, not guessed. After an Open/Close/Stop/Go To Position the driver reads Cover.GetStatus and publishes the device's own state and current_pos. POSITION is what the device reports, not the target you sent.
  • The first observed value is absorbed silently. When a poll or detect discovers the cover's current position and state at boot, the driver adopts them without firing an event — no phantom Motion Started or Fully Open for a change the device did not just make. Events fire only on a genuine transition after that.
  • Movement events are exactly-once. Motion Started fires once when the cover enters a moving state (opening, closing, calibrating); Motion Stopped fires once when it leaves one — no matter how many repeated or coalesced status frames report the same state in between.
  • Uncalibrated means Unknown, honestly. A Shelly Cover only reports a position once it has been calibrated. When the device reports pos_control:false (or omits current_pos), POSITION reads Unknown and CALIBRATED is 0. A calibrated position simply does not exist yet — anything claiming otherwise would be faking it.
  • After a controller reboot the driver knows nothing until the first read. POSITION sits at -1 (Unknown) and COVER_STATE at Unknown; those defaults are not a reading of the hardware, so do not drive automation off them before the first successful Cover.GetStatus.

3 Wire and commission

  1. Put the Shelly in Cover profile in its own web UI and run its calibration routine, so it can report and target a position. Give it a static IP (reserve it in DHCP) and confirm http://<ip>/rpc/Shelly.GetDeviceInfo answers a small JSON identity blob in a browser.
  2. Add IntegrateIT Shelly Cover to the room and enter the Shelly IP Address — a bare dotted-quad IPv4, not a URL and not an IPv6 literal. Leave Allow Non-LAN Address at No unless the device is on a deliberately routed segment.
  3. Set the Cover ID (0 for a single-cover device; 0–3 on a multi-channel model). Bind a second driver instance for a second cover.
  4. If the device has authentication enabled, enter the Username (Gen2+ is always admin) and Password. Gen2+ digest is not implemented in this version — an auth-enabled device answers 401 and the driver reports the hardware gate (see On the wire). Leave both at their defaults when auth is off (the Shelly factory default).
  5. Run Detect Device. Detected Model should populate and Device Status should show the live cover state. A Gen1 device is refused here — use the generic IntegrateIT Shelly driver for Gen1 rollers.
  6. From the Actions tab, run Open / Close and watch the cover move — COVER_STATE follows through opening/closing to stopped/open/closed, and POSITION tracks the reported position. Optionally enter a License Key (Lenient mode runs without one).

4 On the wire

One transport: Gen2+ JSON-RPC 2.0 over HTTP on port 80. Turn on Debug Mode → Print to watch each call in the Lua output window (the method and path only — never the body, never the password):

PurposeRPC
DetectGET /rpc/Shelly.GetDeviceInfo
ControlPOST /rpc — Cover.Open / Cover.Close / Cover.Stop / Cover.GoToPosition{pos} / Cover.Calibrate
StatusPOST /rpc — Cover.GetStatus → state, current_pos, pos_control, errors[]

State is refreshed by polling (Poll Interval (s)) and after every action — the same proven transport the generic IntegrateIT Shelly driver uses. The Gen2 outbound-WebSocket NotifyStatus push is a deliberate non-goal in this version; a shorter poll interval is the latency knob. Any response marks the device online; a transport failure (no response) marks it offline and fires Went Offline. A JSON-RPC error object in a control reply (for example, a Go To Position on an uncalibrated cover) is surfaced on the Status line and in Last Error rather than silently dropped. If a device ever answers HTTP 429 with a Retry-After, the driver waits out that window before issuing another request — it never hammers a rate-limited device.

Authentication. Shelly ships with auth off — the fully exercised default. Gen2+ uses RFC7616 SHA-256 digest, which needs the controller's OS crypto (C4:Hash) and the 401-challenge headers; that primitive is not present in the offline simulator, so the driver does not synthesize a digest header in this version. A 401 therefore reports Auth required: Gen2+ digest needs controller OS crypto (verified on hardware) — unconditionally, even where the controller does expose crypto — rather than faking an unexercised hash path or wrongly blaming your credentials. Until digest ships, leave an auth-enabled device's auth off on a trusted LAN.

Three ways these wire into Composer programming:

  • **When *Motion Stopped* fires → read POSITION.** Because the event follows a confirmed status read and lands after the final position, the next program step sees where the cover actually came to rest.
  • **When *Obstruction Detected* fires → notify and hold.** The device raised a safety fault (LAST_ERROR carries the token) — surface it rather than re-driving into an obstruction.
  • On a Good Night event → Go To Position 0 (or Close). One Control4 event closes the cover; POSITION / COVER_STATE confirm the result. If the cover is uncalibrated, Calibration Needed fires instead of a silent no-op.

Control actions are gated by the license: under Strict enforcement an unlicensed controller issues no control request at all, while status polling keeps running (watching your own cover is not a licensed feature). The default Lenient mode allows commissioning while License Status carries the nag.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of Shelly's published local Cover API (Gen2 JSON-RPC, documented at shelly-api-docs.shelly.cloud). It does not bundle another vendor's runtime, source code, brand assets, trial system, or license. Shelly is a trademark of Allterco Robotics; IntegrateIT is not affiliated with Shelly or Allterco, and this driver is not a Shelly product.

The driver talks only to the Shelly device on your LAN — it never contacts Shelly Cloud, and the Integrator/Cloud APIs (which require issued credentials) are intentionally unsupported. Nothing about your project leaves the controller. The device Password lives only in the driver's property store, is sent only to the local device, and is never written to the Control4 log or the Print Configuration output. The Allow Non-LAN Address gate defaults to No, so the driver cannot be pointed at an arbitrary internet host by accident.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all cover control until the Ops Portal has minted and validated a key for that controller; status polling continues either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.
