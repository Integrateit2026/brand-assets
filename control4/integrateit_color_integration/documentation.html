1 Start here

IntegrateIT Color Integration is a headless color engine for a Control4 project. You hand it a color in whichever form you have it — an #RRGGBB hex from a designer, an h,s,v triple from a picker, a Kelvin number from a lighting spec, or raw CIE x,y from a photometric report — and it normalizes that to the two values the Control4 light color model actually carries: a CIE 1931 chromaticity (COLOR_X, COLOR_Y) and a mode (Full Color or Color Temperature). Alongside those it publishes a Kelvin readout, a display hex, and hue/saturation, so a keypad label, a touchscreen tile, and a fixture command can all be driven from one source of truth. Every colorimetric constant is drawn from public standards literature — the sRGB primaries and companding of IEC 61966-2-1, the CIE 1931 standard observer, the published cubic fit of the Planckian/daylight locus, McCamy's CCT approximation, and the Rec.2020 primaries — not from any other vendor's driver.

This driver does not switch, dim, or command a fixture. It computes a color mapping and publishes it as variables and events; your programming reads those and issues the fixture's own color command. Nothing lights up until you wire that last step.
Ready for controlled commissioning. The package, the LuaJIT runtime, the colorimetry (sRGB↔XYZ, Kelvin↔xy, McCamy, gamut projection, mired ramps), the clamp and transition behavior, the license gate, persistence, and this documentation pass automated QA. A qualified dealer must still commission against a real color-capable fixture on the target controller and confirm the published mapping drives that fixture as intended — no per-fixture white-point or LED-bin calibration is applied.

What you get

  • Four input forms — RGB hex, HSV, Kelvin, or CIE 1931 xy — normalized to one canonical color
  • The Control4 light color parameters published as variables: COLOR_X / COLOR_Y chromaticity plus a Full Color or Color Temperature mode
  • Gamut mapping into sRGB, a wide (Rec.2020-style) triangle, or Clamp Only, with out-of-gamut requests projected to the nearest reachable point instead of dropped
  • A configurable Kelvin floor and ceiling so a fixture is never asked for a white it cannot make
  • Bounded transitions (max 120 published steps) that ramp color-temperature pairs in mired so the fade reads even, and everything else linearly in xy
  • Warmer / Cooler Kelvin nudges for color-temperature scenes
  • The last applied color persisted across a controller reboot and republished silently at boot
  • MAC-locked IntegrateIT licensing with lenient or strict enforcement

2 What the engine carries

The engine carries chromaticity, not brightness, and it never invents a color it cannot produce.

  • COLOR_RGB is the brightest RGB with the published chromaticity — a readout for labels and tiles, not a light level. Keep level on your dimmer; feeding COLOR_RGB to a load as a brightness would wash the color out.
  • A request the configuration cannot reach is moved, never rejected. A chromaticity outside the selected gamut is projected to the closest point on the gamut boundary; a Kelvin outside Minimum Kelvin…Maximum Kelvin is pulled to the nearest end. Either way the driver publishes the nearest color it can actually make and raises Color Clamped with COLOR_CLAMPED = 1, so programming knows the request was moved.
  • COLOR_KELVIN is exact for a Kelvin input and approximated for every other input, derived from the mapped chromaticity by McCamy's fit. Round-tripping a Kelvin value through xy and back can differ by a few kelvin, and correlated color temperature is only meaningful near the Planckian locus — a saturated blue will report a number, and that number means very little. Anything claiming a precise Kelvin for an arbitrary color would be faking it.
  • Unreadable input is a no-op. The driver raises Invalid Color Input, writes the reason to Status, and leaves the published color exactly where it was — a typo in Composer never blanks a lit room.
  • Wide is a generic Rec.2020-style triangle, not a measured profile of your fixture. With real measured primaries, Clamp Only plus your own programming may map more faithfully.

3 Add and commission

The driver has no connections and no Navigator tile — everything happens through properties, variables, and events.

  1. Add IntegrateIT Color Integration to a room.
  2. Set Color Input Mode to the form you will write colors in, and put the first color in Color Input: - RGB Hex — #FF8C42 (the leading # is optional) - HSV — 24,74,100 (hue 0-360, saturation 0-100, value 0-100) - Kelvin — 2700 (a trailing K is accepted) - CIE xy — 0.4578,0.4101
  3. Set Gamut to the triangle your fixtures live in. sRGB suits most LED tape and RGB fixtures; Wide uses Rec.2020-style primaries for wide-gamut engines; Clamp Only skips the triangle and holds x and y on the CIE simplex.
  4. Set Minimum Kelvin / Maximum Kelvin to what the fixture can actually produce. Tunable-white tape is often 2200-6500K; a fixed-white fixture should have both ends set near its rating. Invert the two by accident and the driver swaps them rather than clamping every request onto one value.
  5. Set Transition Time (ms) and Transition Step (ms). 1000 ms in 200 ms steps is a good default — five published steps per fade. The driver lengthens the step interval itself if your numbers would ask for more than 120 steps.
  6. Leave Apply On Input Change on Yes while you commission so every edit to Color Input applies immediately. Set it to No when programming should own the timing and call Apply Color itself.
  7. Fire Apply Color, then confirm Current Mapping fills in and COLOR_X / COLOR_Y / COLOR_MODE update. Wire your fixture's color command to the Color Applied event and watch the light follow.

4 The mapping pipeline

Every apply runs the same five stages; understanding them explains any clamp or fade you see in Debug.

  1. Parse. The input string is read in the selected mode. Hex and HSV become 0-1 RGB; a Kelvin value is clamped into Minimum Kelvin…Maximum Kelvin; CIE xy is taken as written.
  2. To xy. RGB is inverse-companded to linear light, multiplied through the sRGB/D65 matrix into CIE XYZ, and normalized to x = X/(X+Y+Z), y = Y/(X+Y+Z). A Kelvin value goes straight to xy on the locus fit. Pure black has no chromaticity, so it reports the D65 white point rather than dividing by zero.
  3. Gamut. The point is tested against the three primaries. If it is outside, it is projected to the closest point on the nearest triangle edge — the shortest move to a producible color — and COLOR_CLAMPED is set with Color Clamped. Clamp Only instead holds the point on the CIE simplex (x ≥ 0, y ≥ 0, x + y ≤ 1); a coordinate past x + y = 1 is projected onto that edge, because it is not a real color at all.
  4. Mode and Kelvin. A Kelvin input publishes Color Temperature mode and its (clamped) Kelvin. Hex, HSV, and xy inputs publish Full Color mode with a Kelvin readout derived from the mapped chromaticity via McCamy.
  5. Transition. Two color-temperature endpoints interpolate in mired (reciprocal megakelvin), the scale color temperature is even on, so a 2700K → 6500K fade does not bunch at the cool end. Every other pair interpolates linearly in xy. The final step always publishes the exact target, never an interpolation of it.

Editing Gamut, Minimum Kelvin, or Maximum Kelvin re-maps the already-published color through the new constraints instantly and without a fade. If the re-map lands on the same color, nothing is published and no event fires. A live edit made mid-fade re-aims both ramp endpoints through the new constraints rather than abandoning the fade, so the ramp still delivers the requested color.

Recipes:

  • Warm scene: set Color Input Mode to Kelvin, write 2700 to Color Input, fire Apply Color. On Color Applied, read COLOR_X / COLOR_Y / COLOR_MODE / COLOR_KELVIN and send them with the fixture's own color command.
  • Keypad warmer/cooler: bind two keypad buttons to the Warmer and Cooler actions and label the keypad from COLOR_KELVIN. Each press nudges by Kelvin Nudge Step and re-fires Color Applied.
  • Touchscreen swatch: with Apply On Input Change at Yes and mode RGB Hex, write the picked hex to Color Input; the tile reflects COLOR_RGB and a "not reachable" badge can key off COLOR_CLAMPED.

Every control path is gated by the license: under Strict enforcement an unlicensed controller publishes no color at all. Lenient mode allows commissioning while License Status carries the nag.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation. The colorimetry is built entirely from public standards literature (sRGB / IEC 61966-2-1, the CIE 1931 observer, the published Kelvin-to-xy cubic, McCamy's CCT approximation, Rec.2020 primaries); the property, variable, action, and event names are IntegrateIT's own. It does not bundle another vendor's runtime, source code, brand assets, or license. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

The color engine is pure on-controller computation: your colors, mapping, and project data never leave the controller. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below; the license key is never written to the log.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks every color control path until the Ops Portal has minted and validated a key for that controller. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

  • `remapCurrent` (the live Gamut / Kelvin-bound edit) is a control path — it republishes the color and fires `Color Applied` — but was NOT gated. A Strict-unlicensed controller could be driven from the Gamut dropdown even though `Apply Color` was correctly blocked. Now gated.
  • A live Gamut / Kelvin edit DURING a fade cancelled the ramp and stranded the light on whatever intermediate color it had reached; the requested color never arrived. The ramp is now re-aimed through the new constraints (both endpoints re-mapped, so every remaining step stays inside the new triangle) and runs to completion.
  • A re-map that landed on the already-published color wrote `COLOR_CLAMPED = 0`, so an unrelated Kelvin-bound nudge silently cleared a clamp flag that was still true and handed programming a false "in gamut". The no-op path is now genuinely silent, as documented.
  • The boot restore republished the persisted color verbatim. If the gamut or Kelvin window was narrowed while the controller was down, that put an unreachable chromaticity on the variables and reported it as in gamut. The restore is now re-mapped through the current constraints, with the clamp state recorded silently (still no events).
  • `Clamp Only` clamped x and y independently and so accepted impossible chromaticities: x + y > 1 implies a negative z, and (0.9, 0.9) sailed through unflagged into the XYZ->RGB matrix, which fabricated a hex for a color that does not exist. The point is now projected onto the CIE simplex edge (x + y = 1) and flagged as clamped.
