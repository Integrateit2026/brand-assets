1 Start here

IntegrateIT Hue Button turns one Philips Hue button accessory into Control4 programming triggers over the bridge's local CLIP API v2 (the on-bridge REST API rooted at /clip/v2, documented at developers.meethue.com). A Hue dimmer switch, smart button, wall switch module, or tap dial appears on the bridge as one or more button services — and, on the dial, a relative_rotary service. This driver binds to one accessory, listens on the bridge's /eventstream/clip/v2 Server-Sent-Events stream, and relays every press and every turn of the ring into Composer as an event. There is no cloud hop and no Hue account: the driver talks straight to the bridge on the LAN over HTTPS.

Events only. This driver reads. It never writes to the bridge and it declares no Control4 proxy — there is nothing here to put on a Navigator page, and it cannot turn on a light, set a level, or recall a scene. It is a trigger source for Programming. To control Hue from Control4, add IntegrateIT Hue Bridge alongside it.
The bridge presents a self-signed certificate. The driver connects over HTTPS with CA-chain verification disabled and pins trust to the bridge's LAN address plus the application key — Signify's documented posture for local integration. A non-LAN address is refused unless Allow WAN Bridge is set to Yes.
Ready for controlled commissioning. The package, Lua 5.1 runtime, link-button pairing, CLIP v2 parsing (button, relative_rotary, device_power), eventstream framing and reconnect, the read-path-never-fires rule, baseline silence, the LAN guard, the license gate, and this documentation pass automated QA against the Control4 API simulator (hardwareStatus: simulation-verified). A qualified dealer must still complete a fresh install and an observed press test against a real Hue Bridge and a real accessory on the target controller — this release is not bench-tested on physical hardware.

What you get

  • Per-button events on buttons 1-4 for the whole documented CLIP v2 vocabulary — Initial Press, Repeat, Long Press, Short Release, Long Release, Double Short Release
  • Long Press is named as of 0.2.0, so a hold is a first-class trigger: bind the ramp to Long Press and stop it on Long Release instead of decoding LAST_EVENT inside a catch-all branch
  • A catch-all Button Event that fires for every button report, including any value with no named event of its own, with LAST_BUTTON and LAST_EVENT carrying the detail
  • Rotary Clockwise / Rotary Counterclockwise for a tap dial's ring, with LAST_ROTARY_STEPS and LAST_ROTARY_DIRECTION
  • Battery Low plus BATTERY_LEVEL and BATTERY_STATE, read from the accessory's device_power service
  • Went Online / Went Offline and Event Stream Reconnected with a BRIDGE_ONLINE variable, so a project can see exactly when the driver was blind
  • Link-button pairing built in, and List Accessories to find the accessory's resource id
  • LAN-only destination guard enforced at the transport itself, an application key that is never written to the log, and MAC-locked IntegrateIT licensing

2 The event contract

This is the part to read before you program against it. A button press is an event, not a state — and there is exactly one place it exists.

  • Presses live only on the eventstream. The driver holds GET /eventstream/clip/v2 open and fires the moment a report arrives. That is the whole event source. There is no poll behind it, because there is nothing for a poll to find.
  • A press made while the stream is down is gone. Permanently. Not delayed, not queued, not recovered on reconnect. The driver requests no replay — it never sends a Last-Event-ID header — so nothing is re-delivered when the stream comes back.
  • No read will ever invent one. The bridge does keep the last button_report on each button service, and the driver does read it during enumeration. It cannot tell you whether that press landed inside your outage or a week ago. Firing an event from it would be inventing a press Control4 never observed, so the read path fires no button event, ever — not the named one, not the catch-all. Program accordingly: anything built on presses must tolerate outage loss. A press is a trigger, never a system of record.
  • You can see the blind window. When the stream closes, Device Status reads presses made now are lost and the driver reconnects with bounded backoff (5 s, doubling to a 60 s cap). The first live byte afterwards fires Event Stream Reconnected. Everything between the close and that event was unobservable.
  • A stream close is not an outage. A healthy bridge closes long-lived connections. The stream dropping never fires Went Offline — only a REST read that gets no answer at all does, so the reachability signal stays worth trusting.
  • Unknown-to-known adoption is silent. The first reachability reading, the first battery reading, and every stored button_report are adopted without firing anything. Only a real change from an already-known value fires. A controller reboot re-primes the driver in silence rather than replaying a day it did not witness.
  • The vocabulary is relayed, not translated. Six button_report.event values have named per-button events: initial_press, repeat, long_press, short_release, long_release, double_short_release. Any other value the bridge reports arrives as Button Event with LAST_EVENT holding the literal string — no named event is invented for a value this build cannot account for, and none is dropped either. A named value fires both its own event and the catch-all, so a reaction that branches on LAST_EVENT still sees everything.
  • Nothing is synthesized in either direction. Which of those six values your accessory actually sends is the accessory's and the bridge firmware's behavior, not the driver's. An older switch may tick repeat the whole time it is held and never report long_press at all. The driver fires what arrives and never manufactures the other one for you — see the ramp recipe below for programming that works from whichever your hardware sends.
  • Scope is one accessory. A frame from any other device on the same bridge is ignored. That is what makes LAST_BUTTON unambiguous.

3 Wire and commission

  1. Add the switch, button, or dial to the Hue app first. Until the accessory is on the bridge it owns no button service and there is nothing to bind to.
  2. Reserve the bridge's IP address in your router's DHCP table so it never changes. Discover Bridges browses _hue._tcp on the LAN and prints what it finds.
  3. Add IntegrateIT Hue Button to a room and enter Bridge IP Address.
  4. Pair. Press the round link button on the bridge, then run Pair (Link Button) within ~30 s. The driver POSTs the claim (the first attempt returns Hue error 101 until the button is pressed), stores the returned key in the password-typed Application Key property, and connects. You never handle the key yourself.
  5. Run List Accessories with Debug Mode = Print. It prints every bridge device that owns a button service, with its name, its device id, its button count, and whether it has a rotary dial.
  6. Paste the accessory's device id into Accessory Device ID. (A button, rotary, or power service id of the same accessory is accepted too — they sit next to each other in that listing.) Bound Accessory then reads back the name, button count, dial, and battery.
  7. Optionally enter a License Key. The default Lenient (recommended) mode commissions without one.
  8. Prove it. With Debug on, press button 1 on the physical accessory and watch Status change to Button 1 short_release — then add a Programming reaction to Button 1 Short Release and press it again.
One accessory per driver instance. Add a second instance for a second switch; that is what keeps each accessory's events unambiguous in Programming.

4 Protocol on the wire

Every request is JSON over HTTPS to https://<ip>. The application key rides in the hue-application-key header — never in the URL — so no log line can contain it (Debug shows the method and sub-path only).

PurposeRequestWhat the driver takes from it
Pair (link button)POST /api (no key){"devicetype":"iit_c4#…","generateclientkey":true} → [{"success":{"username":"…"}}] or [{"error":{"type":101}}]
Accessory identityGET /clip/v2/resource/devicemetadata.name, product_data.product_name
ButtonsGET /clip/v2/resource/buttonowner.rid, metadata.control_id — never button.button_report
DialGET /clip/v2/resource/relative_rotaryowner.rid
BatteryGET /clip/v2/resource/device_powerpower_state.battery_level, power_state.battery_state
Live eventsGET /eventstream/clip/v2 (Accept: text/event-stream)long-lived SSE update frames — the only source of presses

A live button frame carries button.button_report.event (or the deprecated button.last_event) with one of initial_press, repeat, long_press, short_release, long_release, double_short_release. A dial frame carries relative_rotary.rotary_report.rotation with direction (clock_wise / counter_clock_wise), steps, and duration. Battery carries battery_state (normal / low / critical) and battery_level 0-100. Battery Low derives from that enum on a change from an already-known state — this driver invents no percentage threshold of its own.

Update frames carry only what changed, so they do not include metadata.control_id. That is why the driver enumerates first: it learns which service id is button 1 versus button 4. A press arriving on a service it has not enumerated still fires Button Event (with LAST_BUTTON showing ? and a short id) and schedules one enumeration so the next press can name its button.

Replies the driver acts on: 200 on a read; 401/403 means the application key was rejected (re-pair); code 0 is no response (offline). SSE frames are parsed tolerant of arbitrary chunk boundaries, keep-alive comment lines, and CRLF or LF line endings — bytes accumulate and only a fully terminated frame is applied. Names you type in the Hue app are treated as text, not as structure: a light called Sconce ] or a room called Nook {1 cannot cut a frame short or move a press onto the wrong accessory.

Exactly one eventstream is live at a time. Reconnect Event Stream and any change to Bridge IP Address, Application Key, or Allow WAN Bridge retire the current one — a superseded stream stops being an event source immediately, even if it is still physically open, so a socket to the address you just moved away from can never keep relaying presses or repainting BRIDGE_ONLINE behind the LAN guard.

  • When Button 1 Short Release fires → toggle the kitchen lights. The simplest wiring, and the one most Hue dimmers are bought for.
  • When Button Event fires → branch on LAST_BUTTON and LAST_EVENT. One reaction handles a whole four-button switch, and it is the only path that also sees event values with no named event of their own.
  • When Button 1 Long Press fires → start a ramp, and stop it on Button 1 Long Release. The full recipe is the next section.
  • When Rotary Clockwise fires → ramp the room up by LAST_ROTARY_STEPS. Pair it with Rotary Counterclockwise for a real dial.
  • When Went Offline or Event Stream Reconnected fires → log it. If a press "did not work", this pair tells you whether the driver was even listening.

Composer event delivery is the licensed product, so every event above — including Went Online/Offline — is withheld under Strict enforcement on an unlicensed controller, along with the LAST_* detail variables. The reads keep running and the state mirrors (BRIDGE_ONLINE, BATTERY_LEVEL, BATTERY_STATE) keep tracking, so Status stays honest. Lenient (recommended) fires everything and keeps License Status carrying the nag.

6 Hold a button to ramp

This is what naming Long Press was for. Here is the event flow of one hold — the driver relays each step the moment it arrives and adds nothing of its own. Which steps a given accessory actually sends is its behavior, not the driver's, so confirm yours with one long hold before you program against it.

The user doesThe bridge reportsThe driver fires
Presses and holdsinitial_pressButton 1 Initial Press
Keeps holdingrepeat, on the accessory's own repeat_intervalButton 1 Repeat, once per tick
Passes the accessory's long-press thresholdlong_pressButton 1 Long Press
Lets go after a long holdlong_releaseButton 1 Long Release
Lets go before the threshold insteadshort_releaseButton 1 Short Release

Build the ramp on the two ends of the hold rather than on a guess about its length:

  1. When Button 1 Long Press fires — set a Composer boolean variable RAMPING to true, start a repeating Ramp Tick timer at ~300 ms, and start a one-shot Ramp Safety timer at 10 s.
  2. When Ramp Tick expires — if RAMPING is true, raise the light one step and restart the tick.
  3. When Button 1 Long Release fires — set RAMPING to false and stop both timers. The light rests wherever the user let go.
  4. When Ramp Safety expires — set RAMPING to false and stop the tick, unconditionally.
  5. When Button 1 Short Release fires — toggle the light instead. A tap and a hold are now two separate reactions, with no press-timing logic of your own to maintain.
Step 4 is not optional — it is the event contract cashing out. If the eventstream drops while the button is held, the long_release that would have stopped your ramp never arrives and never will: the driver requests no replay, and no read can recover it. Without the safety stop the light ramps to full and stays there. Any loop started by an event needs a stop that does not depend on one.
If your accessory ticks repeat while held and never reports long_press, run the ramp off Button 1 Repeat instead — one step per tick, no timer, no loop left running. That variant cannot be stranded by a dropped stream at all, because there is nothing to stop. Watch Status and LAST_EVENT through a single long hold to see which values your hardware sends.

BRIDGE_ONLINE is the live reachability signal — program against it and the Went Online/Offline events, not against the text property. LAST_BUTTON and LAST_EVENT describe the last press the driver actually observed; they are never written by a read, so if they look stale it is because nothing has been pressed since. Re-pointing the driver — a new Accessory Device ID, or a new bridge — clears all four LAST_* variables back to empty, because every one of them is a statement about the accessory it was bound to.

Print Configuration writes the bridge IP, whether the key is set (its length only, never the value), the WAN flag, the refresh interval, the bound accessory, the eventstream state, and the battery to the Lua output window — and restates that a press made while the stream was down cannot be recovered.

9 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of the published Philips Hue CLIP API v2. It does not bundle another vendor's runtime, source code, brand assets, trial system, or license. Philips Hue and the Hue names are trademarks of Signify; IntegrateIT is not affiliated with Signify, and this driver is not a Philips Hue product. Per the Hue Developer Terms, this integration is not for security or surveillance use: a button press is an automation trigger, and this driver must not be programmed as an intrusion, presence-tracking, or life-safety path.

Nothing leaves the LAN. The driver talks only to the Hue Bridge on your network — no cloud service, no Hue account, no telemetry; accessory activity, project identity, and Control4 credentials are never sent to a device vendor. The LAN guard sits at the transport itself, so every path — including the boot-time enumeration, the refresh heartbeat, pairing, and Test Connection — is refused before a single byte leaves if the configured address is not private. The connection is HTTPS: because the bridge's certificate is self-signed, the driver disables CA-chain verification and pins trust to the bridge's LAN address plus the application key — the transport is still encrypted, and a genuinely broken TLS handshake fails closed (the driver reports the bridge offline and never downgrades to plaintext). The application key lives in the password-typed Application Key property and rides only in the hue-application-key request header, so the driver never logs it — even in Debug Mode, lines show the method and sub-path only, and Print Configuration prints the key's length, not its value.

Lenient (recommended) mode allows commissioning without an activated key and keeps License Status visible. Strict mode withholds every Composer event and every LAST_* detail variable until the Ops Portal has minted and validated a key for this controller; the reads, the eventstream, pairing, and the state mirrors keep running either way, so the driver never lies about the bridge to make a point about licensing. Installing this package does not itself mint or activate a controller license. Self-update is check-and-stage, never silent: with Automatic Update Check on Daily the driver reads the version manifest, reports a newer build in Update Available, and only downloads the .c4z into the controller's driver store when you run Download & Stage Update — you still apply it from Composer. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

A named value fires its own event and the catch-all, so long_press now behaves exactly the way short_release already did — every existing "when Button Event fires, branch on LAST_EVENT" reaction keeps seeing every hold. A regression case runs both values through the same button and demands the same shape out of each, rather than asserting the equivalence in a comment.
  • The new ids are appended, not interleaved. 39-42 sit after Event Stream Reconnected rather than slotting into each button's block, so every id shipped in 0.1.0 keeps the number Composer already bound programming to — grouping them would have renumbered 24 live events. The manifest's ascending-id-in-array-order convention holds either way.
  • The read path still cannot fire one. Naming long_press widened what the LIVE eventstream may deliver and changed nothing about the REST path: ApplyReadObject never consults objButtonEvent, so there is no code path from a REST body to a button event at all. A new case hands the driver a stored long_press button_report on all four buttons across a boot enumeration, a Refresh Accessory, and a List Accessories, and demands silence — the no-fabrication law re-proven for the value that just became nameable. Baseline silence, the outage-loss contract, and the no-Last-Event-ID replay refusal are untouched.
  • The named range did not widen either. control_id 5 and up, and any service not yet enumerated, still reach Programming through the catch-all only — holds included. Pinned with a five-button fixture and an explicit "no named Long Press was borrowed from button 1-4" assertion.
  • Strict enforcement covers the new events, because the license gate in FireButton sits above the named/catch-all split. A case asserts it under Strict with no key instead of trusting the construction: no Button n Long Press, no catch-all, no LAST_* detail, while BRIDGE_ONLINE and the battery mirrors keep telling the truth.
  • The XML invariant flipped, deliberately. 0.1.0's suite pinned that no "Long Press" event was declared anywhere; that assertion is now its opposite, backed by a count of exactly 24 per-button events (4 buttons x 6 values) so "and nothing invented on top" stays enforced. The only other edit is the case that used long_press as its example of an unnamed value — it now uses a value this build genuinely cannot account for, keeping that contract covered. Every other 0.1.0 case is byte-identical: run the 0.1.0 suite against this build and 406 of its 408 checks still pass, the two failures being precisely the assertions this decision reversed.
  • Documentation: the vocabulary reads as six throughout, and a new Hold a button to ramp section walks the real flow of one hold — initial_press on touch, repeat ticks while held, long_press at the accessory's threshold, long_release on lift — into a five-step Composer recipe. It carries the two honesty notes the feature needs. The recipe's safety stop is mandatory, not stylistic: a stream drop mid-hold means the long_release that would have ended the loop is lost permanently, so a light ramping on a lost stop event ramps to full and stays there. And which of repeat and long_press a given accessory emits is the accessory's and the firmware's behavior — the driver relays what arrives and synthesizes neither from the other, so the recipe names the Repeat-driven variant for hardware that never reports a hold.

v0.1.02026-07-27
  • Initial release candidate: one Philips Hue button accessory — dimmer switch, smart button, wall switch module, or tap dial including its rotary ring — relayed into Control4 programming over the bridge's local CLIP API v2 (HTTPS, developers.meethue.com). Clean-room original engineering, transport ported from the shipped IntegrateIT Hue Bridge driver.
  • Link-button pairing built in: Pair (Link Button) POSTs /api with generateclientkey, handles the error-101 "press the button" round-trip, and stores the returned application key in the password-typed property — never printed, never logged (it rides only in the hue-application-key header).
  • Accessory binding: List Accessories enumerates every bridge device that owns a button service and prints its name, device id, button count, and whether it has a dial. Paste the id into Accessory Device ID (a button / rotary / power service id of the same accessory resolves to its owner) and the binding persists across a reboot; changing it clears battery, identity, and every LAST_* event detail back to unknown (the bridge reachability baseline is deliberately kept — the bridge did not change, and dropping it would swallow the next genuine Went Offline).
  • Per-button events for the documented CLIP v2 button_report.event vocabulary — initial_press, repeat, short_release, long_release, double_short_release — on metadata.control_id 1-4, plus a catch-all Button Event that fires for every button report and carries LAST_BUTTON / LAST_EVENT. An event value outside the five named ones (the enum also carries long_press in third-party mirrors of the login-gated Signify reference) reaches Composer through the catch-all with the literal string in LAST_EVENT — never renamed into something this build cannot account for, never dropped.
  • Tap dial ring: Rotary Clockwise / Rotary Counterclockwise from relative_rotary.rotary_report.rotation, with LAST_ROTARY_DIRECTION and LAST_ROTARY_STEPS carrying the raw direction and steps. An unrecognized direction is logged, not guessed at.
  • Battery from device_power: BATTERY_LEVEL and BATTERY_STATE mirrors plus a Battery Low event derived from the official battery_state enum (normal / low / critical) on a change from an already-known state — no invented percentage threshold.
  • THE EVENT CONTRACT, enforced in code and stated plainly in the docs: a button press is transient and exists only on /eventstream/clip/v2. The driver sends no Last-Event-ID, so it requests no replay; and the REST read path — which is handed each button's stored button_report on every enumeration — has no code path to C4:FireEvent for a button at all. A press made while the stream is down is lost permanently, and nothing here will fabricate one from a stored report that cannot say when it happened. Programming built on presses must tolerate that loss. BRIDGE_ONLINE, Went Online / Went Offline, and Event Stream Reconnected exist so a project can see the blind window; a stream close alone never declares the bridge offline (that verdict belongs to a REST read that gets no answer).
  • Baseline silence throughout: the first reachability observation, the first battery reading, and every replayed or stored button/rotary report are adopted without firing anything. Only a real change from an already-known value fires.
  • Events-only by construction: the package declares no Control4 proxy and ships combo: true — there is no Navigator surface, because this driver cannot drive the switch it listens to. Pair it with IntegrateIT Hue Bridge to control lights, groups, and scenes.
  • LAN guard at the transport chokepoint (HueRequest and OpenEventStream both re-run it), so no caller — including the boot-time enumeration, the refresh heartbeat, pairing, and Test Connection — can put the application key on a packet bound off-LAN. Refusals are local, named, and carry the reason.
  • Frame discipline, because a dropped frame is a dropped press: the CLIP JSON scanner is string-aware, so brackets and braces inside a customer-typed Hue name (Sconce ], Nook {1) are text and cannot truncate a payload, hide the resources behind them, or merge two objects into one; SSE framing accepts CRLF as well as LF; and exactly one eventstream is ever believed at a time — Reconnect Event Stream and any bridge-identity change retire the current one by generation, so a superseded socket can neither double-deliver a press nor keep repainting BRIDGE_ONLINE from an address the LAN guard has started refusing.
  • Honest TLS trust model: the bridge is self-signed, so the driver connects over HTTPS with CA verification disabled and pins trust to the LAN address + application key; a broken TLS handshake fails closed and never downgrades to plaintext. Bounded eventstream reconnect (5s → 60s cap) and MAC-locked IntegrateIT licensing on every event delivery.
  • Hue Developer Terms: this is an automation trigger source, explicitly not for security or surveillance use.
  • Known limits: one accessory per instance; named events cover control_id 1-4; no motion/contact sensors, no lights/groups/scenes, no entertainment API; on an OS build without C4:url streaming there is no eventstream and therefore no events at all (the driver says so in Device Status rather than pretending to listen).
