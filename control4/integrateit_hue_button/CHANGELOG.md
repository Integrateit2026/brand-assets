# Changelog — IntegrateIT Hue Button

## [0.2.0] - 2026-07-29
- **Button 1-4 Long Press are now named events** (ids 39-42). `long_press` is the sixth and final value in the CLIP v2 `button.button_report.event` vocabulary; the enum's completeness was established during the 0.1.0 verify wave against two independent mirrors of Signify's login-gated reference — openHAB's `ButtonEventType` and the OpenHue OpenAPI description of the `button` service. 0.1.0 named the other five and deliberately let `long_press` ride the catch-all **Button Event** with `LAST_EVENT` carrying the literal string, because minting a Control4 event for a value confirmed only in third-party mirrors is exactly the invention this driver's hand-written event map exists to prevent. Daniel approved naming it, so the four events are declared and fired.
- **Nothing in the dispatch changed to do it, and that is the point.** The feature is four new rows in `BUTTON_EVENT`; `FireButton` was not touched. A named value fires its own event *and* the catch-all, so `long_press` now behaves exactly the way `short_release` already did — every existing "when **Button Event** fires, branch on `LAST_EVENT`" reaction keeps seeing every hold. A regression case runs both values through the same button and demands the same shape out of each, rather than asserting the equivalence in a comment.
- **The new ids are appended, not interleaved.** 39-42 sit after **Event Stream Reconnected** rather than slotting into each button's block, so every id shipped in 0.1.0 keeps the number Composer already bound programming to — grouping them would have renumbered 24 live events. The manifest's ascending-id-in-array-order convention holds either way.
- **The read path still cannot fire one.** Naming `long_press` widened what the LIVE eventstream may deliver and changed nothing about the REST path: `ApplyReadObject` never consults `objButtonEvent`, so there is no code path from a REST body to a button event at all. A new case hands the driver a stored `long_press` `button_report` on all four buttons across a boot enumeration, a Refresh Accessory, and a List Accessories, and demands silence — the no-fabrication law re-proven for the value that just became nameable. Baseline silence, the outage-loss contract, and the no-`Last-Event-ID` replay refusal are untouched.
- **The named range did not widen either.** `control_id` 5 and up, and any service not yet enumerated, still reach Programming through the catch-all only — holds included. Pinned with a five-button fixture and an explicit "no named Long Press was borrowed from button 1-4" assertion.
- **Strict enforcement covers the new events**, because the license gate in `FireButton` sits above the named/catch-all split. A case asserts it under `Strict` with no key instead of trusting the construction: no **Button n Long Press**, no catch-all, no `LAST_*` detail, while `BRIDGE_ONLINE` and the battery mirrors keep telling the truth.
- **The XML invariant flipped, deliberately.** 0.1.0's suite pinned that no "Long Press" event was declared *anywhere*; that assertion is now its opposite, backed by a count of exactly 24 per-button events (4 buttons x 6 values) so "and nothing invented on top" stays enforced. The only other edit is the case that used `long_press` as its example of an *unnamed* value — it now uses a value this build genuinely cannot account for, keeping that contract covered. Every other 0.1.0 case is byte-identical: run the 0.1.0 suite against this build and 406 of its 408 checks still pass, the two failures being precisely the assertions this decision reversed.
- **Documentation**: the vocabulary reads as six throughout, and a new **Hold a button to ramp** section walks the real flow of one hold — `initial_press` on touch, `repeat` ticks while held, `long_press` at the accessory's threshold, `long_release` on lift — into a five-step Composer recipe. It carries the two honesty notes the feature needs. The recipe's safety stop is mandatory, not stylistic: a stream drop mid-hold means the `long_release` that would have ended the loop is lost permanently, so a light ramping on a lost stop event ramps to full and stays there. And which of `repeat` and `long_press` a given accessory emits is the accessory's and the firmware's behavior — the driver relays what arrives and synthesizes neither from the other, so the recipe names the `Repeat`-driven variant for hardware that never reports a hold.
- `semver` 0.2.0, `xmlVersion` 2. No transport, parser, LAN-guard, key-hygiene, SSE-framing, or stream-generation change: the quote-aware CLIP scanner, CRLF framing, the single-live-stream generation guard, and the header-only application key are exactly as the 0.1.0 verify wave left them.

## [0.1.0] - 2026-07-27
- Initial release candidate: one Philips Hue button accessory — dimmer switch, smart button, wall switch module, or tap dial including its rotary ring — relayed into Control4 programming over the bridge's local CLIP API v2 (HTTPS, developers.meethue.com). Clean-room original engineering, transport ported from the shipped IntegrateIT Hue Bridge driver.
- Link-button pairing built in: Pair (Link Button) POSTs `/api` with `generateclientkey`, handles the error-101 "press the button" round-trip, and stores the returned application key in the password-typed property — never printed, never logged (it rides only in the `hue-application-key` header).
- Accessory binding: List Accessories enumerates every bridge device that owns a `button` service and prints its name, device id, button count, and whether it has a dial. Paste the id into **Accessory Device ID** (a button / rotary / power service id of the same accessory resolves to its owner) and the binding persists across a reboot; changing it clears battery, identity, and every `LAST_*` event detail back to unknown (the bridge reachability baseline is deliberately kept — the bridge did not change, and dropping it would swallow the next genuine Went Offline).
- Per-button events for the documented CLIP v2 `button_report.event` vocabulary — `initial_press`, `repeat`, `short_release`, `long_release`, `double_short_release` — on `metadata.control_id` 1-4, plus a catch-all **Button Event** that fires for every button report and carries `LAST_BUTTON` / `LAST_EVENT`. An event value outside the five named ones (the enum also carries `long_press` in third-party mirrors of the login-gated Signify reference) reaches Composer through the catch-all with the literal string in `LAST_EVENT` — never renamed into something this build cannot account for, never dropped.
- Tap dial ring: **Rotary Clockwise** / **Rotary Counterclockwise** from `relative_rotary.rotary_report.rotation`, with `LAST_ROTARY_DIRECTION` and `LAST_ROTARY_STEPS` carrying the raw `direction` and `steps`. An unrecognized direction is logged, not guessed at.
- Battery from `device_power`: `BATTERY_LEVEL` and `BATTERY_STATE` mirrors plus a **Battery Low** event derived from the official `battery_state` enum (`normal` / `low` / `critical`) on a change from an already-known state — no invented percentage threshold.
- THE EVENT CONTRACT, enforced in code and stated plainly in the docs: a button press is transient and exists only on `/eventstream/clip/v2`. The driver sends no `Last-Event-ID`, so it requests no replay; and the REST read path — which is handed each button's stored `button_report` on every enumeration — has **no code path to `C4:FireEvent` for a button at all**. A press made while the stream is down is lost permanently, and nothing here will fabricate one from a stored report that cannot say when it happened. Programming built on presses must tolerate that loss. `BRIDGE_ONLINE`, **Went Online** / **Went Offline**, and **Event Stream Reconnected** exist so a project can see the blind window; a stream close alone never declares the bridge offline (that verdict belongs to a REST read that gets no answer).
- Baseline silence throughout: the first reachability observation, the first battery reading, and every replayed or stored button/rotary report are adopted without firing anything. Only a real change from an already-known value fires.
- Events-only by construction: the package declares **no Control4 proxy** and ships `combo: true` — there is no Navigator surface, because this driver cannot drive the switch it listens to. Pair it with IntegrateIT Hue Bridge to control lights, groups, and scenes.
- LAN guard at the transport chokepoint (`HueRequest` and `OpenEventStream` both re-run it), so no caller — including the boot-time enumeration, the refresh heartbeat, pairing, and Test Connection — can put the application key on a packet bound off-LAN. Refusals are local, named, and carry the reason.
- Frame discipline, because a dropped frame is a dropped press: the CLIP JSON scanner is string-aware, so brackets and braces inside a customer-typed Hue name (`Sconce ]`, `Nook {1`) are text and cannot truncate a payload, hide the resources behind them, or merge two objects into one; SSE framing accepts `CRLF` as well as `LF`; and exactly one eventstream is ever believed at a time — Reconnect Event Stream and any bridge-identity change retire the current one by generation, so a superseded socket can neither double-deliver a press nor keep repainting `BRIDGE_ONLINE` from an address the LAN guard has started refusing.
- Honest TLS trust model: the bridge is self-signed, so the driver connects over HTTPS with CA verification disabled and pins trust to the LAN address + application key; a broken TLS handshake fails closed and never downgrades to plaintext. Bounded eventstream reconnect (5s → 60s cap) and MAC-locked IntegrateIT licensing on every event delivery.
- Hue Developer Terms: this is an automation trigger source, explicitly **not** for security or surveillance use.
- Known limits: one accessory per instance; named events cover `control_id` 1-4; no motion/contact sensors, no lights/groups/scenes, no entertainment API; on an OS build without `C4:url` streaming there is no eventstream and therefore no events at all (the driver says so in Device Status rather than pretending to listen).
