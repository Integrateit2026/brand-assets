1 Start here

IntegrateIT Watchdog watches up to six LAN targets you name — a switch, an access point, a head-end server, a rack appliance — decides whether each is up with real hysteresis instead of a single ping, and can cut and restore power to one bound Control4 relay per target when a fault survives a verified recovery. It uses the controller's own network stack: the ping client when this OS build exposes one, otherwise one outbound TCP connect, otherwise one HTTP GET. Nothing is ever written to a watched device — the driver has no command vocabulary for anything it monitors.

This driver can remove mains power from whatever its relay controls. Read Safety boundary before you set any target's Ladder to Cycle Relay. Everything else in the driver is observation and can be commissioned safely at any time.
Ready for controlled commissioning — package, runtime, Control4 surfaces, probe tiers, state machine, suppression, budgets, quiet hours, licensing and persistence all pass automated QA in the simulator. Every hardware behavior described here is simulation-verified, never bench-tested: a dealer must still do a fresh install and an observed relay cycle on the real controller.

What you get

  • Six declared targets on one schedule, each with a friendly name used in every event
  • N-of-M hysteresis: Fail Streak consecutive misses to call Down, two clean probes to call Up
  • Declared dependency suppression — a target behind a Down upstream goes Suppressed and stays quiet
  • Flap classification as a fault of its own: three transitions inside the window is Flapping, not Down
  • A first-fault snapshot (target states, upstream, probe class, one optional context device's variables) written into a persistent audit ring that survives a reboot
  • Verified recovery, then a per-target ladder — Observe, Fire Event, Cycle Relay — advanced only by a failed recovery, under hard daily budgets that survive a restart, quiet hours and a maintenance hold that can release itself
  • Test Relay 1-4 commissioning actions that walk the whole safety chain minus the fault requirement, so you prove the wiring before trusting the automation
  • Eleven events, twelve WD_ variables (one per target), five live Navigator state icons

2 What a probe can and cannot prove

A probe answers exactly one question: did something at that address answer this probe?

  • A hit means something accepted the connection (or the ping, or served an HTTP status) — not that the device is healthy. A wedged server still completes a TCP handshake; a switch with a dead uplink still answers on its management address. This reports reachability, never health.
  • A miss means nothing answered inside the probe window — not that the device is off. A firewall rule, a closed port, a saturated link or a controller network problem produce the same silence, which is precisely why a single miss changes nothing here.

From those two facts and your thresholds it builds every verdict, and publishes nothing it cannot defend:

  • It never diagnoses and never discovers: no cause is offered or invented, and Target N Upstream is a declaration you make — a wrong one produces wrong suppression the driver cannot detect.
  • It never reports latency in milliseconds — DriverWorks exposes no monotonic clock accessor — so a probe is classed fast, slow or none and the snapshot records the class, not a number.
  • It cannot announce, email, text or push. No DriverWorks API gives a driver those channels; notification is Composer programming on the events below, and claiming otherwise would be faking it.
  • A relay confirmation proves one thing: the relay proxy reported the change this driver just wrote. It is not proof the load lost power. A relay that has never reported its state yields no claim in either direction — no window is armed and Relay Unconfirmed can never fire for it, because the absence of a report is not evidence of a failed write. That latch lives in RAM and is re-learned after every reboot, so a fresh boot claims nothing until a relay speaks again. Nothing on this path retries, blocks or alters a relay write.
  • It does not persist verdicts. After a reboot every target is Unknown until it is probed again. Two things deliberately DO survive a restart: the audit ring, and the daily cycle budget — a ceiling a reboot resets is not a ceiling, and the reboot in question can be one this driver's own relay caused.

3 Safety boundary

A relay cycle removes power from live equipment. Wire it only to loads that tolerate an abrupt interruption, never to anything with a documented shutdown sequence, and never to life-safety, medical or egress equipment. A qualified installer owns the wiring, the load rating, and any inrush or contactor protection.

Ten conditions must ALL hold before a relay opens. Every refusal names itself in Last Event and the audit ring, and every refusal but one fires Cycle Blocked — the exception is the unlicensed refusal of a manual test, which is recorded rather than announced, below.

#Condition
0Enabled is Yes
1The target reached the Cycle Relay rung — Fail Streak misses and a failed verified recovery
2A relay is bound to that target (targets 1-4 only; there are four relay bindings)
3The probe subsystem is healthy — three probes that cannot be built set every target Unknown and disable actuation, so the driver never cycles a rack on the strength of its own blindness
4Maintenance Hold is off
5The clock is outside quiet hours
6No other cycle is in flight anywhere in the driver
7The target is under its Max Cycles Per Day ceiling. Every cycle is written down and the ledger is persisted, so a controller restart — including one the relay itself caused — does not hand the next episode a fresh budget. A stamp the driver cannot age (no clock, or a clock that has moved backwards) is kept, never discarded
8The fleet is under the fixed ceiling of four cycles per day across all targets, from the same persisted ledger
9The license gate passes, re-checked at the instant of the relay write

Test Relay 1-4 run this same chain with only condition 1 removed — there is no fault to wait for, which is the point: it is the commissioning tool that proves the relay is wired, bound and reachable before any automation is trusted to drive it. A test spends a daily budget stamp like any other cycle, restores power the same way, and arms no recovery verification afterwards, because there is no fault episode to verify. Nor will one run while that target's recovery verification is pending: cutting power to the target mid-verification would manufacture a Recovery Failed out of the driver's own action, so that refusal fires Cycle Blocked like any other. An unlicensed controller under Strict is refused before anything reaches the wire, and the refusal is recorded, not announced — the event bus is not a way around the gate. Reset Budget is the deliberate override of conditions 7 and 8, so it takes two presses inside 30 seconds and the ring records who asked.

Two paths are deliberately exempt from the license gate, because a licensing problem must never be the reason a rack stays dark: the CLOSE leg that restores power at the end of a cycle, and the boot-time recovery that closes a relay left open by a controller reboot mid-cycle.

4 Wire and commission

  1. Add IntegrateIT Watchdog to a room. Leave Enabled at No — nothing goes on the wire yet.
  2. Fill in Target 1 Name and Target 1 Address (host or host:port; without a port it probes port 80). Use a LAN IPv4, a bare hostname or a .local name; anything routable is refused unless Allow WAN Targets is Yes.
  3. Add the targets behind it and set each one's Upstream — if T1 is the switch and T2 hangs off it, Target 2 Upstream is T1.
  4. Leave every Ladder at Observe for the first day: the driver watches, publishes and logs without firing Down events or touching a relay.
  5. Set Enabled to Yes. Fleet Status moves off Disabled within one probe interval and each target adopts its first verdict silently — no events, by design.
  6. Run Print Audit Log from the Actions tab. Expect one adopt line per configured target.
  7. Only once a full day of entries looks right: bind a relay to Target N Cycle Relay, confirm it is isolated and rated for the load, then run Test Relay N once and watch the load drop and come back. Prove the wiring here, before any Ladder is raised — then raise that target's Ladder.
  8. Prove it end to end — unplug the watched device, watch Fleet Status reach Down after Fail Streak intervals, then watch the log record the snapshot, the recovery attempt, and either the cycle or the named block.

6 How a verdict is made

StateWhat it meansWhat it does
UnknownNothing settled yet, or probing is degradedNothing
UpAnswered — one probe from Unknown, two consecutive from a faultClears the fault, resets the ladder
DownMissed Fail Streak consecutive probesSnapshot, audit, then the current rung
FlappingThree or more transitions inside Flap Window (min)Fires Target Flapping; no Down event, no actuation
SuppressedIts declared upstream is Down, Recovering, or itself SuppressedFires Target Suppressed once; nothing else. No verification runs, no Recovery Failed, no rung of escalation — a dependent never climbs a ladder on its upstream's fault
RecoveringThe grace expired and the verification probe is runningNothing until the verification settles

The first settled verdict after a boot, an address edit or a probe-subsystem recovery is adopted silently: properties, variables, the icon and the audit ring update, and no event fires — nothing changed, the driver simply opened its eyes. An adoption is not a transition either, so one outage and its recovery can never be mistaken for a flap.

The ladder is a ceiling, not a starting point: every fault begins at Observe. When the grace expires the driver opens a fresh probe of its own — never a scheduled one that happened to be in flight, which would decide a "verified" recovery on evidence gathered before the verification began — and a clean streak means Target Recovered while a miss means Recovery Failed and one rung of escalation. A verification whose probe never went on the wire decides nothing at all, and an episode that was acknowledged, withdrawn by an address edit, or suppressed behind an upstream is not verified in the first place. At the ceiling a further failed recovery stops the ladder for that episode (no new grace, no repeated event, no second cycle), so a permanently dead target produces a bounded number of decisions rather than an endless drumbeat, and scheduled probes still bring it back on their own. Flap windows and daily budgets are measured against driver uptime accumulated by the probe scheduler, not the wall clock, so a drifting or unset controller clock cannot skew a flap verdict.

7 Program the project

  • When Target Down, announce it. The driver deliberately has no notification channel of its own; this event is how you get one, using whatever announcement, push or email agent the project has.
  • When Target Flapping, log it and do not act. A flapping link is an intermittent-cable problem and rebooting it hides the evidence — a different alarm from Down.
  • When Cycle Blocked, tell the dealer. Read WD_LAST_EVENT in the same script: it carries the reason (budget, quiet hours, maintenance hold, no relay, unlicensed, probe subsystem degraded).
  • When All Targets Up, clear the dashboard flag. It fires once per outage, on the edge.
  • When WD_T3_STATE changes, act on that one target. Each slot publishes its own state (unknown, up, down, flapping, suppressed, recovering, or unused for a slot with no address), so a per-room script never has to infer one target's fate from the fleet aggregate.
  • When Relay Unconfirmed, tell the dealer to check the relay binding. It only ever fires for a relay that used to report and has stopped; it changes nothing the driver does.
  • Use Maintenance Hold On/Off around a planned rack shutdown, so a scheduled outage never triggers a cycle while monitoring keeps logging. Set Maintenance Hold Auto-Release (h) so a hold a tech forgets clears itself instead of disarming the watchdog for months; 0 means never. Releasing by hand cancels the timer, changing the hours while a hold stands re-arms the full new duration, and a restart restarts the countdown.

Every decision also lands in a persistent ring bounded by Audit Log Size — adoptions, state changes, the target that suppressed another, snapshots, cycle starts and ends, every named block, budget resets, acknowledgements, reboot recovery — because the fault worth reading about is the one nobody was awake for. Print Audit Log dumps it to the Lua output window, and Print Target Report prints the whole live picture beside it — every configured target's state, ladder position, probe class, upstream, relay binding and cycle outcomes, then the budget ledger with each stamp's age, the probe subsystem, the quiet window and whether now is inside it, the maintenance hold and any time left on its auto-release, and a tally of every Cycle Blocked reason since boot. It probes nothing and decides nothing; where a fact is unavailable it says so. Clear Audit Log is deliberately awkward: the first run arms a 30-second window and records who asked, and only a second run inside it erases anything. Evidence anything can wipe in one click is not evidence.

10 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation built on documented Control4 DriverWorks contracts. It bundles no other vendor's runtime, source, brand assets, trial system or license, and engineering, documentation, QA, licensing, updates and support are all provided by IntegrateIT.

Nothing about a watched target leaves the controller. Probes go only to the addresses typed into the Target Address properties — no discovery, no subnet enumeration, no way to reach a host that is not in that list — and the driver sends no target list, no verdict and no audit entry anywhere. The shared license and update services use the controller identity, driver slug, version, license key and update channel documented in the reference below; the key is never logged, and a transient license-server error will not de-license a controller that has already validated.

Lenient mode (the default) allows commissioning without an activated key and keeps License Status visible. Strict mode blocks the relay write on every power-removal path; monitoring, state, events, variables and the audit log continue exactly as normal, and the two power-restore paths in the safety boundary still run. Installing this package does not itself mint or activate a license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
