1 Start here

IntegrateIT Bond Generic Device brings a single Bond generic device — Bond device type GX — into Control4 over the Bond Home local HTTP API v2 (the vendor's own published local API, github.com/bondhome/api-v2). GX is what Bond calls a hand-held RF remote it has learned that is not a ceiling fan, shade, fireplace, or light: a gas log lighter, an exhaust vent, a projector screen, a pool blower, an attic fan. There is no cloud hop — the driver talks straight to the Bond Bridge on your LAN, authenticated by the local token you copy from the Bond Home app.

A generic device has no fixed feature set, so this driver does not guess one. It reads the device's own advertised action list from the bridge and exposes exactly that: Power On, Power Off, Toggle Power, and Stop are sent only when the device advertises them and are refused by name when it does not, and Run Advertised Action reaches anything else on the list by name. State arrives over the Bond Push UDP Protocol (BPUP) with hash-gated HTTP polling as the fallback, so a change made from the Bond app shows up in Control4 without waiting for a poll.

The Bond local API is plain, unencrypted HTTP on port 80, and BPUP push is unencrypted UDP on port 30007, authenticated only by the local token. Physical LAN access is the whole security model — keep the Bond on a trusted, segmented network and never port-forward it. The driver refuses a non-LAN Bond address unless Allow WAN Bond is set to Yes, and it never writes the token to the log.
Release candidate, verified against the Control4 API simulator. The package, Lua 5.1 runtime, action framing, the advertised-action and device-type gates, /state and BPUP frame parsing, the transition-only event diffing, the LAN guard, the license gate, timer hygiene, and this documentation pass automated QA. A qualified dealer must still complete a fresh install and an observed control test against a real Bond Bridge and a learned generic device on the target controller — nothing here has been bench-tested on hardware.

What you get

  • One Bond generic device (type GX) per instance over the local v2 HTTP API — no cloud dependency
  • Power On / Power Off / Toggle Power / Stop, each gated on what the device actually advertises
  • Run Advertised Action to send any other advertised action by name, with an optional numeric argument
  • A non-GX device is refused by name, pointing at the IntegrateIT driver that models it properly
  • BPUP push state (UDP 30007) with automatic hash-gated /state poll fallback; Feedback Mode names the live path
  • POWER, POWER_ASSUMED, and DEVICE_ONLINE variables with transition-only Turned On/Turned Off and Went Online/Went Offline events
  • List Bond Devices, List Advertised Actions, Test Connection, and Print Configuration to commission without guesswork

2 The assumed-state contract

A GX device is a learned one-way RF target. It has no return path — it never tells Bond anything. That single fact governs everything this driver claims:

  • Bond's state is Bond's belief, not a measurement. What GET /v2/devices/<id>/state returns is the state Bond believes it last transmitted. The device is never asked and never answers. This driver publishes that belief and labels it: Power State reads On (assumed — Bond's tracked belief), and POWER_ASSUMED is 1 for as long as a state is held.
  • The original remote is invisible. The hand-held remote the device was learned from transmits directly to the device and bypasses the Bond entirely. Press it, and the device changes while Bond's belief does not. Neither Bond nor this driver can detect that, so POWER is silently wrong until something re-commands the device through Bond. There is no fix for this in software; anything claiming otherwise would be faking it.
  • Unknown at boot, and after every rebind. After a controller reboot, and after any change to Bond IP Address, Device ID, Allow WAN Bond, or State Feedback, the belief is dropped rather than carried forward: POWER and POWER_ASSUMED clear to 0 (nothing observed yet), DEVICE_ONLINE clears with them, and Power State reads Unknown until the first frame or poll lands. Nothing observed about one device ever leaks onto the next. Clearing fires no event — the device did not change, the driver simply stopped claiming to know. That first observation afterwards *adopts* Bond's belief silently for the same reason. Events fire only between two observed states.
  • Reachability is a real signal. A push frame, or any HTTP reply — even a 401 or 404 — proves the bridge answered, so DEVICE_ONLINE goes true and Went Online fires. Only a transport failure with no response marks it offline. DEVICE_ONLINE says the *bridge* is reachable; it says nothing about the device on the other end of the RF link.
  • Commands are not acknowledgements. Bond returns no new state inline with a command, and the device returns nothing at all. A successful PUT means the bridge accepted the action, not that the device received the RF or acted on it.

This is the same one-way honesty register the IntegrateIT Bond Shade, Somfy URTSI II, and ESI R2D7 drivers use. Program around the endpoints and the events, not around a power state you can trust to be continuously true.

Only advertised actions are sent. Once the device's action list is known, an action absent from it is refused locally — Status names the command and the reason, and nothing reaches the wire. In the seconds after load, before the list has been read, the four power commands are attempted once and the bridge's own error is surfaced, because refusing on no evidence would be inventing a verdict. Run Advertised Action always requires the list.

3 Wire and commission

  1. In the Bond Home app, open the device → Settings → Advanced Settings and note the Local Token and the Bond's IP address. Reserve that IP in your router's DHCP table so it cannot change.
  2. Add IntegrateIT Bond Generic Device to the device's room. Enter Bond IP Address and Bond Token (the token is password-typed and never logged).
  3. Run the List Bond Devices action. It prints every device id, name, and type on the bridge, marks the GX entries as belonging to this driver, and names the dedicated driver for anything else. Paste a GX id into Device ID.
  4. Run Test Connection. On success it prints the device name and type, refuses in plain language if the type is not GX, and fills Device Type and Advertised Actions.
  5. Run List Advertised Actions to see exactly what this device can be told to do. Anything beyond the four power commands is driven by pasting a name into Action Name and running Run Advertised Action (with Action Argument set when the action takes one).
  6. Leave State Feedback on Push + Poll fallback unless UDP 30007 is blocked on your network; set Poll Interval (s) for the fallback cadence.
  7. Optionally enter a License Key (see Ownership, privacy, and licensing) — the driver runs in Lenient mode without one.
  8. Prove it: run Toggle Power, watch the device react, and watch Feedback Mode read Push (BPUP) with Power State flipping to the new assumed value.
Bond publishes this local API specifically so control systems and installers can integrate offline; this driver implements that published contract with original IntegrateIT engineering.

4 The Bond GX API on the wire

The transport is HTTP on port 80 with a BOND-Token request header; push is UDP on port 30007. Every control command is a PUT /v2/devices/<id>/actions/<Action>; state and metadata are GET reads.

CommandWire action (PUT …/actions/…)Body
Power On / Off / ToggleTurnOn / TurnOff / TogglePower{}
StopStop{}
Run Advertised Actionthe Action Name value, verbatim{} or {"argument":N}
  • Capability learning: GET /v2/devices/<id> returns the device's name, type, and actions array. That array is the whole control surface — Advertised Actions shows it, and the gate keys on it.
  • Change detection: the device record embeds each sub-resource's change hash, so GET …/properties is re-read only when the bridge reports the properties hash moved. A GX device's properties are device-specific, so the driver lists their field *names* for diagnostics rather than inventing meaning for values it cannot interpret.
  • Reads: GET /v2/devices (enumerate), GET /v2/devices/<id> (name/type/actions), GET …/properties, GET …/state (power). 401 means a wrong token, 404 a wrong device id.
  • BPUP frame: the bridge pushes {"B":<serial>,"t":"devices/<id>/state","s":200,"b":{"_":<hash>,"power":1}}\n. The driver reassembles \n-delimited frames tolerant of arbitrary datagram boundaries and junk, applies only frames carrying this device's state topic, and ignores the rest. It resubscribes with a keep-alive newline ahead of the bridge's 125-second silence drop.
  • Hash-gated poll: GET …/state carries a _ change hash; the driver re-applies state only when that hash moved, so an unchanged device costs nothing and fires no duplicate events. A 429 with Retry-After stops polling for that window instead of hammering.

  • Scene participation: wire Power On into a scene and hang the follow-on off Turned On, which fires on the transition rather than on every repeat command.
  • Drive an uncommon action: set Action Name to an entry from List Advertised Actions (and Action Argument if it takes one), then call Run Advertised Action from Programming. If the device stops advertising that action after a re-learn, the command is refused by name instead of silently doing nothing.
  • Watch reachability: program Went Offline to raise a notification or set a "needs attention" flag; Went Online, or DEVICE_ONLINE as a condition, clears it.

Control is gated by the license, re-checked at the moment of each wire write: under Strict enforcement an unlicensed controller sends no action at all. Push and poll feedback stay live regardless — watching your own device's reported state is not a licensed feature. The default Lenient mode allows commissioning while License Status carries the nag.

The older IntegrateIT Bond driver also covers a generic Bond device, alongside fans, lights, and shades, using periodic polling only. It remains the right choice for a Bond light (type LT), which has no dedicated driver yet. For a GX device this driver is the better fit: it adds push state, the advertised-action gate, the device-type gate, and the assumed-state labeling.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of Bond's published local HTTP API v2 and Bond Push UDP Protocol (github.com/bondhome/api-v2, documents Olibra publishes so external equipment can drive Bond devices). It bundles no other vendor's runtime, source, brand assets, trial, or license. Bond, Bond Bridge, and Smart by Bond are trademarks of Olibra LLC; IntegrateIT is not affiliated with Olibra, and this driver is not a Bond product.

Nothing leaves the LAN. The driver talks only to the Bond address you configure — HTTP on port 80 and UDP on port 30007 — and to nowhere else; no device state, customer identity, or Control4 credential is sent to any device vendor. The Bond Token is treated as a secret: it travels only in the request header, and it is never written to the Lua log, not even with Debug Mode on. The LAN check runs at the single transport chokepoint, so it covers control, polling, and the metadata reads that fire at load — a public or routable destination is refused outright, and no token-bearing request leaves the controller, unless Allow WAN Bond is deliberately set to Yes.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all device control until the Ops Portal has minted and validated a key for that controller; push and poll feedback continue either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means

Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.
