1 Start here

IntegrateIT Bond Fireplace brings a single Smart by Bond fireplace — device type FP — into Control4 over the Bond Home local HTTP API v2 (the vendor's own published local API, github.com/bondhome/api-v2). There is no cloud hop: the driver talks straight to the Bond Bridge (or a Smart by Bond radio) on your LAN, authenticated by the local token you copy from the Bond Home app. Where the generic Bond driver can only fire a press, this one models the fireplace as three separate concerns — the flame (on/off, and level where the fireplace exposes it), an independent blower fan (on/off, speed), and a light — and it reflects changes made from a handheld remote or the Bond app back into Control4 through the Bond Push UDP Protocol (BPUP).

This is convenience control of an appliance that keeps its own listed safety systems. The driver provides NO flame supervision, NO ignition safety, NO flame-failure detection, NO gas-valve interlock, and NO timer-based auto-off — it cannot observe or guarantee any of those, and it deliberately runs no auto-off timer. The fireplace's own listed safety mechanisms (thermocouple/flame-sense, over-temp cutoff, the appliance's own controls) remain the only safety layer and must stay fully in service. Anything claiming otherwise would be faking it.
Release candidate, verified against the Control4 API simulator. The package, Lua 5.1 runtime, action framing, /state and BPUP frame parsing, the flame/fan/light domain separation, the transition-only event diffing, the LAN guard, the license gate, timer hygiene, and this documentation pass automated QA. A qualified dealer must still complete a fresh install and an observed control test against a real Bond Bridge and physical fireplace on the target controller — acceptance on physical hardware is not yet attached to this release.

What you get

  • One Bond fireplace per instance over the local v2 HTTP API — no cloud dependency
  • Flame: Flame On/Off/Toggle Flame, plus Flame Up/Down and Set Flame Level where the fireplace exposes graded flame
  • An independent fan: Fan On/Off and Set Fan Speed (clamped to Fan Max Speed) — never entangled with the flame
  • Toggle Light and Set Brightness where the fireplace was learned with a light
  • Real push feedback: the BPUP UDP listener (port 30007) reflects remote/app changes without polling, with hash-gated HTTP polling as the fallback
  • FLAME_POWER, FLAME_LEVEL, FAN_POWER, FAN_SPEED, LIGHT, and DEVICE_ONLINE variables with transition-only events
  • Honest feature detection — an action the fireplace was not learned with is refused, never a silent no-op

2 Safety boundary

Flame and fan are separate concerns, and the driver enforces that separation in code. On a Bond fireplace the blower (FpFan) is independent of the flame: the Bond FP contract exposes TurnFpFanOn/TurnFpFanOff/SetFpFan distinctly from the flame's TurnOn/TurnOff/SetFlame. This driver honors that on both directions of the wire:

  • Outbound. Every command is tagged with the one concern it may act on. A fan command (Fan On, Fan Off, Set Fan Speed) issues only an FpFan action and can never emit a flame action; a flame command (Flame On/Off/Toggle, Flame Up/Down, Set Flame Level) issues only a flame action and never touches the fan. A domain guard refuses any action outside the stated concern before it reaches the wire — the separation is enforced, not merely a naming convention.
  • Inbound. State is applied field by field. A fan-only change (fpfan_power, fpfan_speed) updates only the fan variables and fan events; a flame-only change (power, flame) updates only the flame variables and flame events. A fan change never mutates FLAME_POWER, and a flame change never mutates FAN_POWER.

What the driver deliberately does not do: it never infers that turning the fan on should light the flame, never runs a safety timer that turns the flame off, and never reports a flame or fan state it did not observe. It is layered on top of the fireplace's own safety systems, never a replacement for them.

3 The feedback contract

State feedback is push-first, poll-as-fallback, and the Feedback Mode property always says which path is live.

  • Push (BPUP). The driver opens a UDP socket to the bridge on port 30007 and sends the keep-alive datagram to subscribe. The bridge then pushes a JSON state frame whenever the fireplace changes — from a remote, the Bond app, or another controller — and the driver applies it immediately. It resubscribes on a timer, ahead of the bridge's 125-second silence drop.
  • Poll fallback. If push goes silent (roughly two keep-alive intervals with no frame), or you set State Feedback to Poll only, the driver polls GET /v2/devices/<id>/state on the Poll Interval (s) and only re-applies when the state hash (_) changed.
  • Boot is silent, then honest. After a controller reboot FLAME_POWER, FLAME_LEVEL, FAN_POWER, FAN_SPEED, and LIGHT are unknown until the first frame or poll lands. That first observation *adopts* the current state silently — no spurious event. Events fire only on a genuine change between two observed states.
  • Reachability is a real signal. A push frame, or any HTTP reply (even a 401/404), proves the fireplace answered, so DEVICE_ONLINE goes true and Went Online fires. Only a transport failure with no response marks it Offline and fires Went Offline.
  • Commands are not acknowledgements. Bond returns no new state inline with a command, so after a successful action the driver schedules a fast follow-up poll (~400 ms) to catch the variables up.
Unsupported features are refused, not faked. Flame Up/Down, Set Flame Level, Fan On/Off, Set Fan Speed, Toggle Light, and Set Brightness are offered only when the fireplace was learned with those actions. On a fireplace without them the command sets Status to "not supported by this fireplace" and sends nothing. Base flame on/off is assumed present for any FP and is never gated.

4 Wire and commission

  1. In the Bond Home app, open the fireplace → Settings → Advanced Settings and note the Local Token and the Bond's IP address. Reserve that IP in your router's DHCP table so it cannot change.
  2. Add IntegrateIT Bond Fireplace to the fireplace's room. Enter Bond IP Address and Bond Token (password-typed and never logged).
  3. Run the List Bond Devices action — it prints every device id, name, and type the Bond exposes. Paste the fireplace's FP id into Device ID.
  4. Run Test Connection. On success it prints the device name and type, warns if the device is not FP, and populates Fan Max Speed and Supported Features from the fireplace's properties and actions list.
  5. Leave State Feedback on Push + Poll fallback unless UDP 30007 is blocked on your network; set Poll Interval (s) for the fallback cadence.
  6. In Programming, wire the flame, fan, and light commands to keypads and scenes, and optionally react to the events or read the variables.
  7. Optionally enter a License Key (see Ownership, privacy, and licensing) — the driver runs in Lenient mode without one.
  8. Prove it: turn the flame on from its handheld remote and watch Feedback Mode read Push (BPUP), FLAME_POWER update, and Flame On fire — with no polling delay — while the fan variables stay untouched.

5 The Bond FP API on the wire

The transport is HTTP on port 80 with a BOND-Token request header; push is UDP on port 30007. Every control command is a PUT /v2/devices/<id>/actions/<Action>; state and metadata are GET reads.

CommandConcernWire action (PUT …/actions/…)Body
Flame On / Off / ToggleflameTurnOn / TurnOff / TogglePower{}
Flame Up / DownflameIncreaseFlame / DecreaseFlame{}
Set Flame LevelflameSetFlame{"argument":N} (1-100)
Fan On / OfffanTurnFpFanOn / TurnFpFanOff{}
Set Fan SpeedfanSetFpFan{"argument":N}
Toggle LightlightToggleLight{}
Set BrightnesslightSetBrightness{"argument":N} (1-100)
  • Set Fan Speed sends the Fan Speed property, clamped to the fireplace's reported maximum (Fan Max Speed, learned from GET …/properties).
  • Feature learning: GET /v2/devices/<id> lists the actions the fireplace was learned with. The driver reads that list into Supported Features (flame level / fan / fan speed / light) and gates those commands on it. A 4xx/5xx or 429 on a control PUT is surfaced in Status and not retried — no retry storm.
  • Reads: GET /v2/devices (enumerate), GET /v2/devices/<id> (name/type/actions), GET …/properties (max_speed), GET …/state (power, flame, fpfan_power, fpfan_speed, light). 401 means a wrong token, 404 a wrong device id.
  • BPUP frame: the bridge pushes {"B":<serial>,"t":"devices/<id>/state","s":200,"b":{"_":<hash>,"power":1,"flame":30,"fpfan_power":0}}\n. The driver reassembles \n-delimited frames tolerant of arbitrary datagram boundaries and junk, applies only frames carrying this fireplace's state topic, and ignores the rest.

  • Scene the flame, leave the fan alone: call Flame On from a "Movie Night" scene — it never spins the blower. Add Fan On to the same scene only if you want the fan, and it runs as its own concern.
  • React to a physical remote instantly: because push is live, lighting the fireplace from its handheld fires Flame On within the push latency, not the poll interval — use it to dim the room lights.

9 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of Bond's published local HTTP API v2 and Bond Push UDP Protocol (github.com/bondhome/api-v2, documents Olibra publishes so external equipment can drive Bond devices). It bundles no other vendor's runtime, source, brand assets, trial, or license. Bond and Smart by Bond are trademarks of Olibra LLC; IntegrateIT is not affiliated with Olibra, and this driver is not a Bond product.

Nothing leaves the LAN. The driver talks only to the Bond address you configure — HTTP on port 80 and UDP on port 30007 — and to nowhere else; no fireplace state, customer identity, or Control4 credential is sent to any device vendor. The Bond Token is treated as a secret: it travels only in the request header and is never written to the Lua log, not even with Debug Mode on. A public or routable destination is refused outright unless Allow WAN Bond is deliberately set to Yes.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all fireplace control until the Ops Portal has minted and validated a key for that controller; push and poll feedback continue either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.
