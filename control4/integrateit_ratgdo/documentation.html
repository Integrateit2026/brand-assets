1 Start here

This driver is a local Control4 client for a ratgdo garage-door control board running the stock ESPHome ratgdo firmware, spoken over the ESPHome Native API — the same TCP protocol Home Assistant uses, but with no Home Assistant, no MQTT broker, and no cloud in the path. It connects straight to the board's api: component (default TCP port 6053), performs the documented Hello / Connect handshake, enumerates the board's entities, and binds them to the ratgdo roles a garage integration needs: the door (a cover), the opener light, the wireless-remote lock, and the obstruction and motion binary sensors. The wire format is the public plaintext-framed protobuf described at esphome.io/components/api.html; this is an original, hand-rolled client of that protocol, and an independent network client of the GPL-2.0 ratgdo firmware, not a derivative of its source.

This is a plaintext-only v1. A board configured with an api: encryption: key (Noise) refuses plaintext connections. This driver detects that refusal and reports encryption required — it cannot connect to an encrypted board until a v2 adds the Noise handshake.
Automated QA drives the whole protocol in a simulator: the handshake, entity enumeration and role binding, the door-state contract, obstruction / motion / light / lock feedback, cover / light / lock commands, the close-warning delay, keepalive reconnect, transport tortures, the encryption-refusal and bad-password paths, and the license gate. A qualified dealer must still run the on-hardware acceptance on a real controller with a ratgdo board and opener — including a live door cycle and obstruction test — before this is called bench-tested. It is not yet.

What you get

  • A direct, cloud-free bridge to a ratgdo board: door open / close / stop / toggle, opener light, wireless-remote lock, and live obstruction and motion.
  • A live Door State (Closed / Open / Opening / Closing / Partially Open / Unknown) derived from the cover's reported position and operation — never a guessed position — plus Door Position as a percentage.
  • Obstruction reported exactly as the opener reports it, published as a property and variable and fired as events, and never suppressed.
  • A Navigator button with live door-state icons whose press toggles the door, and an optional unattended-close warning delay with a Door Close Warning event.
  • Keepalive with automatic, backed-off reconnect and re-enumeration, and a password-typed credential that is never printed or logged.

2 Safety boundary

A moving garage door can injure people, pets, and property. Keep the door in view during commissioning. This driver is a convenience integration, not a listed safety device. It commands the opener and reports what the opener says back; it does not provide entrapment protection and does not enforce photo-eye or obstruction reversal. Never defeat the opener's own photo eyes, force sensing, entrapment protection, manual release, or listed UL 325 safety controls — those remain the opener's job.

The ratgdo board is an accessory wired to a safety-listed opener. Before you rely on remote control:

  1. Prove the opener and all of its safety devices using the manufacturer's wall control and the ratgdo's own web UI first.
  2. Confirm the ratgdo board is flashed with stock ESPHome ratgdo firmware and is reachable on the LAN with its api: component enabled.
  3. Understand that Obstruction here is reported, not enforced: the driver surfaces it and never hides it, but the opener — not Control4 — reverses the door.
  4. Treat remote open and close as a security and safety exposure. This driver runs them only on an explicit user press or a program action, and never wires the door to auto-open on a scene.
  5. For an unattended-close workflow, set Close Warning (s) so a chime or light runs before the door moves — but that delay and its Door Close Warning event are an automation aid, not an audible/visual safety device. A listed unattended-close path uses the opener's approved warning accessories.

3 Wire and commission

  1. In ESPHome, confirm the ratgdo board's config has the api: component enabled. If it has an encryption: key:, remove it for this v1 (or wait for v2) — an encrypted board cannot be driven here.
  2. Set Device IP Address to the board's LAN IP (or its *.local name) and Device Port to its api port (default 6053).
  3. If the board sets api: password:, put it in Device Password (password-typed, never logged). Leave blank if there is none.
  4. The driver connects automatically once an IP is set. Watch Connection Status walk Handshaking → Authenticating → Connected.
  5. Read Entities Found. It lists every enumerated entity and, after ›› bound:, which entity each ratgdo role was auto-bound to. If auto-binding picked the wrong one, put the correct object id or key hex in the matching override (Door Entity, Light Entity, Obstruction Sensor, Motion Sensor, Lock Entity).
  6. With the door in view and the area clear, fire Open Door, then Close Door, and watch Door State and the Navigator icon track the real door. That round trip proves the whole path.

4 Protocol on the wire

Each message is one frame: [0x00][varint payload size][varint message type] [protobuf payload]. In Debug you will see TX/RX lines naming the frame type and byte count only — never the payload, so a password or value never lands in the log. The driver hand-encodes only the messages it uses (Hello, Connect, DeviceInfo, ListEntities requests, SubscribeStates, CoverCommand, LightCommand, LockCommand, Ping, Disconnect) and decodes the matching responses plus the cover / binary_sensor / light / lock state messages. Door commands use the cover's documented legacy command (open / close / stop). Unknown message types — the ones a newer ESPHome firmware may add — are consumed by their declared length and skipped, so API-version drift never wedges the parser. The reassembly buffer tolerates a board that splits a frame across TCP segments or coalesces several into one.

5 Program the project

  • When Obstruction Detected fires → announce on the kitchen touch screen and turn on the driveway lights; the door is not yours to reverse, but the alert is.
  • When Door Opened fires → run a "someone's home" scene; check IS_MOVING is false first so it runs once the door has settled.
  • On a "Goodnight" event → call Close Door. With Close Warning (s) set, Door Close Warning fires first, so a chime or light can run before the door moves.
  • When Motion Detected fires → light the garage for a timed period.

6 Read status at a glance

  • Connection Status — Not connected, Connecting…, Handshaking…, Authenticating…, Connected, Encryption required, Password rejected, or a Blocked: … destination reason.
  • Door State — the derived door position/operation, or Unknown until the board first reports. Door Position carries the percentage.
  • Obstruction — Obstructed, Clear, or Unknown. Reported, never enforced, and never suppressed.
  • Motion, Light State, Lock State — the last reported value, or Unknown.
  • Entities Found — every enumerated entity plus the role each was bound to.
  • Automate on the typed variables; treat Unknown as "no reading yet", not as a safe or closed door — anything claiming a position the board never reported would be faking it.

7 Troubleshoot methodically

  • Nothing connects, Connection Status shows Blocked — the destination failed the LAN-only check. Use a private LAN IPv4 or *.local, or set Allow WAN Destinations to Yes if you truly mean an off-LAN host.
  • Connection Status shows Encryption required — remove the board's api: encryption: key: in the ESPHome config, or wait for the v2 Noise build.
  • Connection Status shows Password rejected — the Device Password does not match the board's api: password:. Fix it; a rejected password is not retried.
  • Connected, but Door State stays Unknown and Entities Found shows no door= — no cover was enumerated, or the Door Entity override matches nothing. Confirm the ratgdo firmware exposes the garage-door cover, then run Refresh Entities.
  • A command does nothing and Status says no bound entity — that role has no matching entity on this board. Check Entities Found and set the override.
  • The link drops and recovers on its own — keepalive lost three pings and reconnected with backoff; entities re-enumerate automatically.
  • Still stuck? Contact support@integrateit.tech · (913) 804-7575.

8 Ownership, privacy, and licensing

Nothing leaves the controller's LAN: the driver talks only to the ratgdo IP you set, and the destination guard refuses off-LAN hosts unless you opt in. The API password lives in a password-typed property and is never printed or logged — Debug records frame type and byte count only, never payloads. This is an original IntegrateIT implementation of the ESPHome Native API wire protocol; it bundles no third-party firmware source, driver, brand assets, or license. Licensing is MAC-locked to this controller: in Lenient mode (default) control still works and License Status carries the activation nag; in Strict mode an unlicensed controller cannot open the connection or send a door, light, or lock command at all — but obstruction and every other feedback path still flow, because safety reporting is never gated. The license is re-checked at command dispatch and again immediately before each wire write. Self-update, when enabled, stages a newer signed build from the IntegrateIT channel without touching your bindings.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
