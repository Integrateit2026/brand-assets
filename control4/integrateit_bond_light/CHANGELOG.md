# Changelog — IntegrateIT Bond Light

## [0.1.0] - 2026-07-29
- Initial release candidate: dedicated single-light control of a Bond light (device type LT) over the Bond Home local API v2 (github.com/bondhome/api-v2). Completes the dedicated Bond type family alongside Bond Ceiling Fan (CF), Bond Shade (MS), Bond Fireplace (FP), and Bond Generic Device (GX).
- Resolved-action dispatch, because Bond publishes no per-type action list for LT: the OpenAPI action schema is `type: string` with an `example:` and no `enum:`, the device record's `actions` array is likewise example-only, and the one official integrator guide that names light actions (TurnLightOn / TurnLightOff / ToggleLight / SetBrightness) documents them for the light on a ceiling fan. So Light On / Light Off / Toggle Light each carry an ordered candidate list (TurnLightOn then TurnOn, TurnLightOff then TurnOff, ToggleLight then TogglePower) resolved against the light's OWN advertised list from GET /v2/devices/<id>; the light-specific spelling wins where both are advertised, and a command whose candidates are all absent is refused LOCALLY by name with the candidates and the advertised list in the reason.
- Set Brightness (Bond SetBrightness, clamped 1-100 — zero is not off, Light Off is), Brightness Up (IncreaseBrightness), and Brightness Down (DecreaseBrightness), each gated on the advertised list. Run Advertised Action reaches any other advertised action by name with an optional finite numeric argument, and requires the list rather than guessing.
- Non-finite numeric input (nan/inf, reachable through hand-edited project files) is neutralized at both layers: a non-finite numeric property falls back to its default instead of poisoning the range clamps or the poll timer, and the single wire chokepoint refuses a non-finite action argument by name, so malformed JSON can never ship.
- State resolution is data too: /state may carry the light's on/off in `light` or in `power` (Bond's schema publishes one flat state example carrying both and scopes neither to a device type), so both are parsed and whichever the light reports is published, with the resolved surface and the live state field shown in the Light Surface property.
- One device type: a device reporting CF / MS / FP / GX is refused by name and pointed at the IntegrateIT driver that models it; HT (heater), SW (smart switch), and BD (bidet) — the remaining types in Bond's own devices/schemas.yaml — are refused just as hard and named for what they are, without inventing a driver for a dealer to go looking for. List Bond Devices annotates every enumerated device the same way. A record that carries no type at all — Bond's own schema marks it required — is refused rather than guessed at, instead of being treated like the not-yet-read window.
- Assumed-state contract: the local API marks nothing as measured, so this driver cannot tell a Smart by Bond light reporting its own hardware from a one-way RF light whose state is only Bond's tracked belief — and it publishes the weaker claim in both cases. POWER and BRIGHTNESS ride alongside POWER_ASSUMED and BRIGHTNESS_ASSUMED, and the Light State / Brightness State properties spell "assumed" out loud, in the same one-way honesty register as the Bond Shade, Bond Generic Device, Somfy URTSI II, and ESI R2D7 drivers. Unknown at boot and after any rebind.
- Real push state feedback via the Bond Push UDP Protocol (BPUP) listener on UDP port 30007: keep-alive subscription, \n-delimited JSON frame parsing tolerant of arbitrary datagram boundaries and junk, topic-filtered to this device, and resubscribe before the 125s bridge drop.
- Automatic fallback to hash-gated HTTP polling of /state when BPUP goes silent, with a bounded 429 Retry-After backoff; the Feedback Mode property reports which path is live and why it fell back.
- Publishes POWER, POWER_ASSUMED, BRIGHTNESS, BRIGHTNESS_ASSUMED, and DEVICE_ONLINE with transition-only Light On/Off, Brightness Changed, and Went Online/Offline events (unknown->known baseline adoption is silent); a rebind clears every published variable back to unknown without firing an event. Reachability reports the bridge answering, never the RF link.
- BOND-Token header auth (user-supplied, never logged), LAN-only destination guard enforced at the single transport chokepoint so control, polling, AND the boot-time metadata reads are all covered, with an Allow WAN Bond override, and MAC-locked IntegrateIT licensing re-checked at wire-write time on every control path. Debug prints every HTTP call as method + path, reads included, and never the token.
- Known limits: one light per instance; LT only; state is labeled assumed in every case because the API never marks it measured; a press on a one-way light's original hand-held remote is undetectable; BPUP needs UDP 30007 reachable or the driver runs poll-only; acceptance on physical hardware is not yet attached to this release.
