1 Start here

IntegrateIT Hue Motion Sensor brings ONE Philips Hue motion accessory into Control4 over the bridge's local CLIP API v2 (the on-bridge REST API rooted at /clip/v2, documented at developers.meethue.com). There is no cloud hop and no Hue account: the driver talks straight to the bridge on the LAN over HTTPS, so it keeps working when the internet is down. You pair with the bridge's link button, run Discover Sensors, pick your sensor by number, and the driver binds it. From then on motion, ambient light, temperature, and battery arrive as push updates from the bridge's /eventstream/clip/v2 Server-Sent-Events stream — no polling — and land in Control4 variables and events you can program against.

This driver is for lighting and comfort automation only. It is NOT a security, surveillance, or intrusion device, and it is not a listed alarm path. The Philips Hue Developer Terms §8.2 forbid using the Hue API for security, surveillance, intrusion detection, presence tracking, or real-time monitoring, and a battery accessory on a consumer Zigbee mesh is not built to carry a life-safety decision in any case. Never bind it into a security partition, and never let it be the sensor a life-safety or intrusion outcome depends on. Use it to turn lights on when someone walks in.
The bridge presents a self-signed certificate. The driver connects over HTTPS with CA-chain verification disabled and pins trust to the bridge's LAN address plus the application key — Signify's documented posture for local integration. Keep the bridge on a trusted LAN segment; a non-LAN address is refused unless Allow WAN Bridge is set to Yes.
Ready for controlled commissioning. The package, Lua 5.1 runtime, link-button pairing, CLIP v2 framing, sensor discovery and binding, eventstream parsing, stream-loss handling, reconnect/backoff, TLS trust model, LAN guard, license gate, and documentation pass automated QA against the Control4 API simulator (hardwareStatus: simulation-verified). A qualified dealer must still complete a fresh install and an observed walk test against a real Hue Bridge and a real sensor on the target controller — this release is not bench-tested on physical hardware.

What you get

  • Motion as MOTION (BOOL) and CONTACT_STATE in the Control4 contact vocabulary — OPENED on motion, CLOSED when clear, UNKNOWN before the first observation — plus Motion Detected / Motion Cleared events
  • Ambient light as LIGHT_LEVEL in lux, converted from the CLIP logarithmic value, with LIGHT_LEVEL_RAW published beside it so the conversion is auditable
  • Temperature as TEMPERATURE in Fahrenheit or Celsius, from the accessory's own on-board sensor
  • Battery as BATTERY_LEVEL (percent) and BATTERY_STATE, with a Battery Low event at a threshold you set
  • Sensitivity as SENSITIVITY and SENSITIVITY_MAX plus a Motion Sensitivity property reading 2 of 4, and a Set Sensitivity command that writes it back to the sensor
  • Enable Sensing / Disable Sensing / Set Sensitivity — the only three writes this driver ever makes, all license-gated at the moment of the write
  • Built-in link-button pairing and Discover Sensors binding by number, each entry annotated with the room the bridge has that sensor in; the binding survives reboots
  • Honest staleness: when the live feed dies, STATE_STALE goes true and Motion State says so, instead of a frozen value pretending to be current
  • LAN-only destination guard on every request including the boot-time reads, and an application key that is never written to the log

2 The feedback contract

This driver reports what the bridge tells it about one sensor, and it tells you plainly how it knows:

  • State is pushed, not polled. The driver holds the GET /eventstream/clip/v2 SSE stream open and applies each update as it arrives, so a walk-past shows up in Control4 within moments. A slow Resync Interval (s) heartbeat (default 300) backs the stream up and re-reads the sensor if the stream ever stalls.
  • First observation is silent. The first motion state the driver sees — from the opening resync or the first event — is adopted without firing Motion Detected/Cleared. Those fire only on a real change from a value the driver already saw. Same rule for the sensing-enabled flag. A controller restart wipes what the driver remembered; the first read re-primes it silently.
  • A lost feed is announced, not hidden. A sensor has no command whose success would re-prove it, so when the eventstream drops the driver publishes BRIDGE_ONLINE false, fires Bridge Offline and Sensor State Stale, sets STATE_STALE true, and relabels Motion State as Stale (feed down) — last seen …. A resync that gets no answer at all does the same — that is the only signal a build without streaming has, so the gate works there too. The last observed values stay published — they are the last thing that was actually true — but they are labelled, never presented as live. If your programming must not act on old data, gate it on STATE_STALE.
  • Nothing is invented. Before the first successful read LIGHT_LEVEL, TEMPERATURE, BATTERY_LEVEL, SENSITIVITY, and SENSITIVITY_MAX are empty, not zero, and CONTACT_STATE is UNKNOWN. MOTION is a BOOL and cannot express "unknown" — read CONTACT_STATE or Motion State when the difference matters. The same rule governs the room: it is blank until the bridge has been asked, and blank if the sensor is in none.
  • Sensitivity follows the wire like everything else, and fires nothing. It is adopted silently from a read or a stream frame, so it also tracks a change made in the Hue app; a successful Set Sensitivity publishes nothing at all, because the bridge accepting a PUT is not the sensor having changed. There is no Sensitivity event on purpose — a setting on the sensor is not an occurrence in the room.
  • A gap produces no event — but the stream coming back is not a gap. When the feed returns the driver takes exactly one catch-up read and adopts whatever is true now into the variables, with no Motion Detected/Cleared fired: a transition that happened while the driver was blind is not one it observed, and firing it late would tell Composer something happened now that did not. Programming that must still react across a gap should watch the MOTION / CONTACT_STATE variable, which does update. What the eventstream itself delivers once it is back is a different thing entirely — the bridge pushes only on change and never replays what it missed, so a frame arriving on a live stream is a change happening now and fires normally, even if it is the very first thing after a reconnect. Same on a build with no streaming: once a read succeeds the heartbeat is the feed again, and the next change it sees fires.
  • Sensing Enabled/Disabled follow the wire, not the button. Running Enable Sensing does not fire Sensing Enabled; the read-back after the bridge confirms does. That means the events also fire when someone flips the sensor in the Hue app.
  • Rebinding forgets everything. Binding a different sensor, or running Clear Binding, resets every reading to unknown and fires nothing — no observation has been made yet against the new id.
  • On OS builds too old for C4:url() streaming the eventstream is skipped and the resync heartbeat is the whole feedback path — lower Resync Interval (s) there.

Motion reaches Composer as variables and events, not as a bindable contact-sensor connection. This driver declares no CONTACT_SENSOR connection because the producer side of that contract — a driver pushing OPENED/CLOSED out to a bound consumer — is not verified SDK surface in the IntegrateIT factory, and shipping an unproven binding would look wired while delivering nothing. CONTACT_STATE carries the same vocabulary in a form that is proven to work: OPENED on motion matches what a Control4 motion sensor reports, and it is the polarity IntegrateIT Occupancy expects by default.

3 Wire and commission

  1. Reserve the bridge's IP address in your router's DHCP table so it never changes. Discover Bridges browses _hue._tcp on the LAN and prints what it finds.
  2. Add the sensor to the bridge in the Hue app first. This driver reads accessories; it does not join them to the mesh.
  3. Add IntegrateIT Hue Motion Sensor to a room and enter Bridge IP Address.
  4. Pair. Press the round link button on the bridge, then run Pair (Link Button) within ~30 s. The driver POSTs the claim (the first attempt returns Hue error 101 until the button is pressed), stores the returned key in the password-typed Application Key property, and connects. You never handle the key yourself.
  5. Run Test Connection — it prints the bridge_id and confirms the stored key works.
  6. Bind the sensor. Run Discover Sensors with Debug Mode = Print so you can read the Lua output. It lists every bridge device that publishes a motion service, numbered, and names the room the bridge has each one in — 1. Hallway sensor [Hue motion sensor] (Hallway) device 0a1b… — which is usually how you tell three identical sensors apart. Set Sensor Selection to the number you want and run Bind Selected Sensor. Sensor Device and Sensor Name fill in, and the binding persists across reboots.
  7. Set Temperature Units and Battery Low Threshold (%) to taste. If the sensor is twitchy or deaf, set Sensitivity and run Set Sensitivity (see Program the project).
  8. Optionally enter a License Key. The default Lenient (recommended) mode commissions without one.
  9. Prove it. Walk in front of the sensor and watch MOTION flip to 1, CONTACT_STATE read OPENED, and Motion State read Motion. Walk away and watch it clear after the sensor's own hold time.
One instance binds one sensor. Add another instance for a second sensor or a second bridge.
The room is a label, not a link. The driver reads it from the bridge's own room list to help you recognise a sensor and to annotate Sensor Status; the binding itself is the sensor's resource id, so renaming or deleting a Hue room changes what you read here and nothing about how the driver behaves. A sensor the bridge has in no room — and any run where the room list could not be read — shows (no room), never a guess. The room list is asked for at the same moment as the device list rather than before it, so on the rare run where it answers second the listing prints with rooms unknown; run Discover Sensors again and it will be annotated.

4 On the wire

Every request is JSON over HTTPS to https://<ip>. The application key rides in the hue-application-key header — never in the URL — so no log line ever contains it (Debug shows the method and sub-path only). Any body-carrying request declares Content-Type: application/json.

PurposeRequestBody / result
Pair (link button)POST /api (no key){"devicetype":"iit_c4#…","generateclientkey":true} → [{"success":{"username":"…"}}] or [{"error":{"type":101}}]
Discover sensors / read the nameGET /clip/v2/resource/devicedevices whose services[] array really contains "rtype":"motion"
Resolve rooms (labels only)GET /clip/v2/resource/roomeach room's metadata.name plus the device rids in its children[]
ResyncGET /clip/v2/resource/motion · /light_level · /temperature · /device_powereach entry matched to the bound sensor by owner.rid
Live feedbackGET /eventstream/clip/v2 (Accept: text/event-stream)long-lived SSE update/add/delete frames
Enable / disable sensingPUT /clip/v2/resource/motion/{rid}{"enabled":true} / {"enabled":false}
Set sensitivityPUT /clip/v2/resource/motion/{rid}{"sensitivity":{"sensitivity":N}}, 0 ≤ N ≤ sensitivity_max

The driver matches a service to your sensor two independent ways — the resource names your bound device as its owner, or its id is one already learned for that service on a resync. Anything else on the bridge (other sensors, lights, scenes, the SSE envelope's own event id) is dropped before it can touch state.

Light level. CLIP v2 reports illuminance logarithmically: light_level = 10000 * log10(lux) + 1. The driver inverts it — lux = 10 ^ ((light_level - 1) / 10000) — and publishes both the lux figure and the raw value. A reported light_level of 0 sits below the formula's meaningful floor: inverting it yields 0.9998 lux, which is not a reading. The driver publishes 0 lux there rather than round that up to 1. This is a conversion of the bridge's number, not a calibrated measurement.

Temperature arrives in Celsius and is converted to Fahrenheit unless Temperature Units says otherwise. It comes from a sensor inside the accessory's housing, so it reads warm relative to room air — a trend signal, not a thermostat reference.

Sensitivity. The motion service carries "sensitivity":{"status":…,"sensitivity":N,"sensitivity_max":M}, and only N is writable. M is the sensor's own ceiling (4 on the common Hue motion sensors) — the driver publishes whatever the sensor reports and never assumes a range, so Set Sensitivity refuses until the sensor has stated one, and an accessory that never reports the block does not expose sensitivity at all. A value outside 0..M is refused by name rather than clamped: the ceiling belongs to the device, and quietly rewriting a 7 into a 4 would report success for a setting the sensor never received. 0 is the least sensitive setting, not an absent one.

Key order and hostile names. Every payload above is parsed by cutting real object spans out of the data array, because a Hue bridge serializes keys alphabetically — enabled arrives before a motion service's own id, and a room's children before the room's id — so no field is ever attributed by position. The scan skips quoted text whole, which is what keeps a sensor named Hallway [main or a room named Loft ]2[ from truncating an enumeration, and a device's services[] array is walked as structure so a name containing ","rtype":"motion" cannot advertise a service the device does not have.

Replies the driver acts on: 200 on a read, any 2xx on a write; 401/403 means the application key was rejected (re-pair); code 0 is no response (Offline, and stale). SSE frames are parsed tolerant of arbitrary chunk boundaries, comment lines, and both the flat (motion.motion) and newer report (motion.motion_report.motion) payload shapes — bytes accumulate and only a fully terminated frame is applied. A 429 (undocumented on the local API) is honored with a single bounded retry after Retry-After, never an immediate re-send. On a stream drop the driver reconnects with bounded backoff: 5 s, doubling to a 60 s cap.

The driver holds one stream at a time and never asks the bridge to replay: it sends no If-None-Match, so the eventstream carries live changes only and nothing arrives late. A stream the driver has deliberately replaced — by Reconnect Event Stream, a rebind, or a new bridge address — stays on the wire until the bridge closes it, but it is ignored from the moment it is replaced, so it can neither move state nor report an outage on behalf of the stream that took over.

  • When Motion Detected fires → and STATE_STALE is false → turn the hall lights on. The stale check is what keeps a reconnect from driving lights off an old reading.
  • When Motion Cleared fires → start a 5-minute timer → turn the lights off. Keep the timer in Composer, not in the sensor: the accessory's own hold time is short and is not exposed here.
  • When Motion Detected fires → and LIGHT_LEVEL is less than 30 → set the scene to Night. One sensor drives both the trigger and the daylight test.
  • When Battery Low fires → push a notification naming Sensor Name. Replace the cells before the sensor goes quiet, not after someone notices the lights stopped working.

Tuning sensitivity. Set the Sensitivity property (0 = least sensitive) and run Set Sensitivity — from the Actions/Programming side like any other command, so a scene can raise sensitivity at night and drop it during the day. Read SENSITIVITY_MAX first, or run Print Configuration: your sensor's ceiling is usually 4, and anything above it is refused by name rather than quietly rounded down. Nothing is published from the write itself — the bridge accepting the PUT is not the sensor having changed, so SENSITIVITY moves on the read-back a moment later (and equally when someone changes it in the Hue app). Sensitivity fires no event on purpose: it is a setting on the sensor, not something that happened in the room.

Control commands are gated by the license: under Strict enforcement an unlicensed controller writes nothing — Enable Sensing, Disable Sensing, and Set Sensitivity all send nothing — but reading your own sensor, pairing, discovery, and the eventstream stay live, because reading your own bridge is not a licensed feature. The default Lenient (recommended) mode allows commissioning while License Status carries the nag.

MOTION, CONTACT_STATE, LIGHT_LEVEL, TEMPERATURE, and BATTERY_LEVEL hold the last values the eventstream or a resync reported. They drive automation safely while STATE_STALE is false — they are the bridge's own numbers, never invented — but when the feed is down they are history, not news.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of the published Philips Hue CLIP API v2. It does not bundle another vendor's runtime, source code, brand assets, trial system, or license. Philips Hue and the Hue names are trademarks of Signify; IntegrateIT is not affiliated with Signify, and this driver is not a Philips Hue product.

Scope, stated once more where it belongs. The Philips Hue Developer Terms §8.2 forbid using the Hue API for security, surveillance, intrusion detection, presence or event tracking, and real-time monitoring. This driver is built for lighting and comfort automation and nothing else. It is not a security or intrusion device, not a listed alarm path, and must never be bound into a security partition or relied on for a life-safety decision. Programming it as an occupancy trigger for lights, scenes, and comfort is exactly what it is for; programming it as an alarm zone is both a terms violation and an unsafe design.

Nothing leaves the LAN. The driver talks only to the Hue Bridge on your network — there is no cloud service, no Hue account, and no telemetry; sensor state, project identity, and Control4 credentials are never sent to a device vendor. Every request the driver makes — the resync, the device read, the room read, the pairing claim, the eventstream, and the three writes — passes one destination guard before a single header is assembled, so the application key can never be handed to a host outside private address space unless you deliberately set Allow WAN Bridge to Yes. The connection is HTTPS: because the bridge's certificate is self-signed, the driver disables CA-chain verification and pins trust to the bridge's LAN address plus the application key — the transport is still encrypted, and a genuinely broken TLS handshake fails closed (the driver reports the bridge offline and never downgrades to plaintext). The application key lives in the password-typed Application Key property and rides only in the hue-application-key request header, so the driver never logs it — even in Debug Mode, lines show the method and sub-path only, and Print Configuration prints the key's length, not its value.

Motion data stays on the controller. The driver publishes it into Control4 variables and events for your programming; it keeps no history, uploads it nowhere, and exposes it to nothing outside the project.

Lenient (recommended) mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks Enable Sensing, Disable Sensing, and Set Sensitivity until the Ops Portal has minted and validated a key for this controller; reading the sensor, pairing, discovery, and the eventstream continue either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

v0.2.02026-07-30
  • Sensitivity, read and written. The CLIP v2 motion service carries sensitivity: {status, sensitivity, sensitivity_max} — re-confirmed for this release against the OpenHue OpenAPI mirror (src/motion/schemas/MotionGet.yaml, MotionPut.yaml) and aiohue's MotionSensingFeatureSensitivity / MotionSensingFeatureSensitivityPut, since Signify's own reference for the resource is behind a developer login. The driver publishes SENSITIVITY and SENSITIVITY_MAX plus a Motion Sensitivity property reading 2 of 4, adopted silently on a read or an eventstream frame like every other reading — including when the Hue app is what changed it.
  • Sensitivity fires no event, deliberately. It is a configuration value on the sensor, not something that happened in the room, so there is nothing for Composer to trigger on; the variables and the property carry it.
  • New command Set Sensitivity writes the dealer's Sensitivity property to the motion service as PUT {"sensitivity":{"sensitivity":N}} — the only writable field of that block; status and sensitivity_max are read-only. It re-checks LicenseGate() at the moment of the wire write, rides the same LAN-guarded chokepoint as everything else, and refuses locally and BY NAME — costing zero requests — when nothing is bound, when the motion service id is not known yet, when the sensor has not reported sensitivity_max, and when the value is not a finite number or falls outside 0..sensitivity_max.
  • An unknown ceiling is refused, not guessed. The popular Python client defaults sensitivity_max to 10 in its own model; a driver that inherited that default would cheerfully PUT a 7 to a 4-step sensor. If the accessory has not stated its range, Set Sensitivity says so and sends nothing — and an accessory that never states one does not expose sensitivity at all.
  • Out of range is refused rather than clamped, which is a deliberate departure from the fleet's clamp-a-dealer-range habit: this ceiling belongs to the DEVICE, so quietly rewriting a 7 into a 4 would report success for a setting the sensor never received. 0 is a real sensitivity (least sensitive) and goes out unchanged. tonumber("nan") succeeds and defeats every range test because all comparisons against nan are false, so the numeric reader is non-finite hardened (LAW 1) — the driver will not ship {"sensitivity":{"sensitivity":nan}}, which is not JSON.
  • A successful PUT publishes NOTHING. A 2xx means the bridge accepted the request, not that the sensor is now at N — the read-back (or the stream echo) is the only thing that moves SENSITIVITY, exactly as the enabled flag already worked. The bridge's own status: "changing" is its admission that acceptance is not arrival.
  • Room-aware discovery. Discover Sensors now reads GET /clip/v2/resource/room once through the same chokepoint and resolves each device through the rooms' children lists, so the listing reads 1. Hallway sensor [Hue motion sensor] (Hallway) device 0a1b…. A device the bridge has in no room — or a room collection that could not be read — prints (no room); no location is ever inferred. The bound sensor's room is annotated onto Sensor Status and Print Configuration once the bridge has been asked, and a resolved "no room" is remembered so the driver stops asking, while a FAILED room read stays unknown and is asked again on the next heartbeat.
  • Rooms are decoration and nothing else. Matching, binding, and every state decision stay keyed on the resource id, so a renamed, deleted, or unreadable room changes what a dealer reads and nothing the driver does.
  • The parser was rebuilt, and it fixes a defect 0.1.0 shipped. A real bridge serializes object keys ALPHABETICALLY, which puts enabled before a motion service's own id and a room's children before the room's id. 0.1.0 indexed every "id" and sliced the bytes to the next one, so on real hardware it never read the enabled flag at all — MOTION_ENABLED and the Sensing Enabled/Disabled events were dead in the field, and in a multi-sensor collection each resource would have taken its neighbour's flag. Its id-first test fixtures hid the whole class, exactly as they did on the Hue Bridge driver before 0.1.1 (de22cc8). This release cuts REAL object spans out of each data array — the string-aware scanner from integrateit_hue_button (LAW 2), so a sensor called Hallway [main or a room called Loft ]2[ cannot truncate an enumeration — and every field is read off its own object. Rewriting the fixtures in the bridge's real key order made 3 checks in unmodified 0.1.0 cases fail against the 0.1.0 body; the committed 0.1.0 suite passes unchanged against this one (393 checks, 0 fails).
  • The services array is now walked structurally when deciding whether a device publishes a motion service, so an accessory whose customer-typed NAME contains ","rtype":"motion" can no longer advertise a service it does not have. *_report and deprecated-flat payload shapes are still both read for motion, light level, and temperature; a motion resource that omits the motion block entirely (which aiohue documents on some firmware) still reads as "no reading in this update" rather than as a value.
  • intProp is non-finite hardened to the fleet's canonical shape (LAW 1). 0.1.0's reader returned a nan unchanged through its own clamp, which could have poisoned the resync timer.
  • The eventstream framing was hardened, and a CRLF bridge would have gone silently deaf. SSE terminates a line with CRLF, LF, or a bare CR, and a bridge (or any proxy in between) that uses CRLF puts \r\n\r\n between frames — which contains no \n\n at all, so the 0.1.0 splitter never completed a single frame on such a peer: no motion, no events, buffer growing until the bound tripped, and the resync heartbeat as the only feedback left. Line endings are now normalized on ingest, with a dangling CR HELD across a chunk boundary so a split inside one terminator cannot fabricate a blank line and cut a frame in half. The held CR is cleared with the buffer whenever a stream opens, so nothing from a retired transfer leaks into its replacement.
  • The 64KB buffer bound now drops the unterminated residue WHOLE instead of keeping a 4KB tail. The tail was worse than the overflow: it prefixed the next real frame's data: line, so the data: was no longer at the start of a line and the whole following frame was silently discarded. The bound is stated honestly in the code — any frame whose first 64KB arrive without a terminator is lost, not deferred, and a CLIP v2 envelope is orders of magnitude smaller than that.
  • Non-finite hardening extended to the READ side and to the PUBLISH side (LAW 1). %d+ matches a 400-digit integer and tonumber overflows it to inf, and an inf ceiling defeats every range test exactly as nan does — it would have made the gate the whole sensitivity feature turns on accept ANY value — so a payload number is not a number until it is finite, and an unrepresentable one is treated as an absent field. The guard on the parse alone was not enough, because both published measurements are CONVERSIONS: lux is exponential in light_level, so a finite seven-digit reading (9999999) came out of 10 ^ ((raw - 1) / 10000) as inf, and the Fahrenheit conversion multiplies a Celsius value across the same edge. Both refuse at the point the non-finite is manufactured — the bridge's raw value still stands, the derived measurement is simply not published, and no Control4 variable ever carries the string inf. Motion Sensitivity reads 2 (ceiling Unknown) when the ceiling is unknowable, never 2 of ?.
  • Unchanged on purpose: the baseline-silence rule, the one-shot blind-gap token and its motion-feed scoping, the stream-loss staleness contract, the single-eventstream generation discipline, the LAN guard at the one chokepoint, the TLS trust model, the no-CONTACT_SENSOR decision, and every §8.2 scope statement. Sensitivity can neither consume nor arm the gap token — a case pins that — and the 0.1.0 suite is the regression proof.
  • Still releaseStatus: release-candidate / hardwareStatus: simulation-verified: verified against the Control4 API simulator (525 runtime checks, 0 fails, 0 violations), not on a physical bridge, sensor, or controller.
v0.1.02026-07-27
  • Initial release candidate: local Control4 feedback from one Philips Hue motion accessory over the on-bridge CLIP API v2 (HTTPS, developers.meethue.com). Clean-room original engineering; the pairing, transport, TLS posture, LAN guard, eventstream framing, and reconnect backoff are ported from the shipped IntegrateIT Hue Bridge driver rather than reinvented.
  • Scope stated in the manifest, the driver header, Start here, the trust section, and Print Configuration: this is a LIGHTING AND COMFORT driver, NOT a security, surveillance, or intrusion device, and not a listed alarm path. Philips Hue Developer Terms §8.2 forbid security/surveillance use of the Hue API, and a battery accessory on a consumer mesh cannot carry a life-safety decision. Never bind it into a security partition.
  • Link-button pairing built in: Pair (Link Button) POSTs /api with generateclientkey, handles the error-101 "press the button" round-trip, and stores the returned application key in the password-typed property — never printed, never logged (it rides only in the hue-application-key header).
  • Discover Sensors reads GET /clip/v2/resource/device and lists only devices whose service list contains a motion service, numbered; Bind Selected Sensor binds the chosen entry into the persisted Sensor Device property. Clear Binding and any rebind reset every reading to unknown and fire nothing — no observation has been made against the new id yet.
  • The bound sensor's four services (motion, light_level, temperature, device_power) are matched two independent ways — the resource names the bound device as its owner, or its id is one already learned on a resync — so another sensor's services, a light, a scene, or the SSE envelope's own event id can never move this instance's state.
  • Push feedback: consumes the /eventstream/clip/v2 SSE stream and publishes MOTION, CONTACT_STATE (OPENED / CLOSED / UNKNOWN, the verified Control4 contact vocabulary), MOTION_ENABLED, LIGHT_LEVEL, LIGHT_LEVEL_RAW, TEMPERATURE, BATTERY_LEVEL, BATTERY_STATE, LAST_MOTION (the bridge's own creationtime), STATE_STALE, and BRIDGE_ONLINE; fires Motion Detected/Cleared, Sensing Enabled/Disabled, Battery Low, Bridge Online/Offline, Event Stream Reconnected, and Sensor State Stale. SSE parsing tolerates arbitrary chunk boundaries and keep-alive comments.
  • Light level is converted honestly: CLIP reports 10000*log10(lux)+1, the driver inverts it to lux = 10 ^ ((light_level - 1) / 10000) and publishes the raw value alongside so the conversion is auditable. A reported 0 sits below the formula's meaningful floor (inverting it yields 0.9998 lux), so the driver publishes 0 lux rather than round that up to 1. Both the flat CLIP fields and the newer *_report shapes are read for motion, light level, and temperature. Temperature converts C→F unless Temperature Units says otherwise, and is documented as an in-housing trend signal, not a thermostat reference.
  • Baseline silence where it belongs, and nowhere else. The first motion reading, the first enabled-flag reading, and the ONE catch-up read after a blind gap all adopt without firing a transition. What the eventstream delivers once it is back does fire: the driver sends no If-None-Match, so the bridge replays nothing and a frame arriving on a live stream is a change happening now — including the very first frame after a reconnect, which is usually the walk-past the dealer cares about. The gap token is one-shot and scoped to the motion feed, so a build running on the resync heartbeat alone resumes firing as soon as it has a good read, and a failed battery read never suppresses a motion transition the driver did watch. Battery Low is the deliberate exception in the other direction — a low battery is a standing condition, not a transition, so it reports the first time it is seen and latches until the level recovers.
  • Stream-loss honesty: a dropped eventstream — or a resync that gets no answer, which is the only signal a build without streaming has — publishes BRIDGE_ONLINE false, fires Bridge Offline and Sensor State Stale, raises STATE_STALE, and relabels Motion State Stale (feed down) — last seen …. The last observed values stay published because they are the last thing that was actually true — labelled, never frozen and presented as live, and never replaced by an invented zero. The documented trade is that a change during the blind gap moves the variables but fires no event.
  • One eventstream at a time. Connect runs on every relevant property change and on every rebind, so the driver refuses to stack a second long-lived transfer on a healthy one. A C4:url() transfer cannot be aborted, so a stream that has been deliberately replaced (Reconnect Event Stream, a rebind, a new bridge address) stays on the wire until the bridge closes it — it carries the generation it was opened under and is ignored from the moment it is replaced, so an abandoned transfer can neither re-apply state nor announce an outage over the stream that took over. Teardown retires the generation for the same reason: a socket closing a minute after OnDriverDestroyed cannot re-arm the reconnect timer.
  • Enable Sensing / Disable Sensing (PUT the motion service enabled flag) is the ONLY writable surface, and both re-check LicenseGate() at wire-write time. Neither fires Sensing Enabled/Disabled — the read-back does, which also means the events fire when someone flips the sensor in the Hue app. A write before any successful read refuses locally, by name, with the fix ("Motion service id unknown — run Resync Now first").
  • LAN guard at the ONE transport chokepoint, ahead of header assembly, so the resync, the device read, the pairing claim, the eventstream, and the two writes are all covered — including the boot-time reads, which is the exact path a prior driver leaked an application key through. A blocked host produces zero requests of any kind; the runtime suite asserts the request count against the blocked address is 0 after boot and after every command and action.
  • Honest TLS trust model: the bridge is self-signed, so the driver connects over HTTPS with CA verification disabled and pins trust to the LAN address + application key; a broken TLS handshake fails closed and never downgrades to plaintext. A single bounded retry honors 429 Retry-After (no retry storm), and stream reconnects use bounded backoff (5s → 60s cap).
  • No bindable Control4 CONTACT_SENSOR connection, deliberately. Producer-side contact delivery — this driver pushing OPENED/CLOSED to a bound consumer — is unverified SDK surface (still fenced as unverified in the contact-relay template, and shipped by no IntegrateIT driver), and a binding that looks wired while delivering nothing is worse than no binding. Motion reaches Composer as variables and events instead, with CONTACT_STATE carrying the same vocabulary; the runtime suite pins this structurally by failing if a proxy or a CONTACT_SENSOR connection ever appears in the rendered driver.xml.
  • Known limits: one sensor per instance; sensitivity, outdoor daylight thresholds, and Hue-app automations are not exposed; light level is a conversion rather than a calibrated measurement; temperature reads warm because the sensor sits inside the housing; a change during a stream gap moves the variables but fires no event.
  • Verified against the Control4 API simulator only — releaseStatus: release-candidate, hardwareStatus: simulation-verified. Acceptance on a physical Hue Bridge, a physical motion accessory, and a physical controller is not attached to this release.
