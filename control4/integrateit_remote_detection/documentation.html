1 Start here

IntegrateIT Remote Detection is a headless Control4 classifier that tells your programming which handheld remote class is driving the room right now. It is not a hardware driver and it speaks no device protocol: it contacts no device on the network, and only ever classifies activity Composer hands it, from exactly two sources — six BUTTON_LINK connections (500-505), one per supported class, and the Report Remote Activity programming command for remotes that expose a programming event but no linkable button. Each accepted press publishes one active class — SR-250, SR-260, Halo, Halo Touch, Neeo, or Other Remote — as the Active Remote property plus the ACTIVE_REMOTE_CLASS, LAST_REMOTE_CLASS, REMOTE_ACTIVE, REMOTE_ACTIVITY_COUNT, and LAST_REMOTE_BUTTON variables, and fires Remote Detected. LAST_REMOTE_BATTERY moves only when a programming step reports a level. This is original IntegrateIT engineering — there is no external device protocol to conform to.

The class is your wiring, not a measurement. A press on connection 502 publishes Halo because you linked that button to 502 — the driver cannot verify the handheld actually is a Halo, so a link on the wrong connection produces a confident wrong answer. Double-check the Connections page before trusting the class in programming.
Ready for controlled commissioning. The package, Lua 5.1 runtime, both detection sources, duplicate suppression, the stale/offline/reconnect logic, the three-position Privacy Mode, persistence across a restart, the license gate, and this documentation all pass automated QA in the Control4 API simulator. A qualified dealer must still confirm acceptance from the actual handhelds and keypads on the target controller — representative-remote verification on real hardware is still pending.

What you get

  • Six explicitly bounded remote classes: SR-250, SR-260, Halo, Halo Touch, Neeo, and Other Remote — nothing outside this set
  • Two detection sources: one BUTTON_LINK binding per class and the Report Remote Activity programming command — Detection Sources can narrow detection to either path alone
  • Duplicate-press suppression so one physical press delivered twice counts once
  • A stale-activity timeout that returns the room to Unknown and raises an event when the remote goes quiet
  • Per-class offline / reconnect tracking, with Remote Reconnected on the first press after a gap or a reboot
  • Reported low-battery events against a dealer-set threshold, published as LAST_REMOTE_BATTERY
  • Privacy Mode: Full Detail, Class Only (no button text published), or Off (detection suspended)
  • Six events and six programming variables, headless — no Navigator tile

2 The classification contract

This driver never invents state and never senses a remote. It publishes assertions you feed it, and it is blunt about the difference.

  • The class is asserted, not measured. Binding 502 means Halo because you wired it that way; the Report Remote Activity CLASS parameter means what you typed. The driver has no way to interrogate the handheld, so a mis-linked binding or a wrong parameter is published with full confidence. Nothing here is a reading off the air.
  • Detection is fed, not sniffed. A remote that is neither linked to a binding nor reported from programming is never detected. Battery level and offline state are reported *in* through their commands — the driver does not poll a remote's battery variable and cannot see a remote leave the mesh on its own.
  • Button text is only as good as its source. Most BUTTON_LINK presses arrive with no button name, so in Full Detail a binding detection usually reads *(button not reported)* rather than a fabricated label. Button text is dependable only when you pass it yourself in the BUTTON parameter of Report Remote Activity.
  • The class set is closed at six. A report carrying any other CLASS token raises Unrecognized Remote Reported and is deliberately not mapped onto a known class — guessing would publish a confident lie about what is in the room. Common spellings of a supported class (SR-250, halo touch, Neeo Remote) are accepted; anything else stays unrecognized.

3 Wire and commission

  1. Add IntegrateIT Remote Detection to the room the remotes live in.
  2. In Connections, link a button from each supported remote (or the keypad/room button that remote drives) to the matching BUTTON_LINK connection. Leave any class you do not have unbound.
  3. For a remote with no linkable button, use Programming instead: on that remote's own button event, call Report Remote Activity with CLASS set to the class key (and optionally BUTTON with the button's name).
  4. Set Detection Sources if you want only one path to count — a privacy-sensitive room often prefers explicit, auditable *Programming Only*.
  5. Set Privacy Mode. Class Only (the default) publishes the class and never the button text; Full Detail additionally publishes which button was pressed; Off suspends detection entirely.
  6. Set Stale After (min) — how long without activity before the room returns to Unknown (1-240, default 10) — and Duplicate Window (ms), which collapses one physical press that arrives twice into a single detection (0-5000, default 750; 0 disables it).
  7. Optionally set the per-class Label properties to friendly names ("Family Room Halo"), and Low Battery Threshold (%) (1-50, default 20) if you feed battery levels in.
  8. Prove it: press a linked remote and watch Active Remote name the class, ACTIVE_REMOTE_CLASS update, and Remote Detected fire in the event log.

Variables: ACTIVE_REMOTE_CLASS, LAST_REMOTE_CLASS, REMOTE_ACTIVE, REMOTE_ACTIVITY_COUNT, LAST_REMOTE_BATTERY, LAST_REMOTE_BUTTON. Key against ACTIVE_REMOTE_CLASS — it always holds the machine-readable class key, never a friendly label. Three ways this wires into Composer:

  • When Active Remote Changed fires and ACTIVE_REMOTE_CLASS is HALO_TOUCH → load the cinema scene. A room can behave differently for a Halo Touch than for an SR-260 without hand-rolled logic on each remote.
  • When Remote Battery Low fires → announce it and read LAST_REMOTE_BATTERY for the level. Remember a battery report is telemetry, not a press: it marks the class seen but never makes it the active remote and never restarts the stale countdown.
  • When Remote Activity Stale fires → dim the room or mark it idle. The room went quiet; LAST_REMOTE_CLASS still remembers who was last active.

How the state moves:

  • Stale is a timeout; offline is a report. The timeout returns the room to Unknown and fires Remote Activity Stale. Report Remote Offline marks that class offline; it returns the room to Unknown only when the class it names is the one currently active, and it stays silent either way — nothing timed out. Both routes owe that class a Remote Reconnected on its next press; a remote pressed for the first time in a merely-quiet room is a plain Remote Detected, never a reconnect. Offline and stale marks are persisted, so they survive a restart.
  • Across a reboot the last class, seen list, and counter are restored (set Restore Last Remote On Boot to No to start clean). The *active* remote is never restored — it is a live fact about the room — so the driver comes up Unknown and the restored class's next press fires Remote Reconnected.
  • Duplicate Window collapses one press delivered as both DO_CLICK and SELECT, or as a binding press that programming also reports, into a single detection. Shortening it live drops the running guards immediately rather than waiting out the old window.

Print Configuration writes sources, privacy, timings, and the active / last / seen state to the Lua output window with the IntegrateIT identity line. It never prints button text.

7 Ownership, privacy, and licensing

This is an original IntegrateIT classifier. It does not bundle another vendor's runtime, source, brand assets, trial, or license. SR-250, SR-260, Halo, Halo Touch, and Neeo name third-party remote products for classification only; IntegrateIT is not affiliated with their makers, and this driver is not their product.

No detection data leaves the controller. The classifier never probes, enumerates, interrogates, or contacts any device on the network — it only classifies the activity Composer hands it, which is what makes it safe in a privacy-sensitive house. No press, class, button text, battery level, customer identity, or project identity is sent anywhere. Privacy Mode governs what is published on-controller: Class Only never lets button text reach a property, a variable, or the log; Full Detail publishes it; Off is a hard suspend that also wipes the already-published detail and suppresses battery and offline reports until you lift it. The shared IntegrateIT license and update services are the only outbound path in the package; they use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below, and the key is never logged or printed by Print Configuration.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks every detection path — both sources and all three report commands — until the Ops Portal has minted and validated a key for that controller. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.
