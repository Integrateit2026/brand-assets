1 Start here

IntegrateIT Enhanced Lighting is a headless interface that binds up to eight Control4 LIGHT_V2 loads — dimmers or switches — and drives them as one coordinated group from a small set of programming commands. It speaks the standard Control4 light-proxy vocabulary — OFF, SET_LEVEL, and RAMP_TO_LEVEL outbound, LIGHT_LEVEL inbound — so it works with any load that implements that proxy, with no vendor SDK or cloud service anywhere in the path. Its reason to exist is two interactions plain per-load bindings cannot give you: a ladder (one button walks a dealer-defined list of levels) and a glide (Hold to move the level continuously, Release to pin it).

There is no Navigator tile. Every interaction arrives as a Composer programming command from a keypad button, a remote, or an event. Nothing moves until you wire the programming that sends those commands.
Ready for controlled commissioning — verified in the Control4 API simulator only. The package, Lua 5.1 runtime, ladder and glide math, capability detection across the OS matrix, the two transition paths, external-change tracking, licensing, persistence, and documentation pass automated QA. This driver is NOT bench-tested: a qualified dealer must still install it against real dimmers on the target controller and confirm the ladder, glide, fades, and external-change behavior on live hardware.

What you get

  • One to eight LIGHT_V2 loads driven as a single group from one set of commands
  • The ladder: each Tap moves to the first level above where the loads actually are, then wraps to Off or holds at the top
  • The glide: Hold Up / Hold Down ramp at a set rate until Release pins the level
  • Nudge Up / Nudge Down, Recall Favorite, All On, All Off for the rest of the range
  • Version-capability detection: a native RAMP_TO_LEVEL on OS 3.3.0+, a driver-emulated stepped fade below it
  • External-change tracking, so a keypad, app, or scene re-anchors the ladder instead of desyncing it
  • Seven events plus five variables (LIGHT_LEVEL, IS_ON, LADDER_STEP, CAPABILITY_TIER, LAST_INTERACTION) for programming
  • The group level survives a controller reboot

2 The feedback contract

This interface keeps one belief about where the group is — the Current Level property and the LIGHT_LEVEL variable. That belief is set only two ways, and it never invents a third.

  • A level it pushed. When you Tap, Nudge, glide, or recall, the interface commands the loads and adopts the level it sent. Any LIGHT_LEVEL report matching a level it just pushed — including every step of a Legacy emulated fade — is its own echo and is absorbed silently.
  • A level a load reports that it did not push. A keypad press, an app slide, or a scene moves the loads without going through this interface. That report is a real external change: the interface adopts it, publishes it, fires External Change Detected, and the next Tap anchors off it rather than off a remembered rung. This re-anchoring is the whole point of the ladder.

Assumed versus observed, stated plainly:

  • On the Enhanced tier the load owns the fade, so the interface pushes only the target level in one RAMP_TO_LEVEL and does not track each rung the dimmer passes through on the way there.
  • Echo suppression is bounded in time — a pushed level stays a plausible echo only for the fade time plus an eight-second grace. A load that drops off mid-transition and never echoes cannot blind external-change detection at that level forever; once the window closes, a report at that level is an external change again.
  • The first level a load reports after the driver loads or the controller restarts is a bind-time snapshot: the interface learning where the room is, not watching it change. It is adopted silently — no Turned On, no Level Changed, no External Change Detected — so programming bound to those events does not re-run on every Director restart. Every report after that baseline is a live change.
  • The group level is saved and restored across a reboot, so programming that reads LIGHT_LEVEL right after a restart sees the room rather than 0. The restored value is an assumption until a load reports; the first report that disagrees corrects it quietly, as a baseline, with no external-change event.

3 Wire and commission

  1. Add IntegrateIT Enhanced Lighting to the room. In Connections, bind each dimmer or switch to Load 1 … Load 8.
  2. Set Number of Loads to how many you wired. Bindings above that number are ignored, and an unwired binding never reports.
  3. Set Level Ladder to the levels each Tap should walk, comma-separated, low to high (default 10,35,70,100). Entries outside 1-100 and duplicates are dropped and the list is sorted; an unusable list falls back to 10,35,70,100. Pick Ladder Wrap — wrap to Off at the top, or hold at the top.
  4. Set Fade Time (ms) for Tap / Nudge / Favorite / All On / All Off transitions, Glide Rate (%/sec) for the holds, Nudge Step (%), and Favorite Level (%).
  5. Set Minimum Level (%) to the lowest level that still looks lit. Nudging or gliding below it turns the group off instead of parking it at an invisible level.
  6. Leave Capability Mode on Auto unless a load misbehaves — see *Capability tiers*. After the driver loads, check Detected OS Version and Capability Tier.
  7. Optionally set License Enforcement and enter a license key — the driver runs in Lenient mode without one (see *Ownership, privacy, and licensing*).
  8. In Programming, send Tap from a keypad button and watch the group step up to the first ladder rung; Tap again and watch it climb. That first observed step proves the binding, the ladder, and the transition path in one action.
Editing Level Ladder, Number of Loads, or Ladder Wrap live re-derives LADDER_STEP but deliberately does not move the lights — a configuration edit should not flick the room while you type.

4 Capability tiers

The interface reads the controller's OS version when it loads and again on Detect Capabilities, then picks how each transition is delivered.

TierChosen whenA transition sends
EnhancedDetected OS 3.3.0 or newer, or Capability Mode pinned to *Enhanced (OS 3.3+)*One RAMP_TO_LEVEL per load carrying the target level and your fade time — the load owns the fade.
LegacyDetected OS below 3.3.0, an unreadable version, or Capability Mode pinned to *Legacy*A driver-emulated fade: timed SET_LEVEL steps that land exactly on the target. Nothing is assumed about how a load handles a ramp time.

Verified across the version matrix:

Reported OSResolved tier
3.2.4 / 3.2.9Legacy
3.3.0Enhanced
3.10.0Enhanced (compared numerically — 3.10 is newer than 3.3, not older)
4.xEnhanced
unreadable, malformed, or accessor missingLegacy (the conservative fallback)

Detected OS Version always reports what was actually read, or Undetected, even when Capability Mode overrides the tier — so you can see both what the controller said and what you told the driver to do. A tier that resolves to something different from the one in force fires Capability Tier Changed; the boot publish does not.

Every immediate push of level 0 — a zero Fade Time, a glide down through the floor, Resync Loads, and the final landing step of a Legacy emulated fade — leaves as an explicit OFF rather than "level 0 but on", so a switch-only load actually opens. The one exception is a *faded* move to 0 on the Enhanced tier: that goes out as a single RAMP_TO_LEVEL to 0, because on Enhanced the load owns the whole fade, including the fade to dark.

5 Program the project

Every interaction is a programming command; every reaction is an event or a variable.

CommandWhat it does
TapMove to the first ladder rung above the current level; at the top, wrap to Off or hold, per Ladder Wrap.
Nudge Up / Nudge DownMove by Nudge Step. Down past Minimum Level turns the group off; up from off jumps to the greater of Minimum Level and one Nudge Step, so it never lands below the lit floor.
Hold Up / Hold DownGlide at Glide Rate until Release, or until the group hits 100 / off.
ReleaseStop the glide and pin the level reached.
Recall FavoriteJump straight to Favorite Level.
All On / All OffGo to the top of the ladder, or off.

Actions (the Actions tab, not events): Detect Capabilities re-reads the OS and re-resolves the tier; Resync Loads re-sends the believed level at every wired load without changing the level or firing events (use it after a load is power-cycled); Print Configuration writes the live state to the Lua output window.

Events: Turned On, Turned Off, Level Changed, Ladder Wrapped, Favorite Recalled, External Change Detected, Capability Tier Changed. Variables: LIGHT_LEVEL (0-100), IS_ON, LADDER_STEP, CAPABILITY_TIER, LAST_INTERACTION.

Event timing you can rely on:

  • A transition event fires when the interface commits the level — the start of the fade, not when the last step lands — so timing is identical on both tiers.
  • The glide fires nothing while it runs. Exactly one Level Changed (plus Turned On / Turned Off if the group crossed off) fires when Release, or the top/bottom rail, settles it.
  • A discrete interaction during a hold ends the hold and wins; a second Hold replaces the first silently; a new interaction mid-fade cancels the fade in flight — the group is never dragged toward a stale target.

Recipes:

  • One-button dimming. Wire a keypad button press to Tap. Each press climbs the ladder; at the top it wraps to Off (or holds), so one button covers the whole range with no press-and-hold.
  • Press-and-hold ramp. Wire button press to Hold Up and button release to Release (and a second button to Hold Down / Release). Hang your "lights settled" logic off Level Changed, which fires once when the glide stops — not fifty times on the way.
  • React to a manual change. When External Change Detected fires, read LIGHT_LEVEL and log it or adjust a scene: you know the room was moved by a keypad, app, or scene rather than by this interface, and the next Tap is already anchored to the new level.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT interface built on the documented Control4 LIGHT_V2 light-proxy contract (OFF, SET_LEVEL, RAMP_TO_LEVEL, and the LIGHT_LEVEL report). It bundles no other vendor's runtime, source code, brand assets, trial system, or license. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

The interface drives your bound loads through the local Control4 proxy and sends nothing to any device vendor or cloud — no light levels, customer identity, project identity, or Control4 credentials leave the controller. The only credential it holds is the IntegrateIT license key, which is never written to the log and never printed by Print Configuration. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all load control — and silences every device event, including off a load report — until the Ops Portal has minted and validated a key for that controller. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
