1 Start here

IntegrateIT Hue Bridge brings a Philips Hue Bridge into Control4 over the bridge's local CLIP API v2 (the on-bridge REST API rooted at /clip/v2, documented at developers.meethue.com). There is no cloud hop: the driver talks straight to the bridge on the LAN over HTTPS, so control is fast and keeps working when the internet is down. Map up to eight slots — each a light, a grouped_light (room/zone), or a scene — by its stable CLIP resource id, then drive on/off, brightness, color temperature, xy color, and scene recall from keypads, room actions, and scenes. Feedback is push: the driver consumes the bridge's /eventstream/clip/v2 Server-Sent-Events stream and reflects each change into Control4 variables and events as it happens, with no polling.

The bridge presents a self-signed certificate. The driver connects over HTTPS with CA-chain verification disabled and pins trust to the bridge's LAN address plus the application key — Signify's documented posture for local integration. Keep the bridge on a trusted LAN segment; a non-LAN address is refused unless Allow WAN Bridge is set to Yes.
Ready for controlled commissioning. The package, Lua 5.1 runtime, link-button pairing, CLIP v2 framing, eventstream parsing, reconnect/backoff, TLS trust model, LAN guard, license gate, and documentation pass automated QA against the Control4 API simulator (hardwareStatus: simulation-verified). A qualified dealer must still complete a fresh install and an observed light test against a real Hue Bridge on the target controller — this release is not bench-tested on physical hardware.

What you get

  • Slot On / Off / Toggle, Set Brightness (0-100), Set Color Temperature (mirek 153-500), and Set Color (CIE xy) for light and group slots
  • Recall Scene for scene slots, with Scene Recalled + LAST_SCENE for programming
  • Link-button pairing built in: press the bridge button, run Pair (Link Button), and the driver claims and stores the application key itself
  • Live push feedback from the eventstream — BRIDGE_ONLINE, per-slot SLOT_n_ON / SLOT_n_BRI, and LAST_CHANGED_SLOT, updated as the bridge reports changes
  • Slot Turned On / Off, Bridge Online / Offline, Scene Recalled, and Event Stream Reconnected events for Composer programming
  • Self-healing: on a stream drop the driver reconnects with bounded backoff and runs one full resync, without hammering the bridge
  • LAN-only destination guard, an application key that is never written to the log, and MAC-locked IntegrateIT licensing

2 The feedback contract

This driver reports what the bridge tells it, and it tells you plainly how it knows:

  • State is pushed, not polled. The driver holds the GET /eventstream/clip/v2 SSE stream open and applies each update as it arrives — a change made from the Hue app, a wall dimmer, or an accessory appears in Control4 within moments, not on a poll tick. A slow Resync Interval (s) heartbeat (default 300) backs the stream up and reads the bridge again if the stream ever stalls.
  • First observation is silent. The first state the driver sees for a resource (from the opening resync or the first event) is adopted without firing Slot Turned On/Off — those fire only on a real change from a value already known. A controller restart wipes what the driver remembered; the first read re-primes it silently.
  • Reachability is truthful. Any HTTP response — even a 403 — proves the bridge is alive and fires Bridge Online; no response at all (code 0) fires Bridge Offline and sets BRIDGE_ONLINE false. A control write is a reachability check too.
  • A stream drop is not an outage. When the eventstream closes, the driver does not assume the bridge is gone — it reconnects with bounded backoff (5 s, doubling to a 60 s cap) and runs one resync to catch anything missed; the resync decides reachability. The first live byte after a drop fires Event Stream Reconnected.
  • Toggle is an assumption when state is unknown. CLIP has no toggle verb, so Slot Toggle inverts the last observed power; from an unknown state it turns the slot on — a Toggle from unknown is an assumption, not an observation.
  • On OS builds too old for C4:url() streaming the eventstream is skipped and the resync heartbeat is the whole feedback path — lower Resync Interval (s) there.

3 Wire and commission

  1. Reserve the bridge's IP address in your router's DHCP table so it never changes. Discover Bridges browses _hue._tcp on the LAN and prints what it finds.
  2. Add IntegrateIT Hue Bridge to a room and enter Bridge IP Address.
  3. Pair. Press the round link button on the bridge, then run Pair (Link Button) within ~30 s. The driver POSTs the claim (first attempt returns Hue error 101 until the button is pressed), stores the returned key in the password-typed Application Key property, and connects. You never handle the key yourself.
  4. Run Test Connection — it prints the bridge_id and confirms the stored key works. Resync Now then lists the lights, groups, and scenes it found (watch the Lua output with Debug Mode = Print).
  5. Map slots. For each of Slot 1–Slot 8, enter light:<rid>, group:<rid>, or scene:<rid> using the CLIP resource ids from the resync. Empty = unused.
  6. Set Target Slot to the slot a command should act on, then wire the commands into Programming (see below).
  7. Optionally enter a License Key. The default Lenient (recommended) mode commissions without one.
  8. Prove it. Set Target Slot to a light slot and run Slot On — watch the light react, SLOT_n_ON flip to 1, and Device Status read Online — ….
One driver instance maps eight slots. Add another instance for a ninth mapping or a second bridge.

4 On the wire

Every request is JSON over HTTPS to https://<ip>. The application key rides in the hue-application-key header — never in the URL — so no log line ever contains it (Debug shows the method and sub-path only). Any body-carrying request declares Content-Type: application/json.

PurposeRequestBody / result
Pair (link button)POST /api (no key){"devicetype":"iit_c4#…","generateclientkey":true} → [{"success":{"username":"…"}}] or [{"error":{"type":101}}]
Resync lights / groups / scenesGET /clip/v2/resource/light · /grouped_light · /scenethe CLIP data[] collections
Live feedbackGET /eventstream/clip/v2 (Accept: text/event-stream)long-lived SSE update/add/delete frames
Power`PUT /clip/v2/resource/{lightgrouped_light}/{rid}`{"on":{"on":true}} / {"on":{"on":false}}
Brightnesssame{"on":{"on":true},"dimming":{"brightness":N}} (0 → on:false)
Color temperaturesame{"color_temperature":{"mirek":M}}
Colorsame{"color":{"xy":{"x":X,"y":Y}}} (clamped 0.0-1.0)
Scene recallPUT /clip/v2/resource/scene/{rid}{"recall":{"action":"active"}}

Replies the driver acts on: 200 on a read, any 2xx on a write; 401/403 means the application key was rejected (re-pair); code 0 is no response (Offline). SSE frames are parsed tolerant of arbitrary chunk boundaries, keep-alive comment lines, and CRLF / LF / bare-CR line endings — bytes accumulate and only a fully terminated frame is applied. Resource JSON is read by cutting each resource object out of the payload and asking that object for its own fields, so the order the bridge happens to serialize keys in never shifts a value onto the wrong light, and a light or scene named with brackets or braces cannot truncate the read. A 429 (undocumented on the local API) is honored with a single bounded retry after Retry-After, never an immediate re-send.

  • When a keypad is pressed → Set Target Slot to 2, then Slot Toggle. Two Composer actions drive room 2's grouped_light from one button.
  • When Slot Turned On fires → read LAST_CHANGED_SLOT and branch. Because the eventstream also sees changes made from the Hue app or a wall dimmer, Control4 reacts to what the lights actually do, not only to what it commanded.
  • When Bridge Offline fires → notify. BRIDGE_ONLINE dropping to false means the bridge left the network — surface it before someone taps a dead keypad.

Control commands are gated by the license: under Strict enforcement an unlicensed controller writes nothing — but resync, pairing, Test Connection, and the eventstream stay live, because reading your own bridge is not a licensed feature. The default Lenient (recommended) mode allows commissioning while License Status carries the nag.

SLOT_n_ON and SLOT_n_BRI hold the last state the eventstream or a resync reported for slot n; they drive automation safely because they are the bridge's own numbers, never invented.

Print Configuration writes the bridge IP, whether the key is set (its length only, never the value), the WAN flag, the resync interval, the streaming mode, the target slot, and each slot mapping to the Lua output window. It never prints the application key or the license key.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation of the published Philips Hue CLIP API v2. It does not bundle another vendor's runtime, source code, brand assets, trial system, or license. Philips Hue and the Hue names are trademarks of Signify; IntegrateIT is not affiliated with Signify, and this driver is not a Philips Hue product.

Nothing leaves the LAN. The driver talks only to the Hue Bridge on your network — there is no cloud service, no Hue account, and no telemetry; bridge state, project identity, and Control4 credentials are never sent to a device vendor. The connection is HTTPS: because the bridge's certificate is self-signed, the driver disables CA-chain verification and pins trust to the bridge's LAN address plus the application key — the transport is still encrypted, and a genuinely broken TLS handshake fails closed (the driver reports the bridge offline and never downgrades to plaintext). The application key lives in the password-typed Application Key property and rides only in the hue-application-key request header, so the driver never logs it — even in Debug Mode, lines show the method and sub-path only, and Print Configuration prints the key's length, not its value.

Lenient (recommended) mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all bridge control until the Ops Portal has minted and validated a key for this controller; resync, pairing, and the eventstream continue either way. Installing this package does not itself mint or activate a controller license. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
