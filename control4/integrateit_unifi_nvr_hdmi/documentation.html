1 Start here

IntegrateIT UniFi NVR HDMI is a display-only Control4 AV source for the Ubiquiti UniFi NVR G2. The NVR has an HDMI output that shows the live camera grid; that output feeds a Control4-controlled AV matrix (proven on an AVPro Edge MX Pro), which distributes it to TVs. Control4 has no native driver that represents the NVR as a video source, so nothing could be bound in Connections and the feed could not be selected in Watch. This driver is the standard integrator fix: a branded "dummy" source whose only job is to put an HDMI OUT binding on the graph so the matrix has something to route.

This driver drives nothing and reports nothing about the NVR. There is no control path and no feedback path, by design. It is a labeled HDMI patch point — the NVR keeps showing whatever grid it is configured to show, and Control4 only decides which rooms see it.
Automated QA covers the rendered package — the AV binding classes, the flat Navigator icon ladder, the name-equals-filename law, and a clean lifecycle in the Control4 API simulator. The v2 source is bench-proven routing video on Daniel's own AVPro Edge matrix; the v3 branded-icon render on live Navigators is still awaiting field confirmation.

What you get

  • A satellite source proxy Composer lists as a selectable Watch source.
  • One HDMI OUT AV binding (video + audio, classes HDMI + STEREO) to drop onto the matrix input the NVR feeds.
  • A branded IntegrateIT aperture-tile icon in Composer and on OS3 Navigators.
  • IntegrateIT self-update — the hand-built v1–v3 could not update themselves.

2 The display-only contract

The honesty core. This driver cannot know or change anything about the NVR. It never powers it, never switches its camera layout, never reads its status. Selecting "Security Cameras" tells the matrix to route the NVR's HDMI OUT binding to a room — nothing more. There is no transport, no polling, no network socket to the NVR at all. A source driver that showed play/pause or a connection state here would be faking it; this one reports only Idle, because idle is the whole truth.

3 Wire and commission

  1. Connect the UniFi NVR G2 HDMI output to a matrix input (directly, or through an HDMI extender). Note the input number.
  2. In Composer Pro, add the driver. Keep the .c4z named integrateit_unifi_nvr_hdmi.c4z — the icon URLs embed the driver name, and a renamed file (a browser's … (1).c4z) loads fine but shows a blank icon. The factory guarantees this identity: the driver slug drives BOTH the c4z filename and every controller://driver/<slug>/… icon URL, so they always match. (The Composer device label — the room-facing name — is independent; it ships as Security Cameras.)
  3. In Connections → Video/AV, bind this driver's HDMI OUT to the matrix input from step 1.
  4. Add the source to each room's Watch experience. It shows in rooms as Security Cameras (rename per project if you like — the label is cosmetic).
  5. Prove it: select Security Cameras in a room and confirm the live grid appears on the TV. If the display blanks, see Troubleshoot (EDID).

Field refresh order (Control4 fact #5 — icon caches are stubborn): after any re-release, Update Driver → File ▸ Refresh Navigators → force-close the mobile app / reboot T3–T4 touchscreens. xmlVersion is bumped on every release so Director notices the new package; the Navigator icon cache still needs the manual nudge to drop the old tile.

4 Program the project

There is nothing on this driver to program, and that is the design. It declares no commands, no device events, and no variables — a dummy source has nothing to command and nothing to report, so a "Select Source" command or a "Cameras Live" event here would be fiction. The only programmable entries Composer shows under this device are the two shared IntegrateIT events, Update Available and License Problem (see Reference below); neither of them says anything about the NVR. Status reads Idle and stays there.

The automation lives one level up, in the two places that genuinely know this source exists:

  • The room. Choosing a Watch source is a room action in Composer Programming — program the room to select Security Cameras (the device's Composer name; rename it and the room action follows the new name). The room is also where you read back which source is currently selected.
  • The matrix. The AV switch driver bound to this driver's HDMI OUT owns the real input switching and whatever feedback that switch reports. If you want an event when the cameras land on a TV, take it from the matrix or the room — never from here.

One recipe of exactly that shape — doorbell rings, cameras hit the theater TV:

Note who does the work: the doorbell driver supplies the trigger, the room performs the selection, the matrix routes the HDMI, and this driver's whole contribution is that Security Cameras is on the room's source list at all. Because the driver never reports anything, a "put it back" step is a timed step you write — there is no "cameras finished" event to wait on. Nothing here is license-gated either: with no actuating path, there is nothing a license could withhold.

It will never be the room's On-Screen Device, and that is not a gap. The "On-Screen Device" row in Connections lists whatever renders Navigator on that room's TV. In an IntegrateIT project that is normally the controller — a CORE 5 or CORE 3, pushing Navigator out its own HDMI — and Control4 also lets an AV receiver hold the row, which is the case its own driver documentation is written around. Either way the row wants an endpoint. This driver sits at the other end of the wire: it is a source that hands video to the matrix, never an endpoint that video is handed to. Control4's stated condition for an onscreen binding is that a video path must also exist — the room has to be able to select that same device as its video endpoint — and a source can't be one.

Bind it there and the room would enter navigation mode and forward every arrow, ENTER and BACK to a driver with no control path — the keys would vanish and the TV would show the same camera grid it already shows. What you want is already here and is a different row: select Security Cameras as the room's video source. The NVR draws its own grid over HDMI; Control4 only decides which rooms see it. No Control4 UI renders on this feed — no menus, no cursor, no per-camera picker. The remote's arrows keep belonging to the CORE.

5 Read status at a glance

Status reads Idle — there is nothing else for a dummy source to report. The standard IntegrateIT properties (Driver Version, self-update, licensing) behave as in every IntegrateIT driver; see Reference. No property here reflects the NVR: the driver has no connection to it and cannot see its state.

6 Troubleshoot methodically

  • "Security Cameras" is not offered in Watch — the source was never bound. Re-check Connections: HDMI OUT must land on the matrix input the NVR feeds.
  • Blank / no-signal when selected — an EDID mismatch. Set that matrix input's EDID to 4K30 or 1080p; the NVR pushes 4K and can out-run a display or a long HDMI run.
  • Blank icon in Navigator — the .c4z was renamed, or the Navigator cache is stale. Restore the filename integrateit_unifi_nvr_hdmi.c4z, then run the field refresh order above (icon caches survive a plain reload).
  • Still stuck — contact support with the room name, the AVPro input number, and the NVR HDMI resolution.

7 Ownership, privacy, and licensing

Nothing leaves the controller. This driver opens no network connection, holds no credentials, and logs nothing — there is nothing for a dummy source to send, and no camera video ever passes through Control4's data path (the HDMI signal travels the AV matrix, not the network). Licensing runs in the shared IntegrateIT framework, but because the driver has no actuating path, no function is license-gated — a missing or invalid key never disables it. Self-update polls the IntegrateIT channel and can stage the next version for a one-click install.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

V Version history

v3.0.2 current2026-08-01
  • The guide now states plainly why this source can never be the room's On-Screen Device, and why that is not a missing feature. Control4's own driver documentation (DriverWorks, *Receiver with Onscreen Binding*) makes a video path the condition of that binding: the room must be able to select the same device as its **video endpoint**. That row holds an endpoint — the controller pushing Navigator out its HDMI, or an AV receiver. This driver is the opposite end of the wire: a provider that hands video to the matrix. Bound there anyway, the room would enter navigation mode and forward every arrow, ENTER and BACK to a driver with no control path; the keys would vanish and the TV would show the same camera grid it already shows. Adding a room-binding connection to make it appear in that list was designed, costed, and declined — an entry that swallows the remote is a fabrication, and a wrong binding id is expensive to retire once it is fielded.
  • The camera-on-TV workflow is pointed at the row that already works: select **Security Cameras** as the room's **video source**. That path is field-proven, and the doc now says outright that no Control4 UI renders on this feed — no menus, no cursor, no per-camera picker — so nobody goes hunting for one.
  • Tests pin the refusal rather than trusting it: the rendered package is now asserted to carry exactly two connections, no `ONSCREEN_SELECTION` class, nothing in the 7000–7999 room-binding range, no type-7 connection, and the unchanged **HDMI OUT** output — plus the standing truth that this driver declares no commands, no device events and no variables of its own. Landing the declined binding turns those cases red.
