1 Start here

This driver is a local Control4 client for a single ESPHome device, spoken over the ESPHome Native API — the same TCP protocol Home Assistant uses, but with no Home Assistant, no MQTT broker, and no cloud in the path. It connects straight to the device's api: component (default TCP port 6053), performs the documented Hello / Connect handshake, enumerates the device's entities, and brings up to eight of them into Composer as labeled slots with typed variables and events. The wire format is the public plaintext-framed protobuf described at esphome.io/components/api.html and developers.esphome.io/architecture/api; this is an original, hand-rolled client of that protocol.

This is a plaintext-only v1. A device configured with an api: encryption: key (Noise) refuses plaintext connections. This driver detects that refusal and reports encryption required — it cannot connect to an encrypted device until a v2 adds the Noise handshake.
Automated QA drives the whole protocol in a simulator: the handshake, entity enumeration, state parsing across arbitrary packet boundaries, switch / light / cover commands asserted byte for byte against the official api.proto, keepalive reconnect, the encryption-refusal and bad-password paths, capability refusals, and the license gate. Scripted peers also cover the awkward ones — a modern device that answers Hello and then never answers the auth request, and a device that takes the socket and never speaks at all — so neither can leave the driver hung. A qualified dealer must still run the on-hardware acceptance (fresh add, real ESP device, reboot, API-version drift) before this is called bench-tested — it is not yet.

What you get

  • A direct, cloud-free bridge to any ESPHome device's switch, binary_sensor, sensor, text_sensor, cover, and light entities.
  • Automatic enumeration: Entities Found lists every entity's type, object id, and key hex — and for covers and lights, what it can actually do ([pos+tilt], [open/close], [dim], [on/off]) so you know before you program it.
  • Eight slots, each with a Slot n Entity binding, SLOT_n_STRING / SLOT_n_NUMBER / SLOT_n_BOOL variables, a Slot n State property, and a Slot n Changed event.
  • Slot n On, Slot n Off, and Slot n Toggle for slots mapped to a switch or a light; Slot n Light Set Brightness 0-100% for dimmable lights; Slot n Cover Open / Close / Stop / Set Position for covers — all staged through that slot's Slot n Level (%) where a level is needed.
  • Keepalive with automatic, backed-off reconnect and re-enumeration, plus Connect, Disconnect, Refresh Entities, and Print Configuration for commissioning.
  • A password-typed credential that is never printed or logged, and a LAN-only destination guard (Allow WAN Destinations is the deliberate opt-out).
What this version deliberately does not do. Light control is on/off plus brightness — colour, colour temperature, white channels, effects, and transition/flash timing all exist in the protocol and are not sent, so a colour bulb is driven as a dimmer. Cover tilt is enumerated and shown but not driven. Fans, climate, locks, numbers, selects, and user-defined services are not driven at all. These are bounds, not bugs — the driver never pretends to a capability it does not implement.

2 The feedback contract

Once subscribed, the device pushes every state change; this driver does not poll. A slot's variables and Slot n State property reflect the last value the device reported. Four honesty points:

  • Until the device reports a value, a slot's state is unknown — not a guessed default. The first reading moves it from unknown to known and updates the variables without firing Slot n Changed; only a genuine later change fires the event. This holds across reconnects: re-enumeration resets each slot to unknown so a reconnect never emits a phantom change.
  • A switch or light Toggle flips the last known state. If the state is still unknown (no reading yet), Toggle sends On. There is no hidden position model — anything claiming to know a state the device never reported would be faking it.
  • A cover that reports no position support has only two truths to tell, so it reports only those: Open or Closed, and SLOT_n_NUMBER of 100 or 0. The driver does not dead-reckon a percentage from travel time. If you need real intermediate positions, the cover itself has to report them.
  • A light's brightness is republished as a whole percent 0-100. When the light is off, the level reads 0 rather than the brightness it would return to — Off and "on at 0%" are not the same claim, and only the device knows the difference.

3 What a cover or light will accept

ESPHome tells the driver what each entity can do during enumeration, and the driver holds it to that. Entities Found shows the answer inline:

TagMeaningAccepts
[pos+tilt]cover reports position and tiltOpen, Close, Stop, Set Position
[pos]cover reports positionOpen, Close, Stop, Set Position
[open/close]cover has no position feedbackOpen, Close, Stop
[dim]light supports brightnessOn, Off, Toggle, Set Brightness
[on/off]light is on/off onlyOn, Off, Toggle

Firing an action an entity cannot honor is refused by name, locally, with the reason in Status — for example Slot 7 light porch_1 is on/off only — it reports no brightness support. Nothing goes on the wire. That refusal is decided from the device's own enumerated flags, so it holds whether or not the connection happens to be up, you find out immediately instead of watching a command vanish silently, and a refusal is the device's answer rather than a driver limitation. If you believe a tag is wrong, the fix is in the ESPHome config (e.g. a light: platform that actually supports brightness), then Refresh Entities.

Two capability details worth knowing, because they are judgement calls:

  • Set Position is gated on the cover's supports_position flag. That flag has been in the protocol since covers were added, so a false there is genuinely the device's answer.
  • Stop is always offered, and is not gated on the newer supports_stop flag. That field was added late, and the wire format cannot distinguish "this firmware reports no stop support" from "this firmware predates the field" — gating on it would refuse Stop on covers that handle it perfectly. If a cover truly ignores Stop, it ignores it harmlessly.

4 Wire and commission

  1. In ESPHome, confirm the device's config has the api: component enabled. If it has an encryption: key:, remove it for this v1 (or wait for v2) — an encrypted device cannot be driven here.
  2. Set Device IP Address to the device's LAN IP and Device Port to its api port (default 6053).
  3. If the device sets api: password:, put it in Device Password (password-typed, never logged). Leave blank if there is none.
  4. Optionally set Client Name — it identifies this controller in the device's connection log — and tune Keepalive Interval (s) and Reconnect Delay (s).
  5. The driver connects automatically once an IP is set. Watch Connection Status walk Handshaking → Authenticating → Connected. On ESPHome 2026.1.0 and newer, Authenticating lingers about three seconds and then clears; nothing is wrong, and Ownership, privacy, and licensing below explains exactly why.
  6. Read Entities Found. Copy an entity's object id (e.g. relay_1) or its key hex (e.g. 0x1a2b3c4d) into a Slot n Entity field.
  7. For a switch or light slot, fire Slot n On and watch the device react and Slot n State flip to On — that round trip proves the whole path. For a cover, Slot n Cover Open does the same.
  8. To use Set Position or Set Brightness, set that slot's Slot n Level (%) property first, then fire the action. Control4 actions carry no arguments, so the level is a property you stage and the action consumes — the same shape as the IntegrateIT Bond shade and LIFX drivers. In programming that is two steps: set Slot 4 Level (%) to 40, then fire Slot 4 Cover Set Position.

5 Protocol on the wire

Each message is one frame: [0x00][varint payload size][varint message type][protobuf payload]. In Debug you will see TX/RX lines naming the frame type and byte count only — never the payload, so a password or value never lands in the log. The driver hand-encodes only the messages it uses (Hello, Connect, DeviceInfo, ListEntities requests, SubscribeStates, SwitchCommand, LightCommand, CoverCommand, Ping, Disconnect) and decodes the matching responses plus the switch / binary_sensor / sensor / text_sensor / cover / light state messages. Unknown message types — the ones a newer ESPHome firmware may add — are consumed by their declared length and skipped, so API-version drift never wedges the parser. The reassembly buffer tolerates a device that splits a frame across TCP segments or coalesces several into one.

Every message id and field number in this driver was read directly off ESPHome's official api.proto and asserted byte for byte in the automated tests: the exact frame a Set Brightness 60% produces, for instance, is pinned to the hex a reference protobuf encoder emits, float bytes included. Two protocol details are handled rather than assumed. A cover's state carries both protocol eras — the deprecated legacy open/closed field and the modern position field — and the driver reads whichever one the entity's own capability makes meaningful. A light's capabilities likewise come in two eras: the modern repeated supported_color_modes list, which the driver accepts in either legal protobuf wire form (packed or unpacked), falling back to the deprecated legacy brightness flag only when a device sends no colour modes at all.

6 Program the project

  • When Slot 3 Changed (a binary_sensor mapped to a door) → check SLOT_3_BOOL; if true, run a "door opened" scene.
  • When a Control4 button is pressed → fire Slot 1 Toggle to flip an ESPHome relay or light, then read SLOT_1_STRING for the confirmed new state.
  • When Slot 5 Changed (a sensor mapped to temperature) → compare SLOT_5_NUMBER against a threshold and drive HVAC programming.
  • At sunset → set Slot 6 Level (%) to 35, then fire Slot 6 Light Set Brightness for an evening level. Setting the level to 0 turns the light off, so one action covers "dim to X" and "off".
  • When a shade keypad button is held → fire Slot 4 Cover Stop to halt a cover mid-travel; while it moves, Slot 4 State reads e.g. 30% Opening and Slot 4 Changed fires on each reported transition. On the next Slot 4 Changed, compare SLOT_4_NUMBER (the cover's position 0-100) to decide whether a shade scene still needs to run.
  • When Entities Enumerated fires (or ENTITIES_ENUMERATED goes true) → the slot bindings are resolved and safe to program against.
  • When Disconnected, Connection Failed, Encryption Required, or Password Rejected fires → surface it. Each names a distinct, actionable cause, and DEVICE_ONLINE drops with them.

7 Read status at a glance

  • Connection Status — Not connected, Connecting…, Handshaking…, Authenticating…, Connected, Handshake timed out, Encryption required, Password rejected, or a Blocked: … destination reason.
  • Status — the narrative line. On a modern device it reads Connected — the device sent no auth acknowledgement (password auth was removed in ESPHome 2026.1.0), and adds ; the Device Password is being ignored by this firmware when you have one set. On a device that did acknowledge, it reads plain Connected.
  • Device Info / DEVICE_INFO — name, model, ESPHome version, and MAC from the device.
  • Entities Found — every enumerated entity as type:object_id keyhex, plus a capability tag on covers and lights (see What a cover or light will accept). ENTITIES_ENUMERATED goes true once that list has been read.
  • Slot n State — the last reported value, or unknown. What it reads depends on the family:

8 Troubleshoot methodically

  • Nothing connects, Connection Status shows Blocked — the destination failed the LAN-only check. Use a private LAN IPv4, or set Allow WAN Destinations to Yes if you truly mean an off-LAN host.
  • Connection Status shows Encryption required — the device has an api: encryption key. Remove it in the ESPHome config, or wait for the v2 Noise build. This v1 cannot connect to it.
  • Connection Status shows Password rejected — the Device Password does not match the device's api: password:. Fix it; the driver deliberately does not retry a rejected password. Only firmware older than ESPHome 2026.1.0 can produce this — newer firmware does not check passwords at all.
  • Connection Status shows Handshake timed out — the device accepted the TCP socket and then never sent a HelloResponse, so it is listening on that port but not speaking the Native API. Check that Device Port really is the api: port (6053 by default) and not a web-server or OTA port, and that the api: component is enabled. This is not a hard stop: the driver tears the socket down and retries on the normal Reconnect Delay cadence.
  • Connected, but Status mentions "no auth acknowledgement" — expected on ESPHome 2026.1.0 and newer; see Ownership, privacy, and licensing. If you have a Device Password set, that firmware is ignoring it — clear it to remove the noise.
  • Connected, but Entities Found is None — the device exposes no switch, binary_sensor, sensor, text_sensor, cover, or light entities of the types this version reads.
  • Status says a light is on/off only or a cover reports no position support — that is the device's own enumerated answer. The command was refused deliberately and nothing was sent; see What a cover or light will accept for the fix.
  • Set Position or Set Brightness did nothing — the level is a separate property. Set Slot n Level (%) first, then fire the action; firing it alone re-sends whatever level is already staged there.
  • A cover reads Open / Closed with no percentage — that cover reports no position, so those two endpoints are all it tells anyone. Nothing is being hidden and no percentage is being withheld.
  • A slot stays unknown — the Slot n Entity value matches no enumerated entity. Re-check the object id or key hex against Entities Found, or fire Refresh Entities.
  • The link drops and recovers on its own — keepalive lost three pings and reconnected with backoff; entities re-enumerate automatically.
  • Still stuck? Run Print Configuration, then contact support@integrateit.tech · (913) 804-7575.

9 Ownership, privacy, and licensing

Be clear-eyed about what the API password buys you on modern firmware: nothing. ESPHome 2026.1.0 removed password authentication. Its api.proto marks the AuthenticationRequest / AuthenticationResponse messages deprecated and states they are "not processed by the server"; the firmware authenticates a client the moment it answers Hello; and the official Home Assistant client never waits for an auth reply at all. This driver matches that: it still sends the auth request (older firmware still reads it), but it waits a bounded three seconds and then proceeds, saying so in Status rather than pretending an acknowledgement arrived. It will never sit at Authenticating… forever, and it will never report a password as accepted when the device said nothing. If a device does reject the password — at any point, including after the driver has already proceeded — that rejection is authoritative and stops the driver cold. A device that takes the socket and never speaks the protocol at all fails loudly as Handshake timed out and retries on the normal cadence. On-hardware confirmation against real ESPHome 2026.1.0+ hardware is still open — this behavior is implemented from the official proto, firmware, and client sources and proven in the simulator, and the driver's hardware status is unchanged until a dealer benches it. If you need the link actually protected, use API encryption (a v2 feature here).

Nothing leaves the controller's LAN: the driver talks only to the device IP you set, and the destination guard refuses off-LAN hosts unless you opt in. The API password lives in a password-typed property and is never printed or logged — Debug records frame type and byte count only, never payloads. Licensing is MAC-locked to this controller: in Lenient mode (default) control still works and License Status carries the activation nag; in Strict mode an unlicensed controller cannot open the connection or send a switch, light, or cover command at all. The license is re-checked at command dispatch and again immediately before each wire write, so a license that lapses between the two still stops the bytes — and the automated suite proves that second check by denying it in isolation. Self-update, when enabled, stages a newer signed build from the IntegrateIT channel without touching your slot mapping.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).

  • Cover and light state. CoverStateResponse (id 22) and LightStateResponse (id 24) are decoded and published to the existing slot variables, with the baseline-silence guarantee unchanged: the unknown-to-first-known reading updates the variables and fires no Slot n Changed, and only observed transitions fire.
  • Per-slot Slot n Level (%) property. Control4 actions carry no arguments, so Set Position and Set Brightness read a staged RANGED_INTEGER setpoint — the same shape the Bond shade and LIFX drivers use.
  • An exact IEEE-754 float32 encoder. Cover position and light brightness are float on the wire and earlier builds only ever decoded floats (for sensors). The new encoder uses integer arithmetic with correct round-to-nearest-even and proper mantissa-carry handling, and the tests assert its output byte for byte against CPython's struct.pack('<f', v) for all 101 percents, for a rounding carry, and for both directions of a halfway tie. It refuses non-finite input, so nan / inf can never reach the wire.
  • On / Off / Toggle actions are relabelled from "Slot n Switch On" to "Slot n On" now that they drive lights as well as switches. The underlying command strings (SLOT_n_ON / _OFF / _TOGGLE) are unchanged, so existing programming keeps working; the SwitchCommandRequest bytes are byte-identical to 0.1.0 and a test pins them.
  • Entities Found now appends a capability tag to every cover and light so an installer can see what an entity will accept before wiring programming to it.
  • The auth phase could wedge the driver forever on modern firmware. ESPHome 2026.1.0 removed password authentication: api.proto marks AuthenticationRequest / AuthenticationResponse (ids 3 / 4) deprecated with "These messages are kept for protocol documentation but are not processed by the server", the firmware's APIConnection::send_hello_response_ now calls complete_authentication_() outright ("Auto-authenticate - password auth was removed in ESPHome 2026.1.0"), and the official client's _connect_hello_login awaits only HelloResponse — "Never wait for AuthenticationResponse". So the reply this driver blocked on never arrives. And the block was silent, not noisy: the socket was up so no reconnect could fire, the connect timeout had already been cancelled, and the keepalive had not started yet, so the driver sat at Authenticating… indefinitely with nothing to break the deadlock. The handshake is now bounded by one timer, re-armed at HelloResponse. No HelloResponse inside 10s fails loudly — Handshake timed out, a Connection Failed event, the socket torn down, and the ordinary reconnect cadence resumes (not a hard stop). HelloResponse but no auth acknowledgement inside 3s takes the documented modern path: the session comes up exactly as a successful acknowledgement would bring it up, and Status says the device acknowledged nothing rather than implying it did. Both bounds sit well inside the firmware's own HANDSHAKE_TIMEOUT_MS of 60s and the official client's 30s connect-request timeout, so the driver always reaches a verdict before either peer gives up on it. A rejection is still authoritative whenever it lands, including after the driver has proceeded, and the legacy path — a device that does answer id 4 — is byte-for-byte and event-for-event what 0.1.0 did. The bound is absolute, not per-frame: only the first HelloResponse of a handshake is acted on. Because StartTimer cancels before it re-arms, a peer that re-announced itself — or a stream that replayed the frame — used to reset the 3s window on every copy and could park the driver at Authenticating… forever, which is the same silent wedge in a different costume; duplicates are now ignored outright and put no second AuthenticationRequest on the wire, matching the official client, which also stops listening after the first HelloResponse. A genuine re-handshake on a new socket still runs, because beginHandshake clears the flag. Verified against scripted peers for all five cases; bench confirmation on real 2026.1.0+ hardware remains open and hardwareStatus is unchanged.
  • The Connect action on a live session wedged the driver. Connect re-opened the socket without going through the disconnect path, so gConnected was still true when the controller reported the new socket ONLINE — and the online == gConnected guard in OnConnectionStatusChanged swallowed that notification whole. The handshake never started on the new socket, the connect timeout had already been cancelled, and no OFFLINE was coming, so the driver sat online-but-unauthenticated until the driver was reloaded; every command answered "not connected". A duplicate ONLINE is now ignored only when the session it belongs to is genuinely already usable or already handshaking; anything else (re)starts the handshake.
  • A device whose name contained a refusal keyword was hard-stopped as encryption-required. The Noise-refusal detector substring-matched indicator / Noise / handshake / encryption against the raw RX buffer before framing and unconditionally while unauthenticated. HelloResponse carries server_info and the device hostname, so an ESPHome node legitimately named e.g. indicator-panel tripped it — reporting "This device requires API encryption", setting the do-not-retry flag, and refusing to connect to a device that was answering perfectly. The sniff now runs last, only on a stalled buffer that made no framing progress and cannot be the start of a real frame, which is exactly the condition it was written to detect. The non-0x00 Noise indicator byte is caught in the frame loop as before, and both original refusal fixtures still pass.
  • Non-finite property values could reach the wire. intProp fell back with tonumber(...) or default, which does not catch a value that parses as a number but is not finite: tonumber("nan") succeeds, tonumber("1e400") is inf, math.floor(nan) is still nan, and every clamp comparison against nan is false — so a nan sailed through the range check intact. It now falls back to the default on nil, nan, and ±inf. This was latent in 0.1.0 (it could reach the keepalive and reconnect intervals) and would have become a wire-visible defect the moment a float setpoint existed.
  • Light control is on/off plus brightness only. Colour, colour temperature, white channels, effects, and transition / flash timing all exist in LightCommandRequest and are deliberately not sent; a colour bulb is driven as a dimmer. Colour is a later version, not a half-implementation here.
  • Cover tilt is enumerated and surfaced but not driven — no tilt command is sent even when supports_tilt is true.
  • Cover Stop is always offered rather than gated on the enumerated supports_stop flag. That field was added late to the proto and protobuf cannot distinguish "reports no stop support" from "predates the field", so gating on it would refuse Stop on covers that handle it perfectly. supports_position is an original field, so a false there is the device's answer and Set Position does gate on it.
  • A cover without position support reports only its endpoints (0 / 100). The driver does not dead-reckon a position from travel time.
  • Encryption posture is unchanged: plaintext + legacy password only. Noise stays parked, and a device with an api: encryption key is still reported as encryption-required rather than retried.
  • On ESPHome 2026.1.0 and newer the API password does nothing — that release removed password authentication entirely. The driver still sends the auth request for older firmware, proceeds on the documented silence, and says plainly in Status that the device acknowledged nothing and that a configured password is being ignored. It does not pretend to an authentication it did not get, and it does not offer encryption as a substitute in this version.
  • Every message id and field number was byte-verified against the official api.proto (github.com/esphome/aioesphomeapi, MIT) on the day of the change, read from each message's option (id) annotation and field declarations.
  • Repeated supported_color_modes is decoded in both legal protobuf wire forms — packed (wire type 2) and unpacked repeated (wire type 0) — because ESPHome's encoder is hand-written firmware and assuming one form would bet a light's capability detection on an implementation detail. Both are tested.
  • Runtime suite grew from 305 to 573 checks, and the 0.1.0 suite still passes unchanged (305/305) against this body. The new coverage was validated by mutation: 22 deliberate defects (wrong message ids, wrong field numbers, a wrong ColorMode mask bit, dropped carry handling, dropped nan guards, removed capability gates, each wire form of the colour-mode list) were each confirmed to fail the suite. One probe initially passed — removing the wire-write-time license re-check — which exposed a real gap: the ordinary Strict test is caught by the dispatch-time gate and never exercised the second one. A test that denies the license only on the wire-write call now covers all three write paths.
  • A second review pass re-ran that mutation (all three wire-write gates removed, dispatch gates intact: 14 fails, so the test is real) and found one more gap of the same kind. Both round-half-even tie tests happened to be ties that round up, so an encoder that always rounded a tie up passed them — the property being claimed was never actually pinned. The two round-down midpoints (0.5 + 1·2⁻²⁵ and 0.5 + 5·2⁻²⁵, which CPython packs as 0000003f and 0200003f) are now asserted, and the always-round-up mutant fails.
  • All 101 percent-to-float bytes and all 11 expected command frames were re-derived from scratch with CPython during review — an independent encoder, not a re-read of the table — and every byte matched.
  • New adversarial coverage beyond the tie fix: colour modes arriving packed and unpacked in the same message; unknown fields of all four wire types interleaved inside CoverStateResponse and LightStateResponse; a position cover ignoring a contradictory legacy_state; the documented position-over-legacy_state precedence on a cover without position support; a nil value never stamping a slot variable it does not own (a text / switch / binary reading must not zero a live SLOT_n_NUMBER); the encoder refusing an out-of-range magnitude instead of emitting inf; and a proof that the whole 0-100 input domain encodes with no sign bit and no subnormal, so a -0 setpoint cannot put a signed zero on the wire.
v0.1.02026-07-26
  • Initial release candidate: a clean-room Control4 client for the ESPHome Native API, speaking the plaintext-framed protobuf wire protocol directly over TCP (default port 6053) with a hand-rolled minimal codec — no third-party library. Specified from ESPHome's public docs (esphome.io/components/api.html, developers.esphome.io/architecture/api and .../protocol_details) and the public api.proto message-id / field annotations.
  • Handshake: HelloRequest/HelloResponse, then ConnectRequest with the optional legacy plaintext password and ConnectResponse (invalid_password surfaces a Password Rejected event with no retry storm), DeviceInfoRequest, a full ListEntities enumeration, and SubscribeStates.
  • Entities: switch, binary_sensor, sensor, and text_sensor are enumerated and summarized in Entities Found. Up to eight are mapped by object id or key hex into labeled slots, each publishing SLOT_n_STRING / SLOT_n_NUMBER / SLOT_n_BOOL variables and a Slot n Changed event. The unknown-to-first-known transition updates the variables but fires no event.
  • Control: switch slots expose On / Off / Toggle, each gated on the license at dispatch and re-checked immediately before the wire write.
  • Resilience: keepalive Ping every interval with a three-missed-reply reconnect, bounded-backoff reconnect, entity re-enumeration on reconnect, a reassembly parser tolerant of arbitrary chunk boundaries and unknown message types, and a capped RX buffer.
  • Honest v1 boundary: PLAINTEXT + LEGACY PASSWORD ONLY. A device with an api: encryption key (Noise) refuses plaintext; the driver detects the refusal frame and reports "This device requires API encryption; disable the key or wait for v2." rather than retrying. No Noise/ChaCha20 in v1.
  • Safety: LAN-only destination guard with an Allow WAN Destinations override, a password-typed credential that is never printed or logged, Debug that logs frame type + byte count only (never payload content), and MAC-locked IntegrateIT licensing.
