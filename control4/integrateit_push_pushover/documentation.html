1 Start here

IntegrateIT Pushover Notifier turns any Control4 programming event into a Pushover push notification on the homeowner's and dealer's phones and tablets. Wire a door left open, an alarm, a low temperature, or a scene to one of the six Send actions and the driver POSTs the alert outbound over HTTPS to api.pushover.net. There is no local device to find, bind, or wire — the driver is a cloud client built to the public Pushover Messages API (https://pushover.net/api), and the only things it needs are your Pushover credentials.

CLOUD-DEPENDENT, BRING-YOUR-OWN-KEY. Delivery requires the controller to reach api.pushover.net over HTTPS and a working Pushover account; if either is down, nothing is delivered. IntegrateIT embeds no Pushover token — the dealer supplies their own application and user or group credentials, and the customer's own Pushover account pays for and receives every message.
Ready for controlled commissioning. Credential gating, the success/failure event and result mapping, Emergency escalation parameters, the 1024-character codepoint cap, and credential redaction all pass the automated simulator. This is a release candidate: a qualified dealer must still send a live test to a real Pushover account and confirm it arrives on a real phone before relying on it.

What you get

  • Six Send actions — Send Message 1 through Send Message 4, Send Test Notification, and Send Emergency Alert — callable from any Control4 event
  • Four saved message slots — Message 1 Title / Message 1 Body through Message 4 Title / Message 4 Body — with a Default Title fallback when a slot's title is blank
  • Five priority levels (Lowest, Low, Normal, High, Emergency) selected once in Default Priority, and one Default Sound applied to every send
  • Emergency (priority 2) escalation that repeats until acknowledged, tuned by Emergency Retry (s) and Emergency Expire (s)
  • Notification Sent and Notification Failed events plus a Last Notification result string for programming feedback
  • Local pre-flight before any network call: a 30-character credential check, an empty-message guard, and a 1024-character message cap
  • Credential redaction — the token and user or group key are never written to the log

2 Key, data, and cost

This is a cloud notification driver. Be honest with the customer about whose key it uses, what leaves the controller, and what "Sent" does and does not prove.

  • Whose key. The dealer registers a Pushover application to get an Application API Token and copies a User or Group Key for the recipients. Both are 30-character letters-and-digits strings, stored as password properties, and validated before every send. IntegrateIT ships no credential of its own.
  • What leaves the LAN. Each Send makes one outbound HTTPS POST to api.pushover.net carrying the token, the user or group key, the message body, the title, the numeric priority, the sound, and — for Emergency only — the retry and expire values. The message text you configure transits Pushover's servers to reach the phones. Nothing else from the project is sent: no other device state, no Control4 credentials, no project identity.
  • Who pays. The customer's own Pushover account. Pushover's free tier allows 10,000 messages per user per month; anything beyond that is the account holder's concern, not this driver's.
  • What "Sent" means. Success is strictly HTTP 200 with "status":1 in the response — Pushover *accepted* the message. Last Notification reads Sent at that point. That is not proof the phone displayed it, that Do Not Disturb let it through, or that a person read it; the accept response carries none of that and this driver claims none of it. For an Emergency alert, Sent likewise does not mean acknowledged — only Pushover's own app tracks the acknowledgement that stops the re-alerts. Anything claiming delivery-to-eyeballs would be faking it.
  • Redaction. Credentials are sent but never logged. Debug output carries only the title, the numeric priority, and the encoded byte count. The driver's configuration print reports token and key presence and format validity, never the values themselves.

3 Wire and commission

  1. In your Pushover account, register an application to get its Application API Token (30 characters, letters and digits). Copy the User Key, or a delivery Group Key, that should receive the alerts (also 30 characters).
  2. Add IntegrateIT Pushover Notifier to any room — there is no binding or serial port to wire. Paste the token into Application API Token and the recipient key into User or Group Key. Both are stored as passwords. The driver Status line reads Ready once both are present and well-formed, or Credentials look malformed (expect 30 letters/digits) if a paste is the wrong length or contains a stray character.
  3. Confirm the controller can reach the internet. This driver needs outbound HTTPS to api.pushover.net; there is nothing to reach on the LAN.
  4. Press Send Test Notification. A test push should arrive within seconds; Last Notification reads Sent on success or a short reason on failure. Watching that push land on a real phone is the step that proves the whole path — credentials, internet, and the recipient key — works.
  5. Fill in the four slots (Message 1–4 Title / Body) with the alerts you want, then wire each Control4 event to the matching Send Message N action. A blank title falls back to Default Title; a blank body fails locally as an empty message rather than sending nothing.
  6. For a critical alert, use Send Emergency Alert. It reuses Message 1 Body at priority 2 and repeats until acknowledged; if Message 1 Body is blank it sends a built-in default so the most critical alert always delivers. Tune Emergency Retry (s) and Emergency Expire (s) for how often and how long Pushover re-alerts.
Setting Default Priority to Emergency makes every ordinary slot send repeat until acknowledged. Send Test Notification deliberately caps itself to High in that case, so commissioning never nags the homeowner's phone — but your wired slots will, so choose Emergency deliberately.

4 The Pushover request on the wire

Every send is one HTTP POST, built to the public Pushover Messages API and captured 2026-07-16:

POST https://api.pushover.net/1/messages.json
Content-Type: application/x-www-form-urlencoded
token=<app>&user=<key>&message=<text>&title=<t>&priority=<n>&sound=<s>
ParameterSourceNotes
token / userApplication API Token / User or Group KeyRequired; percent-encoded; 30 chars each
messageThe slot body, Test Message, or emergency fallbackRequired; capped at 1024 codepoints
titleThe slot title, else Default TitleOmitted when empty
priorityMapped from the nameLowest −2, Low −1, Normal 0, High 1, Emergency 2
soundDefault Sound (e.g. pushover, siren, none)Omitted when empty
retry / expireEmergency Retry (s) / Emergency Expire (s)Appended only for priority 2

Success is strictly HTTP 200 with a "status":1 body → Notification Sent and Last Notification Sent. Any other code or status fails: Notification Failed fires and Last Notification reads Failed: HTTP <code>. Two failures never reach the wire — the driver catches them locally and records Failed: invalid credentials (a token or key that is not 30 letters/digits) or Failed: empty message, so a guaranteed rejection never burns a round-trip.

Emergency (priority 2) is the one path that carries retry and expire, which the API requires there. Emergency Retry (s) clamps to 30–300 and Emergency Expire (s) to 60–10800; expire is additionally raised to at least the retry value, because an expire below retry would let Pushover re-alert only once and defeat the escalation. The message cap is 1024 UTF-8 *codepoints*, truncated on a codepoint boundary — never mid-character — so non-Latin text is neither corrupted nor silently over-truncated.

Three ways these wire into Composer programming:

  • When a door contact reports "left open" for 5 minutes → Send Message 1. Pre-fill Message 1 Body with "Garage left open" and let one Control4 event push it.
  • When the security panel alarms → Send Emergency Alert. Priority 2 re-alerts the phone until someone acknowledges it in the Pushover app — the right tool for an alert that must not be missed.
  • When Notification Failed fires → light a fault indicator or fall back to another channel. LAST_STATUS and Last Notification carry the reason (HTTP 429, invalid credentials, empty message) so programming can branch on why a critical alert did not go out.

The four Send Message 1–Send Message 4 actions carry no per-action priority: they always send at whatever Default Priority holds. Send Emergency Alert always forces priority 2; Send Test Notification never escalates past High. Sends are gated by the license: with License Enforcement set to Strict an unlicensed controller sends nothing, while the default Lenient mode allows commissioning and keeps the nag on License Status.

8 Ownership, privacy, and licensing

This package is an original IntegrateIT clean-room implementation of Pushover's public Messages API (https://pushover.net/api). It bundles no Pushover runtime, source, brand assets, trial system, or credential. Pushover is a trademark of its owner; IntegrateIT is not affiliated with Pushover and this driver is not a Pushover product. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

What leaves the controller is exactly the notification: the message text and title you configure, plus the token and recipient key needed to deliver it, POSTed to api.pushover.net. No other device state, project identity, or Control4 credential is sent anywhere. The token and user or group key live in password properties and are never logged, printed, or included in diagnostics. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks all sends until the Ops Portal has minted and validated a key for that controller. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
