1 Start here

IntegrateIT Shelly RGBW drives one Gen2+ Shelly light — a Light dimmer, an RGB color light, or an RGBW color-plus-white fixture — over the device's own local JSON-RPC 2.0 API (POST /rpc, per shelly-api-docs.shelly.cloud, the Gen2 Light / RGB / RGBW components). No Shelly Cloud account, no issued credentials, nothing leaves the LAN. The generic IntegrateIT Shelly driver models a relay or a basic roller; this one is the dedicated light: on/off, brightness, RGB color, and a raw white channel, with the device's real state read back on every action.

Automated QA covers detection, component enumeration, every control verb across all three component types, two-way feedback, the LAN-only safeguard, license enforcement, and the 429 backoff — in the IntegrateIT driver simulator. A qualified dealer must still verify on representative Shelly light hardware before calling an install field-validated.

What you get

  • On, Off, and Toggle over <Component>.Set / <Component>.Toggle.
  • Set Brightness (1-100%) with an optional fade time.
  • Set Color (RGB 0-255 per channel) on RGB and RGBW components.
  • Set White Level (0-255) on RGBW components.
  • Real two-way state: POWER, BRIGHTNESS, RGB, and WHITE are read back from <Component>.GetStatus — never assumed.
  • Component-discovery honesty: Detect Device enumerates the device's actual components and refuses a slot the hardware does not expose.
  • Fault reporting (overtemp, overpower, overvoltage, undervoltage, overcurrent) surfaced from the component's own errors[].

2 The feedback contract

This is a reporting device. Every value the driver shows was reported by the Shelly, not inferred from the last command — anything claiming otherwise would be faking it. The honest consequences:

  • Until the device answers, state is Unknown. The first observed value is absorbed silently: an unknown-to-known transition fires no event, so a bind or a reboot never raises a phantom Turned On the light did not just make.
  • Capability honesty. The white channel exists only on RGBW; color exists only on RGB and RGBW. Set Color on a Light and Set White Level on an RGB or Light are refused locally, each naming the missing channel in Last Error — the driver never fires a request the component cannot honor.
  • Faults are read, not guessed. overtemp / overpower / overvoltage / undervoltage / overcurrent are published from errors[] to Last Error with a Fault Detected event. A token is matched on its prefix, so a colon-suffixed detail (overpower:channel_0) still fires.

3 Wire and commission

  1. Power the Shelly and set its profile in the Shelly web UI so it exposes the light component you want (rgbw / rgb / light). This driver does not change the device profile.
  2. Note the device's LAN IPv4 address and reserve it in the router's DHCP table so it never moves.
  3. Add this driver to the light's room. Set Shelly IP Address to the dotted IPv4 address (never a Shelly Cloud address).
  4. Set Component Type (RGBW / RGB / Light) and Component ID (0-3 — most single-light devices are 0) to match the device.
  5. Leave Password blank if the device has authentication off (the Shelly default). If auth is on, enter the device password; see Troubleshoot.
  6. Run Detect Device. It reads Shelly.GetDeviceInfo, refuses a Gen1 device, then enumerates Shelly.GetComponents and confirms your component exists. Detected Component shows the resolved key (e.g. rgbw:0) or the mismatch reason.
  7. Run Power On, then watch Device Status flip to On and the POWER variable go to 1 — that is the device reporting back, proving the round-trip works.

4 Protocol on the wire

Gen2+ speaks JSON-RPC 2.0 over HTTP. Control is a POST to /rpc:

POST /rpc
{"id":7,"method":"RGBW.Set","params":{"id":0,"rgb":[255,64,0],"brightness":80,"transition_duration":2}}

Status is read back with <Component>.GetStatus on the poll timer and after every action. In Debug Mode → Print you see the method and path of every call — never the body and never the password. Documented replies you may see: an HTTP 401 (auth enabled — see Troubleshoot), an HTTP 429 with a Retry-After header (the driver enters a bounded backoff and stops sending until it elapses), or a JSON-RPC error object in a 200 body (the device refused the request; the message lands in Last Error).

State is refreshed by polling — the Gen2 outbound-WebSocket NotifyStatus push is a deliberate v1 non-goal, matching the shipped IntegrateIT Shelly and Shelly Cover drivers. A shorter Poll Interval (s) tightens feedback latency at the cost of LAN traffic; 0 polls only after an action.

5 Program the project

Wire the driver's events and variables into Composer:

  • When the light fires Fault Detected → send a push and turn the circuit off. Last Error carries the token (overtemp, overpower:channel_0, …) for the notification text.
  • When a keypad scene runs → set Red/Green/Blue, then call Set Color. The Color Changed event fires once the device reports the new value back, so downstream logic reacts to the confirmed state, not the request.
  • When the room goes to Night → set Brightness to 10 and call Set Brightness. Watch Brightness Changed to confirm the dimmer took it.

Variables for programming: POWER (bool), BRIGHTNESS (0-100), RGB (r,g,b string), WHITE (0-255), DEVICE_ONLINE (bool), LAST_ERROR, MODEL, and COMPONENT (the resolved key).

6 Read status at a glance

  • Device Status — live reachability and the last light state or gate reason (On, Off, Ready: driving rgbw:0, Blocked: …, Component mismatch: …, an auth or rate-limit note).
  • POWER — 1 on, 0 off; drives automation safely once DEVICE_ONLINE is 1.
  • BRIGHTNESS — last reported level 0-100. RGB — last reported r,g,b. WHITE — last reported white 0-255 (RGBW only). All Unknown until the device first reports.
  • Detected Component — the resolved component key, or the reason the configured slot was refused (with the list of components the device actually has).
  • Last Error — None, a device fault token, or a refused-command reason.

8 Ownership, privacy, and licensing

Nothing leaves the LAN. The driver talks only to the device IP you set, over plain local HTTP — Shelly Cloud is never contacted. The device Password is stored in the Control4 property vault, used only to answer the device's own auth challenge, and is never written to the log (Debug prints method and path only).

Licensing is MAC-locked to this controller. In the default Lenient mode the light still works and License Status nags for activation, so a dealer can wire and verify before a key is minted; in Strict mode an unlicensed controller cannot drive the light, though status polling continues. The license is checked when a command is issued and re-checked at the wire-write moment, so a key revoked mid-flight drops the write rather than actuating the device. The driver self-updates from the IntegrateIT brand-assets channel when Automatic Update Check is on.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

License StatusWhat it means
LicensedBound to this controller and activated.
Not activated, Lenient modeNo valid key yet. Control still works in Lenient mode; enter a key for production.
Bound elsewhereThe key is active on another controller. Unbind it in the Ops Portal to move it here.
Revoked / InvalidContact IntegrateIT. Under Strict enforcement control stays disabled until a valid key is entered.
Replaced the controller? Click Unbind in the Ops Portal. The next controller to activate with the key becomes its new home. The driver re-checks on boot and every 12 hours, and keeps working through brief internet outages (it re-validates when the relay is reachable again).

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
