1 Start here

IntegrateIT Appliance Status turns one bound run-status sensor into a clean, programmable On/Off picture of an appliance for Control4. Bind a current-sensing switch, a flow switch, or a dry contact that signals running versus idle to the Status Sensor input (binding 1), tell the driver which electrical state means running, and it publishes a debounced Appliance State of On, Off, or Unknown — with the IS_ON, APPLIANCE_STATE, RUNTIME_HOURS, and LAST_CHANGE variables and Turned On / Turned Off events for programming. It rides the standard Control4 contact-sensor binding; there is no external protocol, cloud, or vendor API involved.

Its value over a bare contact is the runtime meter. While the appliance is On the driver accumulates run time and publishes it as RUNTIME_HOURS and a human-readable Runtime Display. Set a Runtime Threshold (hours) and it raises a one-shot Maintenance Due event when the meter crosses it — the hook for pool-pump filter changes, well-pump service, or UV-lamp replacement. It is a headless monitor: it reports state, runtime, and reminders for programming and dashboards; it does not switch the appliance and shows no Navigator tile.

Ready for controlled commissioning. The package, Lua 5.1 runtime, sensor-polarity derivation, minimum-run debounce, the runtime meter, the maintenance one-shot, reboot persistence, the license gate, and this documentation pass automated simulation QA. This driver is simulation-verified, not bench-tested: a qualified dealer must still bind a real run-status sensor on the target controller and confirm the derived On/Off tracks the appliance before relying on it.

What you get

  • A debounced Appliance State (On / Off / Unknown) derived from one bound current, flow, or dry-contact sensor
  • Configurable Running Active State polarity, so the same driver fits a switch that closes on load or a flow switch that opens on flow
  • A Minimum Run (s) debounce that rejects brief surges and dropouts so a blip never toggles the state
  • An accumulating runtime meter published as RUNTIME_HOURS and Runtime Display, persisted across reboots
  • An optional Runtime Threshold (hours) that fires Maintenance Due once for filter, pump, or UV-lamp service
  • Reset Runtime and Acknowledge Maintenance actions, plus Turned On / Turned Off / Maintenance Due / Runtime Reset events

2 The derived-state contract

This driver never sees the appliance. It sees exactly one thing — the CLOSED / OPENED reports from the bound contact sensor — and Appliance State is derived from those reports and the Running Active State polarity, nothing more. A correctly set polarity is the whole accuracy story: set it backward and the driver reports the appliance inverted, with complete confidence. Anything it published beyond what that one contact reports would be faking it. Reports on any binding other than Status Sensor are ignored.

The two report forms mean different things on the wire:

  • A bare CLOSED or OPENED is a live change. It runs the Minimum Run (s) debounce; only a reading that survives the window commits — publishing the new state, firing Turned On or Turned Off, and starting or stopping runtime accrual.
  • A STATE_CLOSED / STATE_OPENED is the bind-time snapshot Director replays when the driver loads. It establishes On/Off silently — no transition event, no back-dated runtime — and only syncs the meter to that state.

Two honesty consequences follow, both proven by the sim:

  • Runtime is metered forward, never back-dated. An appliance already running when the driver binds starts its meter from that instant, not from whenever it physically switched on. A pump or UV lamp that never toggles still accrues toward its reminder — but the first partial cycle can be short.
  • An Off snapshot freezes the meter. If Director replays STATE_OPENED mid-run, accrual stops so runtime can never climb under an Off display.

Before any report arrives, state is Unknown — the driver refuses to guess. The runtime total and the maintenance flags are persisted, so accumulated hours and an already-raised reminder survive a Director restart, reload, or power loss rather than zeroing. The meter advances at one-minute resolution, so a single on-cycle can under-count by up to a minute; over a multi-hour service interval that is negligible.

Contact delivery is hardware-unverified. The simulation injects CLOSED / OPENED / STATE_* directly, so a passing sim does not prove that a given stock contact-sensor driver delivers state this way on your controller. Bench-verify the real sensor on the target hardware before you rely on the derived state or the runtime meter.

3 Wire and commission

  1. Wire the run-status sensor — a current-sensing switch clamped on the appliance's load conductor, a flow switch, or a dry contact — and bind its Control4 contact-sensor driver to Status Sensor (binding 1) in Connections.
  2. Set Running Active State to match the sensor: a current-sensing switch usually closes under load (the default, Contact Closed); some flow switches open on flow (Contact Open).
  3. Set Minimum Run (s), the debounce window. On/off changes shorter than this are treated as electrical blips and ignored; the default 5 s suits most motors and pumps, and 0 commits every change immediately.
  4. For a service reminder, set Runtime Threshold (hours) to the manufacturer's interval; leave it 0 to disable. Optionally set Appliance Label for friendlier Status text.
  5. Run Print Configuration and read the Lua output to confirm the polarity, debounce, threshold, and label are what you intended.
  6. Energize the appliance and watch Appliance State turn On after the debounce (and IS_ON flip to 1); switch it off and watch it return to Off. That transition is the proof the binding and polarity are correct.
The driver is headless — there is no Navigator tile to tap. Everything it produces is variables and events for Composer, so commission by watching the properties and the Lua output, not a room icon.

Recipes using this driver's own names:

  • Service reminder: When Maintenance Due fires → push a notification and add a "service the pool pump" to-do. After servicing, run Reset Runtime from the Actions tab, which zeroes the meter and re-arms the reminder for the next interval.
  • Runaway-pump alarm: When Turned On fires → start a project timer; if Turned Off has not fired by the expected cycle time, announce it. Show RUNTIME_HOURS on a dashboard for the running total.
  • Silence a reminder without losing hours: Run Acknowledge Maintenance from the Actions tab. It clears the due flag without zeroing the meter, so RUNTIME_HOURS keeps climbing. Read it as mute, not snooze: the acknowledgement latches and survives a reboot, so Maintenance Due will not fire again until Reset Runtime clears both.

Reset Runtime, Acknowledge Maintenance, and Print Configuration are Composer Actions tab entries — a dealer clicks them during service. This driver publishes no device-specific commands, so programming reacts to its events and reads its variables rather than calling it.

Reset Runtime and Acknowledge Maintenance are license-gated: under Strict enforcement an unlicensed controller performs neither and fires no event. Print Configuration is never gated. State derivation and the runtime meter keep running regardless of license — monitoring your own appliance is not a licensed feature.

7 Ownership, privacy, and licensing

This package is an original IntegrateIT implementation built on the documented Control4 contact-sensor binding contract. It does not bundle another vendor's runtime, source, brand assets, trial system, or license. Driver engineering, Control4 integration, documentation, QA, licensing, updates, and support are provided by IntegrateIT.

Nothing leaves the controller. The driver reads one local contact sensor and publishes local variables, events, and the persisted runtime meter — it sends no appliance state, customer identity, or project data to any external device or cloud. The shared IntegrateIT license and update services use the controller identity, driver slug, version, configured license key, and update channel as documented in the reference below; the license key is never written to the log.

Lenient mode allows commissioning without an activated key and keeps License Status visible. Strict mode blocks the Reset Runtime and Acknowledge Maintenance actions until the Ops Portal has minted and validated a key for that controller; state derivation and metering continue either way. Installing this package does not itself mint or activate a controller license.

L Licensing

This driver is licensed per controller. Each license key locks to one controller's MAC address the first time it activates, exactly like other professional Control4 vendors.

  1. Generate a key for the customer in the IntegrateIT Ops Portal → Licenses.
  2. Paste it into the driver's License Key property in Composer.
  3. On activation the key binds to this controller; the License Status property shows Licensed.

Enforcement. License Enforcement defaults to Lenient (recommended): the driver works the moment it is wired, so you can stage and verify a job before a key is minted, and a paid site keeps running if the license server is ever unreachable. License Status still nags until a key activates. Set it to Strict to disable all control until a valid key binds.

U Automatic updates

The driver checks IntegrateIT for a newer version on boot and once a day. There is no need to re-add the driver. When an update is available the Update Available property shows the new version and the driver fires its Update Available event.

  1. The driver flags Update Available: vX.Y.Z in its properties (or run the Check for Update Now action).
  2. Run the Download & Stage Update action. The new .c4z is fetched onto the controller.
  3. In Composer, right-click the device, then choose Update Driver. Your settings, bindings, and programming are preserved.
Tip: wire the Update Available event to a notification so you know the moment a new build ships.

D Diagnostics and self-test

Every IntegrateIT driver carries two read-only Actions for the field. Run Diagnostics prints a report of what the driver has already observed — version and Lua runtime, license mode and cached activation, update channel and any staged build, every armed timer with its interval, which dealer-supplied properties are still empty, and the last few Status messages. It probes nothing, sends nothing, and changes nothing, so it is safe on a live job. Run Self-Test checks the shared layer itself — string and URL encoding, version comparison, the non-finite number guard, the timer registry, and the persistence store — and ends with SELF-TEST PASS or a per-check failure. It stays local: no network, no device commands.

Neither Action is license gated, on purpose: you reach for them when a site is broken, and the license may be the broken thing. Values are never printed — a key or secret is reported only as set or NOT SET, so the output is safe to paste into a support ticket. Both print to the Lua output window (Composer → the driver's Lua tab).
